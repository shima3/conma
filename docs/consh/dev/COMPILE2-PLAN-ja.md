# ConSh の値と文脈の表し方を変える計画（段階 2）

ConMa 版の ConSh（最適化版）が、文を実行するたびに作って捨てる値と、たどる Dict を減らす計画である（2026-11-17）。[COMPILE-PLAN-ja.md](COMPILE-PLAN-ja.md) の段階 2 にあたる。段階 1（今のクロージャへの変換を広げる）は、1 割前後しか減らない見込みになって止め、重い関数を軽くすることと、GC と文字列の手当てに移った（同じ文書の 5）。ここでは、そこで残った手間を、ConSh の値と文脈の表し方まで変えて減らす。参照版（consh/reference）は変えない。ConSh の言語の見え方（consh/test の出力）も変えない。

## 1. 目的と、測ったこと

### 1.1 ステップの内訳（2026-11-17、Rust 版の VM の `CONMA_PROFILE`、関数を役割で分けた、1 回の繰り返しあたり）

consh/bench のスクリプトを小さくしたもの（`02` は 2 万回、`13` と `14` は 1 万回、`18` は 5000 要素）。ステップは機械によらない。変換した VM の時間も、おおむねステップに比例する。

### 1.2 中身

* **`$( )` の値**：外部コマンドの出力の行を、1 行ずつ LazyList の要素にする（`Subst_lines_next` が 1 行 37 ステップ）。要素を取り出すたびに、ほかの VProc と取り合わないための手続き（`__LazyList_force_claim__`、`__LazyList_force__`、`__LazyList_uncons__`）で約 35 ステップかかる。`02` では、1 要素に約 120 ステップ。
* **変数**：`$x` を読むと、局所変数の Dict を引き（`Sh_lookup`）、SJS と JS の値でないかを確かめ（`Value_force` の 12）、外部コマンドの語にする（`Var_fields` の 24。種類の確かめ、空か、glob の記号を含むか）。1 回 50 ステップ前後。
* **for 文**：繰り返しごとに、continue の継続を取り（`__Cont_get__`）、ループの記録（名前、break と continue の継続）を作り、文脈の `"loops"` に置く（`For_item` 22、`Loop_make` 8）。本体に break も continue もなくても作る。
* **文の終わりの待ち**：文の終わりのたびに、この VProc で起動してまだ終わっていない `$( )` を見る。`for` の値の `$( )` は、ループの間ずっと終わっていないので、本体の文ごとに 30〜50 ステップかかる。
* **コマンドの語の展開**：先頭の語のほかは、実行のたびに語の節を読む（`Parts_count_from`、`Part_split`、`Node_split`、`List_first`）。`14` の `h $i $j` と `m=$a$b`（2 つの変数をつなぐ語）、`if defined i` がこれにあたる。段階 1 の P4 は、2026-11-16 の大きさでは数 % と見積もって作らなかったが、今の `14` では最も大きい。
* **出力の受け取り**：`f > (n)` は、組と記録の Dict を作り（`Capture_new`）、出力の先を作り（`Target_*`）、関数の出力を 1 つずつ記録に加え（`Capture_put`、`Capture_add`）、最後に変数に入れる（`Capture_assign*`）。1 回に約 500 ステップ。
* **関数の呼び出し**：関数を名前で探し（`Func_lookup`。関数は後から定義できるので、毎回）、文脈の Dict（約 30 個のキー）を写して 11 個を書き換え（`Func_call`）、引数を渡す。

### 1.3 見込み

* 役割ごとの割合が、その手当ての上限である。手当てで、その役割のステップの半分前後が減るとすると、`02` で 3〜4 割、`13` と `14` で 2〜3 割になる見込みである。
* 変換した VM では、時間の約 3 割が値の破棄と複製で、その多くは作った値を手放すもの（COMPILE-PLAN-ja.md の 5、2026-11-17）なので、作る値を減らすこの計画は、そこにも効く。

## 2. 方針

* **今の作り（文脈を受け取るクロージャ）のまま、表し方を変える（案 A）**。ConMa のモジュールを作る変換（案 B。`consh compile`）は、しない。実行時に作ったモジュールは、変換した VM では Rust のコードにならず、解釈して動くので、かえって遅くなる。変換した VM に入れるには、スクリプトごとに VM を作り直す（約 20〜40 分）ことになり、ベンチマークのほかでは使えない。
* **見える動きは変えない**。consh/test を、最適化版と参照版で同じ出力にする。外部コマンドの起動の順と時期、`$( )` の並行、fd を閉じる時期も、変えないことを前提にする（変えたいものがあれば、3 で決める）。
* **手当ては、役割ごとに独立した段階にする**。どの段階も、それだけで測れて、それだけでやめられる形にする。
* **変換のときに分かることは、変換のときに決める**。文のコードを作るときに、語の形、ループの本体に break や continue があるか、リダイレクトの形を調べ、実行のときの確かめを減らす。

## 3. 決めること

1. **案 A で進める**（案 B はしない）か。
2. **段階と順番**：4 の S1〜S7 のうち、どれをどの順に作るか。案は、小さくて確かなものから：S1（for 文）、S2（文の終わりの待ち）、S3（語の展開）、S4（出力の受け取り）、S5（変数）、S6（`$( )` の値）、S7（関数の文脈）。
3. **動きの変わる手当てを入れるか**：S2 で、`$( )` が終わったのを見つける時期を遅らせる（たとえば、文ごとでなく、`$( )` を新しく起動した文の終わりと、for 文の終わりだけで見る）と、終わった `$( )` の出力を読み終えて fd を閉じる時期が遅くなる。consh/test の出力は変わらない見込みだが、`$( )` をたくさん起動するスクリプトでは、開いた fd が増える。入れないなら、S2 は「状態を見る手間を減らす」だけにする。
4. **測り方**：各段階で、consh/bench の `02`、`06`、`13`、`14`、`18` のステップ（Rust 版の VM）を数え、段階の終わりに、変換した VM の時間を測る（docs/dev/CONTRIBUTING.md の Benchmarks）。

### 決めたこと（2026-11-17、ユーザーと）

1. 案 A で進める。
2. 順番は案のとおり：S1、S2、S3、S4、S5、S6、S7。
3. 動きの変わる手当ては入れない（決めるまで。S2 は状態を見る手間を減らすだけにする）。
4. 測り方は案のとおり。変換した VM の時間は、いくつかの段階をまとめて測る（作り直しに 20〜40 分かかるので）。
