# Running ConJS on the host's JavaScript

The plan of running the functions of a ConJS program on the JavaScript engine of the host (Node.js or a browser) when the program runs on the wasm VM, calling back into the VM for what the host cannot do. Written on 2026-11-24 at the user's request, after the ConJS benchmarks (conjs/bench/README-ja.md, shima3/conma#71). The first version, the same day, ran only the functions that never wait and undid a call that met anything else; the user then asked that the host call ConJS back instead, and this version does that (3.1), keeping the undoing only as the last resort.

**State**: a plan. Stage H0 (measuring JavaScript written by hand) is done (section 11), stage H1 (the nested run of the VM) is built (section 12), and so is stage H2, in two halves: H2a (the copying of values and the primitives; section 13) and H2b (generators, and keeping the copies the same at a call back and a yield; section 14). Stage H3 is built in two parts: H3a (the translator writes functions of values; section 15) and H3b (arrays, objects, closures and `console.log`; section 16). Of stage H4, H4a (the methods of classes; section 17), H4b (`new`, `instanceof`, `throw` and `try`; section 18) and H4c (slow paths in the VM and calling ConMa back, section 19; waiting host functions, section 20) are built. Host functions have no fuel (the user's decision; section 6). Of H5, H5b (reading and writing members in place; section 22) and H5c (the elements of arrays in place; section 23) are built, the numeric functions try the host first (section 24), and a function that costs more on the host than in ConMa stops using it (H5d; section 25). Of H6, H6a (loops at the top level; section 26), H6b (programs with `import` and `export`; section 27), H6c (top-level loops that wait or call ConMa back; section 28) and H6d (other top-level statements with a loop inside; section 29) are built, and so is H5e (`new Error`, `typeof` and `JSON` on the host; section 30). H7 (the browser) is designed (section 32) and built (section 33). Async functions at the top level of a ConJS file, run on the host, are designed (section 34) and built (section 35). H8 (generator functions on the host) is designed and built (section 36). The rest is not. Section 10 lists what the user is to decide.

## 1. Why

* On the wasm VM, ConJS runs 53 (exceptions) to 18,500 (nbody_class) times slower than Node.js running the same program (conjs/bench/README-ja.md). Every step of ConJS goes through the ConMa VM, which is itself WebAssembly run by the engine of the host.
* The functions of SJS and ConJS that use only numbers and arrays of numbers already run as WebAssembly on the wasm VM (docs/consh/dev/SJS-WASM-PLAN-ja.md and SJS-WASM-ARRAY-PLAN-ja.md): `nbody` of sjs/bench, written with arrays, runs 200 times faster with them (0.55 s against 109 s, M4). They cover little of what ConJS programs do: strings, objects, classes, `map` and `sort`, JSON and exceptions are all outside them, and none of the seven new benchmarks gets a numeric function.
* The host has a JavaScript engine with a JIT that runs all of these. ConJS differs from JavaScript only in a few things (section 5), and most of a ConJS program is plain JavaScript.
* SJS ran on the host's JavaScript once (stage A of docs/consh/dev/SAFEJS-PLAN-ja.md) and left it for two reasons: no sandbox for the scripts of ConSh, and different behaviour from the native VMs. Neither stops this plan: a ConJS program already reads and writes files and the network, and section 7 keeps the results the same as on the native VMs.

## 2. What runs on the host

* **Host functions.** The translator writes a JavaScript version of a function (a declaration, a function expression, an arrow function or a method of a class) when its body uses only what section 4 can write. What it calls need not run on the host: what the host has no version of is called back in the VM (3.1).
* **Two kinds.**
    * A **plain host function** is a JavaScript function. The translator makes one of a function that, as far as it can see, does not wait: every call in it is to another host function, to a built-in that does not wait (`push`, `slice`, `map`, `JSON.stringify`, `Math.sqrt`, `console.log`, ...), or to a method or a function value whose callee it does not know.
    * A **waiting host function** is a JavaScript generator (`function*`). The translator makes one of a function that calls something that waits (`join`, `sleep`, `host.wait`, `fetch`, `readLine`, `nextEvent`, `accept`, the functions of the library that call them), or calls a waiting host function. At each of these calls it yields to the VM (3.1).
* **What the host does not write**: what section 4 cannot write (a generator of ConJS with `yield`, `import` at the top level, constructs to be added later). A function with one stays in ConMa, and the host calls it back like any other function of the VM.
* **Where it starts.** When ConMa code calls a host function, the call runs on the host, with what it calls; calls between host functions stay on the host. Code at the top level of a file runs in ConMa until a later stage (H6) moves it to the host.
* **Only on the wasm VM.** The Rust, transpiled and Python VMs have no JavaScript: there every function is its ConMa version, as now. The program prints the same on every VM (section 7).

## 3. Calling between the VM and the host

### 3.1. What the host does when it cannot go on

A call of a host function begins as in the first version: its arguments (and `this` for a method) are copied from the VM to the host (3.2), and the JavaScript runs on the copies. When it comes to something the host has no version of, it does one of three things.

1. **Call back (plain and waiting host functions).** For a function of the VM that the host has no version of (a method of a class with no host version, a function passed in from ConMa code, a function of the library written in ConMa), or for a value of a kind the host does not have (a task, a file object: reading its member or calling its method), the host calls the VM at once and waits for the result, as a JavaScript function waits for a function it calls:
    1. the host writes back into the VM the copies it changed (3.2) and writes out what `console.log` put in its buffer;
    2. the VM runs the call to its end, as a nested run (8), and returns the value or the exception;
    3. the host copies again from the VM what the call may have changed (3.2), and goes on.
   The call back must not wait: the host's JavaScript cannot be suspended in the middle of a plain function. If the code of the VM comes to a call that waits during a call back, the VM stops it and reports an escape to the host (3, below).
2. **Yield (waiting host functions).** At a call that waits (`join(t)`, `sleep(ms)`, `f.readLine()`, and a call back that may wait), the generator yields a request to the VM:
    1. as before a call back, the host writes back the changed copies and the buffer of `console.log`;
    2. the VProc of the task does the request as ConMa does it now: it waits, and the other tasks run meanwhile;
    3. when the request is done, the VM resumes the generator with the result; the host copies again what may have changed, and goes on.
   So a waiting host function runs as its ConMa version does: other tasks run only where it waits, and see everything it did before that point (the rule of ConJS that a call that waits is the only point where other tasks run).
3. **Escape (the last resort).** A plain host function that comes to a call that waits (a call back whose code waits, a method that turns out to wait) cannot yield. It throws an escape, the host drops its copies and its buffer, and the ConMa version of the function runs from the start with the original arguments, as in the first version of this plan. This undoing is correct only when nothing of the call has been seen outside, so a plain host function that has already called back or written out its buffer cannot escape: the VM stops the program with an error that says the translator chose wrongly (`conjs: internal: a plain host function came to a call that waits after a call back`), to be fixed in the translator. The translator avoids both by making a function a waiting host function whenever it cannot tell (10.1).

### 3.2. Copying values

* **To the host**: numbers, strings, booleans, `undefined` and `null` as they are; arrays as arrays; objects as plain objects with their own properties in the order of the VM; an instance of a class as an object made by the host version of that class (3.3), with its own properties; an error object as an instance of the host version of its error class.
* **What the host keeps as a handle**: functions of the VM (closures), tasks, file objects, servers and requests, generators, the objects of `host`. The host gets a small object that names the value in the VM; calling it, or reading a member of it, calls the VM back (3.1). A handle is passed back to the VM as the value it names.
* **Aliases are kept**: the same array or object (the same `"id"` of the VM) reached twice is copied once, and a cycle (`o.self = o`) is copied as a cycle. The host keeps a table from host objects to the ids of the VM.
* **Back to the VM**: every copied array and object is compared with what was copied in, and the changed ones are written back (their own properties, their length). Objects the host made are made in the VM. The return value is copied the same way.
* **Keeping the two sides the same at a call back or a yield.** The host writes back its changes before the VM runs, and after it copies again the objects it holds. To avoid copying everything again, the VM counts the writes to each array and object (a number kept with it), and the host copies again only those whose count changed.
* **Cost**: the first copy of a call is all that its arguments reach; each call back and yield adds the changed objects. A host function given a large structure for little work, or one that calls back in every step of a loop (`a.map(f)` with `f` a function of the VM), can be slower than its ConMa version. The runtime counts, for each host function, the words copied, the call backs and the time spent, and stops using the host for a function that copies more than it runs (a rule to set when measuring, H5). Copying only what is read (copy on first touch, with proxies) is a later step if the measurements ask for it.

### 3.3. Classes and methods

* Each class with a host function becomes a JavaScript class on the host with the same name, fields and methods. A method with no host version becomes a stub that calls the VM back (3.1).
* `b.move(dt)` on the host calls the method of the object's class on the host, or the stub. If the object has no such method, the host throws the TypeError of ConJS, as the ConMa version does.
* A method read without being called (`const m = o.m`) is bound to `o` as in ConJS (section 5), with a small function of the runtime.

## 4. What the translator writes

* The translator (sjs/include/sjs_gen.se and the files of ConJS) writes, beside the ConMa it writes now, the JavaScript of the host functions: one text for the program, with every host function and class, and a table of their names and kinds (2). The text goes into the module as a String, as the WAT of the numeric functions does, so `--emit` shows it.
* The JavaScript uses only its own names and those of one object of the runtime passed in (`rt`): the translator writes no free name, so the code cannot reach the globals of the page or of Node.js. It is compiled once with `new Function("rt", text)` (Node.js), or loaded from a file made by the build (a browser page; 8).
* What section 5 needs is written as calls of `rt` (`rt.len(s)`, `rt.add(a, b)`), and a call of a method ConJS does not have becomes `rt.missing(...)`, which throws the TypeError of ConJS. Where the translator knows the types (a number in a loop counter, a field written only with numbers), it writes plain JavaScript (`i + 1`).
* Reading and writing a member and calling a method keep the name in the code, with the check of ConJS written in place: `(o == null ? rt.fail(o, "x") : o.x)` and `(typeof o.m === "function" ? o.m(a) : rt.notFn("m"))`, never a call such as `rt.get(o, "x")` with the name as an argument. H0 found the second 25 times slower than plain JavaScript and the first 1.14 times (section 11): with the name in the code, the engine keeps the shape of the object in its caches.
* In a waiting host function, a call that waits becomes `yield rt.wait(...)`, and a call of another waiting host function `yield* g(...)`.
* The ConMa version of each host function stays in the module, wrapped by a function of the runtime (`Sjs_host_fn`, like `Sjs_wasm_fn`) that decides at each call whether to go to the host.

## 5. Keeping the meaning of ConJS

What ConJS does differently from JavaScript (conjs/README.md, Language, and sjs/README-ja.md) is written in the JavaScript of the host, so that a host function gives what its ConMa version gives:

* **Strings count characters** (code points), not units of UTF-16: `length`, indexes, `at`, `slice`, `indexOf`, `replace` and the others go through `rt`, which uses the methods of the host directly when the string has no character outside the Basic Multilingual Plane (checked once per string and kept).
* **`+` joins numbers only**: `rt.add` throws the TypeError of ConJS for anything else, unless the translator knows both sides are numbers.
* **Methods bound when read**, no prototype, `instanceof` only with classes and the errors: written with `rt`.
* **Errors**: the TypeErrors the runtime of ConJS throws (`null.x` and the like) are thrown by `rt` with the same messages; the position of an exception that leaves a host function is that of the ConMa version (the host keeps a table from its lines to the positions of the source). An exception crosses between the host and the VM, both ways, as an error object copied as in 3.2.
* **`console.log`**: formatted on the host by a port of the formatter of the runtime (sjs_rt.se), and compared with it in the tests. It writes into a buffer, written out at the end of the call and before each call back and yield (3.1), so that the output keeps its order with what the VM prints.
* **Numbers**: both are IEEE doubles; `-0` follows JavaScript already (section 11 of SJS-WASM-PLAN-ja.md). Conversions to strings (`String(1e21)`, `toFixed`) use the formatter of the runtime where the host's could differ.
* **Sorting**: the host's `sort` and that of the runtime need not call the comparing function in the same order (to be checked in H2), so the host uses a port of the runtime's algorithm.
* **Missing built-ins**: a method or function that ConJS does not have (`splice`, `Array.from`) is not called on the host, where it exists, but through `rt.missing`, so the program fails in the same way.
* **Tasks**: `spawn(f)` from a host function is a call back: the VM makes the task, and the host gets a handle (3.2). The task runs in the VM when the caller next waits, as now; if `f` has a host version, the task calls it on the host like any other ConMa code.

## 6. Fuel and Ctrl-C: none (the user's decision, 2026-11-24)

**Decision**: host functions have no fuel. Code on the host runs until it returns, waits (a waiting host function yields at `sleep`, `join` and `nextEvent`, section 20) or calls back; meanwhile the VM, its other VProcs and the events of the host wait. A program that needs other things to run in the middle of a long computation says so in its source, with a call that waits, such as `sleep(0)`, which is a point where the host function gives the VM back its turn (in a waiting host function, a yield; nothing is done again).

**Why** (the user, 2026-11-24): ConJS promises that asynchronous calls look synchronous, and that tasks switch only where a call waits (conjs/README.md, "No interruptions": a long loop that does not wait stops the other tasks, as in JavaScript). It does not promise that everything else keeps running all the time. Keeping the VM running in the middle of a host function kept only a property of how the ConMa version happens to run (the VM switches between any two steps), not of ConJS: no other task runs then anyway, as the tasks share one VProc, and a program that does not trap SIGINT is stopped by Node.js at once, with or without fuel. A loop that never ends on the host behaves as it does in JavaScript.

**What was tried** (stage H5a, built and measured on 2026-11-24, then removed before it was pushed): a check of fuel at the top of every loop body and at the start of every function; a plain host function out of fuel before a call back ended the time slice of the VM (a mark `"e"` in the answer of the host, read by vm/src/prim/jsfn.rs as `end_slice`, as `__Wasm_call__` does) and was called again from the start with 8 times the fuel, from 2^20 to 2^30, then in ConMa; after a call back it went on without fuel; a waiting host function yielded a request `tick` and went on. It worked on every case of conjs/test/step20 with a first fuel of 1 (21 calls started again; the same output), but:

* the checks cost nothing that could be measured on nbody_class (2.20 s against 2.26 s for 1,000,000 steps in one call of `advance`, 5.67 s against 5.68 s for 3,000,000, with a first fuel large enough for no retry; corrected the same day: the first measure, about 8%, put the translator of each version in place between the runs, so that every run first made the module of the translator again, about 5 s; section 22);
* starting again throws away the earlier tries of a call that runs long, at most 8/7 of its last fuel: `advance` with 3,000,000 steps in one call took 10.2 s against 5.6 s with no retry (1.8 times);
* making long loops generators instead (10.1), so that they yield rather than start again, would have made their callers generators too and kept them out of function expressions.

All this paid for the property above, which ConJS does not promise, so the user chose to remove it.

## 7. The same results on every VM

* A host function runs only on the wasm VM. With `CONMA_NO_HOSTJS=1`, the wasm VM runs the ConMa version (as `CONMA_NO_WASM=1` does for the numeric functions), so that the two can be compared.
* The tests: conjs/test and sjs/test on the wasm VM with and without it, against the Rust VM; a new step of conjs/test with the cases of sections 3 and 5 (aliases and cycles; a call back that changes an object the host holds; `console.log` on both sides of a call back, in order; a yield where another task changes a shared object; an escape; a method that is not a host function; a task in an argument; strings with emoji; exceptions crossing both ways, with their positions; fuel that runs out in both kinds); conjs/test/compare.sh against Node.js; the benchmarks of conjs/bench and sjs/bench.

## 8. The host, the VM and the browser

* **New primitives of the platform feature `"js"`** (docs/PRIMITIVES.md): `__JS_fn_compile__ onError text ,(module)` and `__JS_fn_call__ onError module name args fuel ,(status value)`, made like `__Wasm_compile__` and `__Wasm_call__`. The status tells the VM whether the call returned, threw, escaped, or yielded a request (with the generator to resume, by a handle). On the native VMs they call `onError` (`JavaScript is not available`), and the ConMa version runs. `__JS_call__` is not used: it runs a call as a Stream that the VProc waits for, which is too slow for this.
* **Calling the VM back (a nested run).** A call back happens while the VM is inside the import that called the host. The wasm VM exports a function that runs a closure of the VM with arguments to its end and returns its value: it runs a new VProc for the call, alone, inside the current step, with the scheduler of the VM set aside, and stops it with an escape if it waits. The Rust VM keeps its state in `RefCell`s that the step that called the host still borrows, so it has to be checked, and changed where needed, that a nested run borrows nothing the outer step holds (H1 does this first).
* **Resuming a generator.** The VM keeps the generator of a waiting host function by a handle, as a value of the VProc that waits, and resumes it with `__JS_fn_resume__ onError handle value ,(status value)`, with the same statuses as `__JS_fn_call__`.
* **New imports of vm/wasm/src/sys.rs**: compile a text into a module of host functions, call one, resume a generator, read the result, free a module or a generator. The arguments, the results and the copies of 3.2 cross as one buffer in a compact form of the graph of values, written and read by Rust in the VM and by vm/wasm/conma.js on the host.
* **Content-Security-Policy**: the pages of ConSh (consh/js) forbid `eval` and `Function` when `js` is not used (section 5 of SAFEJS-PLAN-ja.md). For the pages of ConJS, conjs/web/build.sh writes the JavaScript of the host functions into a file of its own, which the page loads with a `<script>`, and which registers its modules by the hash of their text; `__JS_fn_compile__` finds the module by that hash instead of compiling the text. A page that allows `eval` can skip this. Node.js (vm-node.js) uses `new Function`.

## 9. Stages

* **H0 — measure first.** Write by hand the JavaScript the translator would write for `advance` of conjs/bench/nbody_class.con.js and for the loop of hof (moved into a function), with the copies of 3.2 done by a small script, and measure them against Node.js and the wasm VM; measure also a call back in each step of a loop. This tells how much copying, call backs and the calls of `rt` cost before anything is built, and whether the plan is worth it.
* **H1 — the nested run of the VM.** The exported function of 8 that runs a closure to its end inside a step, with the checks of the `RefCell`s, and its stop with an escape when it waits. Tests call it from JavaScript written by hand.
* **H2 — the host and the VM**, still without the translator, in two halves (2026-11-24):
    * **H2a**: the primitives and imports of 8 for compiling and calling, the copying of 3.2 with aliases, cycles and handles, the call back of a handle, and escapes (section 13).
    * **H2b**: the generators and their requests (3.1, 2), the copying at a call back and a yield with the counts of writes (3.2), and a call back whose arguments keep their aliases with the nodes of the call.
* **H3 — the translator, numbers and strings.** The two kinds of section 2 and the JavaScript for functions of numbers, strings, booleans, arrays and plain objects, with the calls of `rt` for section 5; `console.log` into the buffer. In parts (2026-11-24):
    * **H3a**: functions of values only (numbers, strings, Booleans, `undefined`), which change nothing and can be run again in ConMa (section 15).
    * **H3b**: arrays and plain objects, copied as in 3.2 into the forms of SJS (`items`, `length`, `props`, `keys`), and `console.log` into the buffer.
* **H4 — classes, exceptions and waiting.** Classes and methods (3.3), `throw`, `try`, `catch`, `finally`, `instanceof`, the positions of exceptions; waiting host functions with `yield rt.wait(...)`, and `spawn`. In parts (2026-11-24):
    * **H4a**: the methods of classes, on instances that come from the VM, with `Math` (section 17).
    * **H4b**: `new` on the host, exceptions and `instanceof` (section 18).
    * **H4c**: calling ConMa back (callbacks passed in from ConMa code), and waiting host functions. The user chose on 2026-11-24 that, after a call back, the host asks the VM to do what it cannot (slow paths) rather than stop the program, in three parts: **B1** the slow paths of the operations on values, **B2** calling ConMa back (with iterating over values of the VM), both in section 19, and **B3** the waiting host functions (section 20).
* **H5 — measure and tune.** (Fuel was dropped on 2026-11-24; section 6. H5b, the members written in place, is built, section 22; H5c, the elements of arrays, section 23; the numeric functions, section 24; H5d, the rule that stops using the host, section 25; H5e, `new Error`, `typeof` and `JSON`, section 30.) The benchmarks of conjs/bench and sjs/bench; the rules that stop using the host for a function (3.2); the choice between WebAssembly and the host for the numeric functions (both work for them; keep the faster).
* **H6 — the top level.** Running the top level of a file on the host, as a waiting host function. In parts (2026-11-24): **H6a**, the loops at the top level that do not go to the VM, as statement functions (section 26); **H6b**, host functions and statements in programs with `import` and `export` (section 27); **H6c**, top-level loops that wait or call ConMa back, with the top-level variables kept the same on both sides at each crossing (section 28); **H6d**, a top-level `if`, block or `try` with a loop inside (section 29).
* **H7 — the browser.** conjs/web/build.sh and the pages (8). Designed on 2026-11-25 (section 32): the pages already run host functions, so H7 decides 10.3, makes the host functions visible and measurable in a page, and tests the pages that forbid `eval`. Built on 2026-11-25 (section 33).

* **H8 — generators on the host** (planned on 2026-11-27 at the user's request, for speed; designed and built on 2026-11-28 in one step for both halves below, section 36). A generator of ConJS (`function*` with `yield`) stays in ConMa (section 2, "What the host does not write"), and is slow there. Measured on 2026-11-27 (M2, Apple M2, the wasm VM against Node.js, run in turn three times each, the time taken inside the program): a generator that yields `0` to `n - 1`, summed by `for...of`, costs 25 to 29 µs for each `yield` in ConJS (2.5 to 2.9 s for 100,000) against about 14 ns in Node.js (137 to 146 ms for 10,000,000), about 2,000 times; the same sum as a plain `for` loop, which runs on the host as a host function, costs 40 to 50 ns a step (4 to 5 ms for 100,000, most of it the copying of the call) against about 7 ns (68 to 72 ms for 10,000,000). Two halves:
    * **A generator whose body does not wait**: its `yield` can be the `yield` of a JavaScript generator, and the generator object can stay on the host, held by the VM by reference (stage S0 of docs/dev/CONJS-SHELL-PLAN.md, sections 14 and 15, on `alpha`), which ConMa code already steps through with `for...of` and which a `<$` of a command line can give to the host as it is (section 17 of that plan). This half is the smaller one.
    * **A generator whose body waits**: a waiting host function is already a JavaScript generator that yields requests to the VM (section 20), so the two meanings of `yield`, a value for the reader and a request for the VM, have to be told apart, by marking what it yields, both where the host steps through it and where ConMa does. The built-in `readLines()` of files and of the standard input (conjs/include/conjs_file.se) are generators of ConMa that wait, and stay in the VM until this half is built.

## 10. What the user is to decide

1. **When a function is a waiting host function** (H0: a generator for `advance` alone costs 4%, generators for every function 8.3 times; section 11). A generator is slower than a plain function in the engines, but only it can yield. (Settled on 2026-11-24 with section 6: a function is a waiting host function when it calls something that waits; there is no fuel, so no other reason to make one.) The plan made a function a waiting host function when it calls something that waits, or when it calls back something the translator does not know and has a loop that can be long; otherwise a plain one. The other choice is to make every host function that calls back a generator, which never needs the error of 3.1, 3, at some cost in speed.
2. **Whether to go on after H0** (section 11): the host's JavaScript is 1.1 to 1.8 times Node.js where the VM is 1,000 to 18,500 times, but the crossings of today are too slow (a call back costs about 18 µs, and copying a value about 4 µs), so H1 and H2 must make them faster, with the copying done by Rust in the VM.
3. **The browser (8)**: a file of JavaScript made by the build, or allowing `eval` in the pages of ConJS. Decided by the user on 2026-11-25 (section 32): allow it, and leave the file for later.
4. **The numeric functions**: keep WebAssembly for them, or move them to the host when the host is as fast (H5). Decided on 2026-11-24: the host first (section 24).
5. **SJS**: whether SJS in ConSh (`(( ))`) uses host functions too. Its scripts are not trusted in a page in the way a ConJS program is, so the plan leaves it out unless the user says otherwise.

## 19. Results of H4c, B1 and B2 (2026-11-24)

**The problem.** Until H4b, a host function that came to something it could not do threw `rt.Escape`, and the ConMa version ran from the start: right, because nothing of the host function had been seen. Calling ConMa back breaks that: the function called back may print, change objects, or start tasks, and running the ConMa version from the start would do it twice. The user chose (2026-11-24) that, once a host function has called back, it does not stop but asks the VM to do, one at a time, the operations it cannot do itself.

* **Asking the VM** (`$vm` in the helpers of sjs/include/sjs_host.se; `Conjs_hostfn_vm` in conjs/include/conjs_host.se): every call of a host function now gets, after the counter of ids, a closure of the VM, which the host calls back (`rt.callVm`, H2b) with the lines of `console.log` kept so far, a position, an operation and its arguments. The closure prints the lines (so that they keep their order with what the VM prints), runs the operation with the runtime of SJS and ConJS (`Sjs_add` and the others, `Sjs_to_string`, `Sjs_console_string`, `Sjs_get_member`, `Sjs_get_index`, `Sjs_set_member`, `Sjs_set_index`, `Sjs_call_member`, `Sjs_call`, `Conjs_instanceof`, and `Sjs_iter_open`, `more`, `take`, `close`) under a handler of exceptions, and returns `("ok" value)` or `("threw" exception)`. Before asking, the host writes what it changed into its copies of the values of the VM (`$sync`), and after, it reads back what the VM changed (`$refresh`), so that both sides agree at every crossing.
* **B1, slow paths**: the checks of section 5 that failed with an escape now call `$slow`: before any call back, it still escapes (the ConMa version gives the same result, positions included); after one, it asks the VM: arithmetic and comparisons of other values than numbers (comparing strings, the TypeError of `+`), numbers in templates, `console.log` of other values, members and elements of other values (an opaque value, a string of more than ASCII), assignments to them, methods of strings of more than ASCII and of arrays when the host cannot do them, `instanceof` of an opaque value. An exception that the VM throws gets the position of the operation on the host: the translator now gives every check the position of its node (`$P`, "file:line:col", the form `Kit_err_pos` gives), which is the position the ConMa version reports for the same node.
* **B2, calling back**: a function of the VM that a host function calls (`f(x)` with `f` passed in from ConMa, a method of an instance whose class the host does not know, a callback given to `map` and the other methods of arrays) is called in the VM (`call`, `callm`). So is iterating over a value of the VM with `for...of` (a generator, the lines of a file), with the same operations as the ConMa version (`Sjs_iter_open` and the others; leaving the loop early closes it). After any of these, the host function cannot fall back (`$committed`).
* **Exceptions after a call back**: one that the VM throws (in a function called back, or in an operation) becomes `$Thrown` on the host, so `catch` takes it; one that leaves the host function is thrown again by the VM after the host's changes are written back and its lines printed, with the position of its `throw` on the host, or its own position when it came from the VM.
* **What still stops a program**: after a call back, a check that has no slow path (`Math` of other values than numbers, a function of the host returned to the VM, holes in an array, a call back that waits, an error of the engine such as a stack overflow) ends the program with `conjs: the host function NAME could not go on after calling back: ...`, status 2. Before a call back, such a check falls back as before.
* **State per call**: a function called back may call host functions again; the state of the helpers is kept per call (`$enter` saves and restores it). A continuation that returns into the empty chain of a nested run loses its values in the VM (vm/src/step.rs), so the closure of the VM returns through one ordinary frame.
* **Reporting**: with `CONJS_HOST_REPORT=1`, every fall back prints its reason (`conjs: escape: NAME: ...`); this found a missing helper and a call with too few arguments while building this part.
* **The tests**: conjs/test/step20/case7 (a callback of the VM from a host function, to `map`, from a host function that logs before and after; strings of more than ASCII, a template of a number that is not an integer and `at` after a call back; a host change seen by the callback and its result; the TypeError of `+` after a call back, uncaught with its position and caught by the host; a callback that throws, caught and uncaught; an instance of a class the host does not know). The log is the same on the Rust, wasm and Python VMs; 6 functions return from the host. conjs/test/step16/case3, whose `find` iterates over `f.readLines()`, needed the iteration of B2: it now runs on the host. `keep` of case4 (a callback passed in) now runs on the host too.
* **What a call back costs** (the M4, the wasm VM, user + sys, the least of 3): a host function that calls a function of the VM 10,000 times in a loop takes 31 µs a call back, against 15 µs for the same calls in ConMa: calling back in every step of a loop is slower than staying in ConMa, as 3.2 expected. The rule of H5 that stops using the host for such functions is still to be made.
* **Not done**: B3, the waiting host functions (generators that yield their waits to the VProc; section 20), and the fuel of section 6.

## 20. Results of H4c, B3: waiting host functions (2026-11-24)

* **Which functions** (sjs/include/sjs_host.se): a top-level function that calls `sleep`, `join` or `nextEvent` (the built-ins, when the program does not declare or assign the name), or a waiting host function, is a **waiting host function**, written as a JavaScript generator (`function*`). Which functions wait depends on which functions they call, so `Host_prepare` writes all the functions again until the set of waiting ones (`"#waits"`) stops growing (`Hx_wait_loop`); a function known to wait is written as a generator. Methods, constructors and fields that would wait are not host functions, and nor is a function whose function expression waits (`a.map((x) => { sleep(0); ... })`): function expressions are not generators, so they cannot yield.
* **What waits writes**: a waiting built-in becomes `$Yr(yield $Yq(p, 'callg', "sleep", [args]))`, a waiting host function `(yield* f_g(...))`. In a waiting host function, calling a function or a method of the VM (`f(x)` with `f` passed in, `o.m()` of a value of the VM, such as `f.readLine()`) also goes to the VProc by a yield (`$callG`, `$mcallG`), so it may wait too; in a plain host function it is still a nested call back, which cannot wait (section 19).
* **A request** (`$Yq`): the host writes its changes into its copies of the values of the VM (`$sync`), and yields `[position, op, arguments, lines of console.log]`. `Conjs_hostfn` (conjs/include/conjs_host.se, `Conjs_hostfn_wait`) prints the lines, runs the op in its VProc with `Conjs_hostfn_vm_run`, the same as a call back (section 19) but where it may wait, so the other tasks run meanwhile and see what the function did so far; then it resumes the generator (`__JS_fn_resume__`) with `("ok" value)` or `("threw" exception)`. The host reads back what the VM changed (`$refresh`) and goes on, or throws the exception where `catch` can take it (`$Yr`). The op `callg` calls a global function of the program (`Sjs_global`): an exception it makes itself (the TypeError of `sleep("x")`) gets the position of the call, and one it throws again (`join` of a task that ended with an exception) keeps the position where the task threw it, as in the ConMa version.
* **What the host cannot check, after waiting** (the review of shima3/conma#76 by M1): after the first request, as after a call back, a check that fails asks the VM to do the operation. At first some built-ins had no such way and stopped the program where ConMa runs it (`"é,b".split(",")`, `reduce` without a first value, `sort` without a comparing function, `replace` with `$`, after `sleep(0)`): their check threw `$Fatal`, which the fall back of the methods of strings and arrays (`$m`, section 19) did not take. Now it throws `$NoHost`, which `$m` takes and runs the method in the VM (unless a function of the host is passed, which the VM cannot call). `reduce` without a first value runs on the host when the array is not empty. `Math` with other arguments than numbers (`$M_sqrt` and the others, `$math`), `Object.keys` of other values than objects of the host, and `for...of` over other values than arrays and strings now ask the VM too (the ops `math`, `keys` and the iteration of B2). The same held after a call back (shima3/conma#75). What still stops the program says why: `... could not go on after waiting: ...` or `... after calling back: ...`.
* **The request is an array**: the first version yielded an object, which became a new node of the session at every yield; as each crossing compares every node of the session, 20,000 waits took 19 s (quadratic). As an array, which crosses as a list without a node, the cost of a wait no longer grows.
* **After the first request**, the function cannot run again in ConMa (the other tasks have seen its changes): as after a call back, what it cannot do it asks the VM, or the program stops (section 19). Before it, an escape falls back to the ConMa version from the start, as before.
* **State per call**: while a waiting host function waits, other tasks call host functions, and other waiting host functions wait. The state of the helpers is kept per call in an object (`$fresh`) and put into the variables of the helpers only while that call runs (`$go`); `$enter` of the plain host functions is the same with one step. `$runG` drives the generator of the function and yields its requests.
* **The test**: conjs/test/step20/case8: two tasks running `sleep` in a host function in turn, with their lines in order; a change made by another task while the host function waits, seen after it; a waiting host function that calls another; `join` with a value and with an exception caught on the host; a function of ConMa that waits, called from a waiting host function; a function whose function expression waits, which stays in ConMa; the uncaught TypeError of `sleep("x")` after waiting, with its position. The log is the same on the Rust, wasm and Python VMs; 7 functions return from the host.
* **What a wait costs** (the M4, the wasm VM, user + sys, the least of 3; the load average was about 3.4 from other sessions): a request costs 25 µs on the host against 11 µs for the same call in ConMa (`join` of a task that has ended, 20,000 times: 0.67 s against 0.39 s, 0.18 s of it start-up). A loop of 100 steps of work between two waits, 4,000 times, takes 0.32 s on the host against 1.13 s in ConMa. `sleep(0)` measures mostly the timers of Node.js (1.6 ms of real time each while the M4 was busy), the same on both sides.
* **Not done**: what still has no way to the VM after waiting or calling back (`$arr` of a pattern over other values than arrays, holes in an array, a function of the host given to the VM, the methods of arrays given a function of the host that fail their check); `spawn` in a host function (a function expression of the host cannot go to the VM), waiting in a `for...of` over a value of the VM (its steps are still nested call backs), and waiting methods of classes. (Fuel was dropped; section 6.)

## 22. Results of H5b: members read and written in place (2026-11-24)

* **Why**: the profile of nbody_class on the host (Node.js `--cpu-prof`) spent half its time in `$getn`, the helper that reads a member: a helper shared by every member gets the name of the member as a variable, so the engine reads it with a lookup by key, where code that names the member (`o.x`) is read through a cache made for its shape. H0's "checks written in place, names in the code" (section 11) was 1.21 s for 20,000,000 steps.
* **What the translator writes** (sjs/include/sjs_host.se, `Hx_read_named`, `Hx_write_named`, `Hx_call_named`): for a member named in the code (not `__proto__`),
    * reading `o.x`: `(($t = o) != null && $t[$K] === true && ($v = $t.x) !== undefined && typeof $v !== 'function') ? $v : $getn($t, "x", p)`;
    * writing `o.x = e`: `(($t = o) != null && $t[$K] === true) ? ($t.x = e) : $putn($t, "x", e, p)` (and the compound assignments, `++` and `--` the same way);
    * calling `o.m(...)` (outside a waiting host function): `$v.call($t, ...)` when `$t.m` is a function of the host other than `$nom`, else `$mcall($t, "m", p, ...)`.
    Everything else (a member that is missing, a method read as a value, a value of the VM, a string, an array) goes to the same helpers as before, so the meaning is unchanged. `$t` and `$v` are temporaries of the innermost function or function expression (`Hx_temp`, declared at its start), so a recursion cannot overwrite them, and each expression is evaluated once.
* **What it gives** (the M4, the wasm VM, user + sys, alternately, 3 times each): nbody_class with 3,000,000 steps in one call of `advance`, 0.85 s against 5.7 s before; 100,000 steps, 0.47 s against 0.63 s; so a step costs about 0.13 µs against 1.74 µs, 13 times less. With 20,000,000 steps (the size of Node.js): 3.2 s against 1.12 s in Node.js, the same energies: 2.9 times Node.js, where H4a measured 31 times (section 17). hof (6,000 rounds) is the same, 33 s, as its loop is at the top level, in ConMa (H6).
* **How the versions were measured**: the translator and the runtime of ConJS are modules that conjs makes again when one of their sources is newer than the module (bin/lang). Putting one version of a source in place, then the other, between runs makes every run make its module again (about 5 s), which hides what is measured. Each version was kept in a file with an old time, put in place with `cp -p`, and given its own `CONMA_CACHE_DIR`. The first measure of the fuel of section 6 (H5a) did not do this; it is corrected there.
* **The tests**: conjs/test (Rust, wasm with `CONJS_HOST_STRICT=1`, Python), the same functions return from the host in every case of step20, compare.sh and sjs/test (Rust, wasm).
* **Not done**: the rules that stop using the host for a function that costs more than it gains (3.2); the elements of arrays (`a[i]`, `$idx`) and `length`, still through helpers; WebAssembly or the host for the numeric functions.

## 23. Results of H5c: elements of arrays in place (2026-11-24)

    * reading `a[i]`: `(($t = a), ($u = i), Array.isArray($t) && typeof $u === 'number' && ($u >>> 0) === $u && $u < $t.length) ? $t[$u] : $idx($t, $u, p)`;

## 24. The numeric functions: the host first (measured and decided by the user, 2026-11-24; 10.4)

A numeric function of ConJS (the stages of SJS-WASM-PLAN-ja.md) has two versions on the wasm VM: WebAssembly, tried first, and the host's JavaScript (`"hostAlso"`, section 15), tried when WebAssembly does not take the call. `CONMA_NO_WASM=1` leaves WebAssembly out, so the host's version runs.

| (the M4, the wasm VM, user + sys, 3 times alternately) | WebAssembly | the host | Node.js |
|---|---:|---:|---:|
| `fib(38)`, a recursion | 0.48 s | 0.43 s | 0.24 s |
| `mandel(2400, 1800, 500)`, loops of floats | 2.65 s | 1.44 s | 1.17 s |
| `collatz(100000)`, a loop with `%` and `/` | 0.47 s | 0.21 s | 0.05 s |

(About 0.17 s of each time on the wasm VM is the start-up.) The host's version is faster in all three: the engine of the host optimizes the plain JavaScript as well as the WebAssembly the translator writes, and WebAssembly counts fuel and starts over with 8 times the fuel when it runs out (SJS-WASM-PLAN-ja.md 5.5), where the host has no fuel (section 6). A call that WebAssembly cannot finish within its last fuel (2^30) tries the host only after that: `collatz(1000000)` took 3.47 s with WebAssembly on, against 1.91 s with it off.

**Decision** (the user, 2026-11-24): a numeric function of ConJS that has a host's version tries it first, then WebAssembly (when the host's module could not be made, `CONMA_NO_HOSTJS`, or when the host falls back), then ConMa (sjs/include/sjs_gen.se: `Conjs_hostfn` wraps `Sjs_wasm_fn`, which wraps the ConMa version; before, the other way round). The numeric functions of SJS in ConSh (`(( ))`), which have no host's version (10.5), keep WebAssembly.

* **After the change**: `fib(38)` 0.44 s, `mandel` 1.48 s, `collatz(100000)` 0.21 s, the host's times; with `CONMA_NO_HOSTJS=1`, WebAssembly's (0.49 s, 2.75 s, 0.47 s). In conjs/test/step20, 12 numeric functions of case1, case3, case4 and case7 now return from the host, and their names are added to case*.host.txt (none removed). conjs/test on the wasm VM with `CONMA_NO_HOSTJS=1 SJS_WASM_STRICT=1` still gives every log (only the lists of host functions differ), so the WebAssembly versions still work; sjs/test checks them for SJS too.

## 25. Results of H5d: the rule that stops using the host (2026-11-24)

* **Where the host loses** (the M4, the wasm VM, user + sys; ConMa is the same program with `CONMA_NO_HOSTJS=1`):

| | the host | ConMa |
|---|---:|---:|
| A: `first(a)` returning `a[0]`, called 2,000 times with the same array of 2,000 objects | 15.3 s | 0.28 s |
| B: one call that calls a function of ConMa back in each of 20,000 steps | 0.61 s | 0.33 s |
| C: one call that calls back every 20 of 400,000 steps | 0.64 s | 2.78 s |
| D: 20 calls, each summing a field of the same 20,000 objects | 3.5 s | 2.7 s |

  Copying costs much more than H2a measured with small values (0.5 µs a value): about 4 to 9 µs for each object of SJS (an object of SJS is several nodes, and each call copies again everything its arguments reach). A call back costs about 25 µs more than the call in ConMa, and a step of ConMa about 7 µs.
* **What the host counts** (sjs/include/sjs_host.se): `$ops`, the work: the steps of every loop and the elements of the arrays given to their methods (`$m`); `$cp`, the arrays and objects copied in or out (`$fromArray`, `$fromObject`, `$fillArray`, `$fillObject`, which `$refresh` and `$sync` also use at each crossing); `$cr`, the crossings to the VM (`$vm`, `$Yq`). They are part of the state of each call, and the answer of a call carries them (`cost`). The steps of a loop are counted in a variable of the function or function expression (`$loops`, added to `$ops` in a `finally`): counting them in the shared `$ops` made the sieve of section 23 about 25% slower, as a fast loop then writes to memory at every step; counted locally, they cost about 5% on the sieve and on nbody_class and nothing measurable on fib and mandel. The starts of functions are not counted (that cost 10% on fib): a recursion without loops counts no work.
* **The rule** (conjs/include/conjs_host.se, `Conjs_hostfn_judge`): for each host function, the runtime adds up an estimate of the host's cost, 9 × `cp` + 25 × `cr` (µs), and of ConMa's, 7 × `ops`, over its calls. When the host's grows larger, the function runs in ConMa from then on (`CONJS_HOST_REPORT=1` prints `conjs: off: NAME`). A, B and D are turned off after their first call, C and the functions of sections 22 to 24 (nbody_class, the sieve, fib, mandel, collatz) are not. A trivial function that copies nothing (`add(a, b)` making a string) costs the same either way, about 28 µs a call, so the rule adds no cost per call.
* **What it gives**: A, 0.37 s against 15.3 s (ConMa 0.30 s); D, 2.94 s against 3.5 s (ConMa 2.88 s); C stays on the host. B is one call: the rule decides only after a call, so a single call that loses is not helped.
* **In the tests**: in conjs/test/step20, small functions that copy an object and do no loop (`point`, `move`, `same`, `nest`, `keep`, `cls`, ...) are turned off after their first call; their first call still runs on the host, so the lists of case*.host.txt are the same. Building it, the counter was first named `$o`, the helper that makes objects, and `counts` of case4 fell back to ConMa (its escape, `$o is not a function`, showed only as a missing name in the list of host functions).
* **Not done**: deciding before the first call (B); copying less (keeping the copies of a session between the calls of a function, or copying on first touch, 3.2), which would make A and D cheaper on the host instead of sending them back to ConMa.

## 26. Results of H6a: loops at the top level (2026-11-24)

* **Which statements** (sjs/include/sjs_host.se, `Hx_stmt_candidates`, `Hx_stmt_func`): the loops at the top level of a file (`for`, `for...of`, `while`, `do...while`), in a program without `import` and `export`, that the host can write by the rules of the host functions (sections 15 to 23), and that do not wait. Each is a candidate `$s1`, `$s2`, ... in the order of the file, compiled and checked with the host functions (the fixpoint: what it calls must be host functions).
* **The variables of the top level**: inside such a loop, a variable declared before it at the top level by `let`, `const` or `var` (with a name, not a pattern) is a parameter `g_name` of the statement function; one declared after it is not taken in (it is not in scope yet in the order of the file), nor a function of ConMa, which the host does not call. The variables the loop assigns are returned in an array at its end: `function s_1(g_n, g_acc) { ...; return [g_acc]; }`. (An assignment to a `const` is already an error of the translator.)
* **What ConMa writes** (sjs/include/sjs_gen.se, `Gen_host_stmt`): it reads the variables (`Gen_read`), calls `Conjs_hoststmt` (conjs/include/conjs_host.se) with their values and the ConMa version of the statement wrapped in a closure, and, when the host ended it, assigns the new values (`Gen_write`). When the host cannot (no module of the host, as on the Rust and Python VMs, or an escape), `Conjs_hoststmt` runs the closure.
* **No crossing** (`$runS`, `$noCross`; replaced by H6c, section 28): a statement function may not go to the VM at all (no call back, no slow path, no request): `$vm` escapes at once, and the loop runs in ConMa from the start. A function of ConMa called back could otherwise read a top-level variable that the host has not written back yet. Nothing is lost by starting again: the host has written nothing back, and the lines of `console.log` it kept are dropped. An exception thrown in the loop escapes the same way, so ConMa throws it with its own position. A statement runs once, so the rule of section 25 does not judge it.
* **The test**: conjs/test/step20/case9 (reading and writing top-level variables, an object and an array changed in place, `for...of`, `while`, `do...while`, a new array assigned to a top-level variable, a host function called from a top-level loop and `console.log` in order, a loop calling a function of ConMa that stays in ConMa, a loop that would call ConMa back through `map` and runs in ConMa with each line once, an exception thrown in a loop, uncaught with its position). The log is the same on the Rust, wasm and Python VMs; 4 statements return from the host. conjs/bench at a small size prints what Node.js prints for all eight programs.
* **What it gives** (the M4, the wasm VM, user + sys): hof with 6,000 rounds, 0.26 s against 33 s in ConMa (Node.js 0.06 s); strings with 180,000 rounds, 0.34 s (Node.js 0.10 s); dict with 600,000, 0.44 s (Node.js 0.08 s). json is not taken (`JSON` is not on the host), nor exceptions, tasks and startup, whose loops call ConMa or wait.
* **Not done**: the rest of the top level (the statements between the loops, `if` and blocks), loops that wait (as waiting host functions, which would have to write the top-level variables back at each request), `JSON` on the host. (Files with `import` or `export`: section 27.)

## 28. Results of H6c: top-level loops that wait or call ConMa back (2026-11-25)

* **The problem**: in a top-level loop on the host, the top-level variables are parameters `g_name` of the statement function, written back only at its end. While the loop waits, other tasks run and may read or write them; a function of ConMa called back may too. H6a avoided this by letting no statement function go to the VM (section 26).
* **Keeping both sides the same** (sjs/include/sjs_host.se, `$gio`, `$gout`, `$gin`): a statement function that uses top-level variables sets `$gio = { get: () => [g_written, ...], set: ($v) => { [g_used, ...] = $v; } }` at its start. At every crossing (a call back, a slow path or a request), `$vm` and `$Yq` send the values of the variables it writes with the crossing; ConMa (`Conjs_hostfn_vm_run`, `Conjs_hostfn_set_globals`) assigns them before the operation, and after it reads the values of all the variables the statement uses (`Conjs_hostfn_get_globals`) and returns them with the answer; the host puts them into its parameters (`$gin`) before it goes on. The getter and the setter are closures that sjs_gen.se writes for each statement (`Gen_host_stmt`, with `Gen_read` and `Gen_write`) and that `Conjs_hoststmt` keeps in the PDict while the statement runs (the statements of the top level run one at a time, in the main task). `$noCross` is gone: a statement function crosses like a host function, and after a crossing it cannot start again in ConMa (section 19).
* **Waiting loops**: a top-level loop that calls `sleep`, `join`, `nextEvent` or a waiting host function is written as a generator and run with `$runG`, like a waiting host function (section 20); the requests carry the top-level variables too.
* **A bug found on the way** (there since B2, shima3/conma#75): `$log` was `$out.push(line)` with the line made in the argument. JavaScript reads `$out` first; when a number logged after a call back was formatted by the VM, `$vm` handed the buffered lines over and started a new `$out`, and the line went into the old array, already sent, and was lost. `$log` now makes the line, then pushes it. No test logged a number after a call back; case9 and case11 do now.
* **The tests**: conjs/test/step20/case11: a top-level loop that sleeps while another task reads the variable it writes and changes another it reads; a top-level loop that joins tasks; a function of ConMa that reads a top-level variable the loop has just written, called back through `map`; one that writes a top-level variable the loop then reads. The four loops return from the host, and the log is the same on the Rust, wasm and Python VMs. In case9, the loop that calls ConMa back through `map` now stays on the host (its lines, numbers included, come out once each).
* **Not done**: the statements between the loops (`if`, blocks, expressions; section 29); `spawn` in a loop on the host.

## 29. Results of H6d: other top-level statements with a loop (2026-11-25)

* **Which statements** (sjs/include/sjs_host.se, `Hx_stmt_candidates`, `Hx_has_loop`): besides the loops, a top-level `if`, block or `try` with a loop somewhere inside (in a function expression too) is a statement function, by sections 26 and 28. ## 30. Results of H5e: new Error, typeof and JSON on the host (2026-11-25)

* **Built-in errors** (sjs/include/sjs_host.se): `new Error(...)`, `new TypeError(...)`, `new RangeError(...)`, `new SyntaxError(...)` and `new ReferenceError(...)`, when the program does not declare or assign the name, ask the VM to make the error (`$vm('new', ...)`; the op `new` of conjs/include/conjs_host.se looks the constructor up with `Sjs_global` and calls `Conjs_new`), so that its name, message and class record are those of ConMa. On the host the error is a value of the VM: `throw` and `catch` take it, `e.message` and `e.name` are read through the VM. Like a call back, making one means the call cannot start again in ConMa. `x instanceof TypeError` (and the others) is false for values of the host, which are never errors, and asks the VM for its values (op `instofg`).
* **`typeof`** (`$typeof`): on the host for its own values (`null` is `"object"`, a function of the host is `"function"`); a value of the VM asks the VM (op `typeof`, `Sjs_typeof`).
* **`JSON.stringify(x)`** (`$jsonS`): the engine's `JSON.stringify` when `x` holds only `null`, `undefined`, Booleans, strings, numbers that `$S` writes as ConMa does (integers below 10^21, not -0) or `NaN` and the infinities (both `null`), arrays, objects of the host without `toJSON`, and functions (left out), with no cycle (`$jsonOk`). Anything else asks the VM (op `json`, `Sjs_json`): other numbers, values of the VM, `toJSON` (ConJS does not call it, the engine would), and a second argument (ConJS ignores the replacer and the indent, the engine would not).
* **`JSON.parse(text)`** (`$jsonP`): the engine's `JSON.parse`, then its objects made objects of the host (`$jsonIn`). A key that looks like an integer (the engine puts such keys first, ConJS keeps the order of the text) or `__proto__`, a text the engine cannot read (so that the error is that of ConJS), a value that is not a string and a reviver ask the VM (op `jsonp`, `Sjs_json_parse`).
* **What it gives**: conjs/bench/json with 4,500 rounds, 0.33 s against 29.9 s in ConMa (Node.js 0.07 s); with 200,000 rounds (the size of Node.js), 4.45 s against 1.13 s in Node.js.
* **The test**: conjs/test/step20/case13 (built-in errors thrown, caught and tested with `instanceof`; `typeof` of each kind of value; `JSON.stringify` and `JSON.parse` on the host and in the VM: a number that is not whole, `toJSON`, invalid text, a key like an integer; an error made on the host and thrown out of it, uncaught). The log is the same on the Rust, wasm and Python VMs. In case6, `runtimeError`, and in case9, the top-level loop that throws `new Error`, now return from the host.
* **Not done**: classes that extend a built-in error (`class Bad extends Error`, as in conjs/bench/exceptions) and `new` of a class of ConMa from the host (top-level classes are not globals, so `Sjs_global` cannot find them); `typeof` of a value of the VM before any crossing (it escapes).

## 31. for...of over values of the VM that wait (2026-11-25)

* **The bug** (found by M1 in shima3/conma#83, with conjs/examples/wordcount.con.js reading its standard input): since H6c (section 28), a statement at the top level may go to the VM. A top-level `for...of` over a value of the VM, such as the lines of `fs.stdin.readLines()`, asked for each next value by a nested call back (`$vmIter`, section 19), and a nested call back cannot wait: when the next line had not come yet, the program stopped with `the host function $s1 could not go on after calling back: a call back could not finish: the call back waits`. Before H6c, such a statement could not go to the VM and ran in ConMa. Since stage P10 (shima3/conma#82) ConJS runs on the wasm VM only, so every ConJS program with such a loop stopped.
* **The fix** (sjs/include/sjs_host.se, `Hx_forof_gen`, `Hx_stmt_forof_waits`): in the body of a generator (a waiting host function or a statement of the top level, outside function expressions), a `for...of` is written as `{ $t = yield* $iterG(x, p); try { while (yield* $moreG($t)) { const v = yield* $takeG($t); ... } } finally { yield* $closeG($t); } }`. An array or a string of the host is stepped through on the host, without requests; a value of the VM goes through the same steps as the `for...of` of ConMa (`Sjs_iter_open`, `more`, `take`, `close`), each a request (section 20), which may wait. Leaving the loop early closes it; after the last value there is nothing to close. A top-level statement with such a `for...of` is marked as waiting (`Hx_wait`), so that it is written as a generator; it has no callers, so this costs nothing elsewhere. A `for...of` in a plain host function, or in a function expression, is as before (nested call backs), which cannot wait.
* **The test**: conjs/test/step20/case14, with case14.feed.py, which gives the standard input through a pipe a line at a time (bin/lang-test): a top-level loop over its lines; a top-level loop over a generator of ConMa left early (its `finally` runs); a waiting host function looping over a generator; a top-level loop over an array with a pattern. All four return from the host, and the log is that of the version before H6c. With the translator of alpha (11dfa22), the first loop stops the program.
* **In a plain host function** (M1's review of shima3/conma#84): the same stop happened in an ordinary host function given the lines of the standard input (`function count(lines) { for (const l of lines) ... }` with `count(fs.stdin.readLines())`), or a generator of ConMa that sleeps; it was so since B2, and since P10 it stopped every such program. `$iter` now steps through a value of the VM only after a crossing: before one, the function gives the call to its ConMa version (`$no`), which can wait. Such functions over generators of ConMa no longer run on the host (they did since B2); arrays and strings still do. conjs/test/step20/case15 (with case15.feed.py): `count` over the lines of a pipe and `sumOf` over a generator that sleeps fall back to ConMa and give the log of ConMa; `sumArray` stays on the host. With the translator of alpha, `count` stops the program.
* **Not done**: a plain host function that has already crossed to the VM and then steps through a value of the VM that waits still stops; making such functions waiting host functions would make their callers generators too, and keep them out of function expressions.

## 34. Design: async functions in a ConJS file run on the host (2026-11-26; designed by M1, reviewed by M2 in shima3/conma#90)

Section 33 (the results of H7) is on `alpha`, not yet on `main`; this section is numbered after it.

**The question** (the user, 2026-11-26): when the translator finds `async` in a `.con.js` file, could it take the function as code of the host instead of stopping with `conjs: not in ConJS: async`? Today the code that uses async/await (Node.js's `fs.promises`, a library that returns Promises) goes into a host file of its own, given with `CONMA_HOST` (docs/HOST-ja.md, 3.2; conjs/test/step21), and the program calls it with `host.wait`. ConJS is not SJS: it is not a sandbox (section 1: a ConJS program reads and writes files and the network), and it is to take more of JavaScript (conjs/README.md). So nothing in ConJS asks that code of the host stay out of its files. The user chose to design it (2026-11-26).

**What the program writes**

```js
// files.con.js
async function countLines(name) {                     // runs on the host, as JavaScript
  const fs = require("node:fs/promises");
  const text = await fs.readFile(name, "utf8");
  return text.split("\n").filter((line) => line !== "").length;
}

const t = spawn(() => countLines("a.txt"));            // a call that waits, as host.wait does
console.log(countLines("files.con.js"));
console.log(join(t));
```

**1. What the translator takes**

* An `async function` declaration at the top level of a file (exported or not). Not yet, at the top level of ConJS code: async arrow functions and function expressions, async methods, async generators, `await` outside such a function. They stop as now, with `not in ConJS: async`; `await` in ConJS code stops with `conjs: await is not needed: a call of an async function waits` (M2's review), as a programmer used to JavaScript will write it first.
* **Exported and imported** (M2's review): another `.con.js` file that imports the name gets a ConJS function that makes the call of 2 (a call that waits), as the name used as a value does in its own file. In the importing file it is a name of the program, so the body of an async function there cannot use it (below): it calls the function of the other file only through ConJS code, or by `require` of a plain JavaScript file that both share.
* The body is **JavaScript, not ConJS**: it means what it means in JavaScript (`+` joins strings, `length` counts units of UTF-16, Promise, `Map` and the methods ConJS lacks are there). The translator copies its text into the module as it is in the source, from the token after `async` to the closing brace, so nothing of section 5 applies to it. To find the closing brace and the names of the body, the translator parses it with its parser, with `await` added as a unary operator, and `async` taken before arrow functions, function expressions and methods of object literals inside the body (`Promise.all(xs.map(async (x) => ...))`; M2's review). The parser already knows optional chaining (`?.`) and `??`. A body with syntax that the parser does not know stops the translation with `conjs: not in ConJS yet, in an async function: ...` for now: a regular expression literal (`new RegExp("...")` works), `for await`, a label, a class expression, a getter or setter in an object literal. A lexer that knows these, used only to find the end of the body, is a later step.
* **The names of the body**: its parameters and local names (with those of the functions nested in it, by the scopes of JavaScript: a local name or a parameter of a nested function that has the name of something of the program hides it, and is no error; M2's review), the globals of the host (`fetch`, `setTimeout`, `process`, `globalThis` ...), `require` on Node.js (2), and the other async functions of the same file. A free name of the body that is declared at the top level of the ConJS program (a variable, a function that is not async, a class, an imported name) or is one of the names of ConJS (`spawn`, `join`, `sleep`, `host`, `fs`, `http`, `readLine` ...) is an error of the translator: `conjs: an async function runs on the host and cannot use NAME of the program`. The host has no copy of them and could not call them back (values cross, functions do not; HOST-ja, 2).
* **`console`** (M2's review): on Node.js, `console.log` and `console.error` of the body write to the standard output and error of the program, in order with what the program prints. vm-node.js writes the output of the VM with `fs.writeSync` (`writeAll`), while the `console` of Node.js writes to a pipe asynchronously on macOS and Windows, so with the `console` of Node.js a line of the body could come after a line that the ConJS code printed later, only when the output goes to a pipe (conjs/test, `| less`). So vm-node.js passes into the text a `console` of its own whose `log` and `error` format their arguments with `util.format` (the JavaScript formatting, not that of ConJS: the body is JavaScript) and write with `writeAll`. Its other methods are those of the `console` of Node.js. In a page, `console` is that of the browser (its console, not the output of the page).

**2. How it runs**

* The translator writes the text of the async functions of a file into the module as one String, with their names, as it writes the JavaScript of the host functions (section 4). At the start of the program the runtime of ConJS hands it to the host with a new primitive of the feature `"js"`, `__JS_host_define__ onError text names ,()`: vm/wasm/conma.js compiles the text with `new Function` and adds each function to its `hostFunctions` under a name of its own (`conjs.async.N.NAME`, N the number of the module, so that two files can have functions of the same name and none meets a name of `CONMA_HOST`).
* On Node.js, vm-node.js passes into the text a `require` made with `module.createRequire` from the absolute path of the `.con.js` file as it was translated, which the translator writes into the module with the text (M2's review: bin/lang and bin/lang.cjs build the module of the program in a temporary directory, so neither the place of the module nor the current directory gives it). So `require("./x.js")` and the packages of `node_modules` are found from the program, as a CommonJS module beside it finds them. The async functions of an imported file `require` from the path of that file, each file with its own text and its own `require`. In a page there is no `require`, and the body uses what the page has.
* **Positions in the stack** (M2's review): the text begins with `//# sourceURL=` and the path of the file, and the translator puts before the first function as many line breaks as there are lines before it in the source, and keeps the lines between the functions, so that the stack of an exception of the host (a TypeError in the body) and the debugger of Node.js and of a browser point at the lines of the `.con.js` file. The columns are those of the source too, since the text is copied as it is, after `async` is dropped (the first line is written with spaces where `async ` was).
* **A call** of the function in ConJS code (`countLines(x)`) is written as the call of `host.wait` (`__Host_start__`) with that name: it waits for the Promise, the other tasks run meanwhile, and the arguments and the result are copied as `host.wait` copies them (HOST-ja, 2: numbers, strings, Booleans, plain objects, arrays; the empty array comes back as `undefined`, a function cannot be passed). A rejection throws an `Error` of ConJS with the message of the host, at the position of the call. The name used as a value (`const f = countLines`) is a ConJS function that makes that call.
* A ConJS host function (section 2) that calls it is a waiting host function, as one that calls `host.wait`.
* **Where it cannot run**: ConJS runs on the wasm VM only (stage P10). On the native VMs (`CONMA_VM=rust`) and where `new Function` is forbidden (a page with a Content-Security-Policy against `eval`, Node.js with `--disallow-code-generation-from-strings`) `__JS_host_define__` fails, and the program stops at the start with `conjs: the async functions of FILE need JavaScript on the host: ...`. There is no ConMa version to fall back to, unlike the host functions of section 7. The file of the build of section 8 (10.3) would let a page that forbids `eval` run them; it waits, as before.

**3. What does not change**

## 35. Results: async functions in a ConJS file run on the host (2026-11-26)

What the parser or the generator cannot take in a body stops with `conjs: not in ConJS yet, in an async function: ...` (`Conjs_async_message`, from `Sjs_uncaught`): a regular expression literal (with `new RegExp(...) can be used`), getters and setters, `this` outside a class, `==` and `!=`. `for await`, labels and class expressions work.

## 36. Design and results of H8: generator functions on the host (2026-11-28)

Designed and built by M2 at the user's request (2026-11-28), starting with the generators that do not wait (section 9). The form chosen keeps the generator object of ConMa and tells the two meanings of `yield` apart by the class of what is yielded, so the generators that wait came with it; only the built-in `readLines()` (generators of ConMa) stay in the VM.

* **Which functions.** A top-level `function*` declaration (not `async`) whose parameters are names and whose body the translator can write, as for other host functions (section 2), with `yield` and `yield*` (sjs/include/sjs_host.se: `Hx_candidate` notes `"genfn"`). Generator methods of classes and generator expressions stay in ConMa, and so does a generator that yields a function expression (a function cannot go to the VM).
* **The JavaScript.** The host version is a JavaScript generator `f_NAME`, always written as a waiting host function is (section 20), so that its calls of ConMa functions and its calls that wait are requests to the VM as before. `yield e` becomes `$Gr(yield new $Give(e, p))`: a `$Give` is a value for the reader, a plain array a request for the VM. `yield* e` becomes `yield* $star(e, p)`.
* **Called from ConMa** (conjs/include/conjs_host.se, `Conjs_hostgen`; sjs/include/sjs_gen.se gives it the ConMa body as a thunk): the call makes the generator object of ConMa (`Sjs_generator`), so `typeof`, `console.log`, `next`, `return`, `throw`, spreading, patterns and `for...of` in ConMa are those of every generator. Its body (`Conjs_hostgen_run`), at the first `next`, calls the host version through `$runGen`, which runs it in one session for its whole life, as `$runG` does for a waiting host function. A `$Give` becomes the request `give`: the body of ConMa prints the lines of `console.log` waiting, stops as at a `yield` of ConMa (`Sjs_yield_wait`) and sends what the reader does next to the host as `["ok", x]` (`next(x)`), `["threw", x]` (`throw(x)`, thrown at the `yield` as `$Thrown`) or `["ret", x]` (`return(x)`: the `yield` throws `$Ret`, which no `catch` takes, `finally` runs, and `$go` ends the generator with `x`). Any other request runs on the VProc as for a waiting host function, and may wait, so a generator may call `sleep`, `join`, `nextEvent` and waiting host functions.
* **The copies.** As at a wait (3.2), the host writes back its changes before it gives a value (`$sync`) and reads again what it holds when it goes on (`$refresh`): an array given twice is the same array of the VM, and a change the reader makes to an argument between two values is seen by the generator.
* **Escapes.** Before the first value, an escape (something the host cannot do, section 3.1) runs the ConMa body from the start as the body of the same generator object; nothing of the host was seen. After it, the host works as after a wait: what it cannot check goes to the VM (`$slow`), and what the VM cannot do either stops the program (`conjs: the host function NAME could not go on after yielding: ...`).
* **Called from a host function.** The call gives a `$HG` (the JavaScript generator, not started), which `for...of` and `yield*` step through on the host, in the session of the caller: the values cross nothing. In an ordinary host function (`$iter`, `$hgIter`), the other requests of the body are call backs (`$vmReq`, a nested run that must not wait); in a waiting host function or a generator (`$iterG`, `$moreG`, `$takeG`, `$closeG`) they go up as requests and may wait. A function that calls a generator function that waits is itself a waiting host function (`Hx_call`). A loop left early closes the generator (its `finally` runs). A `$HG` that leaves the function (returned, kept in an object, given to ConMa) cannot cross to the VM: before a call back the function runs in ConMa instead.
* **`yield*`** gives the values one by one as values of the outer body, as `Sjs_yield_star` of ConMa does: the value given to `next` is not passed in, and `throw` and `return` happen in the outer body (JavaScript passes them to the inner iterator; the host follows ConMa, so that every VM prints the same). Its value is the return value of a generator: of a host generator at once, of a value of the VM by the new operation `iter_ret`.
* **The rule of section 25**: each value given to ConMa counts as a crossing (`$cr`), so a generator whose body costs less than a crossing runs in ConMa after its first run from ConMa. Calls from host functions are not counted and keep the host.
* **Measured** (M2, Apple M2, the wasm VM, alpha 132492d and this branch run in turn three times, the time inside the program; scratchpad programs as in section 9): the generator that yields `0` to `n - 1`, summed by `for...of` in a host function, 2.53 to 2.55 s for 100,000 before and 9 to 10 ms after (about 250 times faster; about 0.1 µs a value against 25 µs); the same `for...of` at the top level (a statement function, section 26) 2.51 to 2.54 s and 9 to 10 ms. `next()` called 20,000 times from a ConMa function (a label keeps it there) took 0.74 s before and 0.86 to 0.90 s after the first run (37 µs and 44 µs a value): the crossing costs more than this small body, which is why the rule above turns such a generator off. `next()` from a top-level loop (a statement function that calls the method back in the VM each time) took about 1.9 ms a call before and after; that is the cost of the call backs of H6c, not of the generator, and is left for later.
* **The tests**: conjs/test/step20, case16 (values from a host function, the top level, spreading and patterns; `next(x)` and the return value; `return` with `finally`; `throw` caught inside and leaving; an endless generator closed by `return` in a host function; `yield*` over an array, a string, a host generator and a generator of ConMa, with their return values; a tree walked by a recursive generator; the same output as Node.js, step20/node.txt) and case17 (an array given twice; an argument changed by the reader; `console.log` of both sides in order; a ConMa function called back; a string that is not ASCII before the first value, the escape; an exception after a value, caught in ConMa and in a host function; a generator that sleeps while another task runs, read at the top level and in a host function). Their host lists (case*.host.txt), and those of case14 and case15, whose generators now run on the host, say which functions returned from the host.
* **Not done**: a generator object that is dropped before it ends keeps its session in the VM (`GENERATORS` of vm/src/prim/jsfn.rs) and on the host until the program ends, as nothing tells the host that ConMa dropped it (a `for...of` left early, a pattern and a spread close it, so this is a generator read by `next()` and left); generator methods and expressions; `readLines()`; a faster `next()` from the top level.
