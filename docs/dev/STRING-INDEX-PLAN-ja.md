# 文字列の位置を速く求める計画（ASCII の印と文字数）

Rust 版の VM（wasm 版と変換した VM も同じコード）の文字列に、「すべて ASCII か」と文字数を覚えさせ、文字（コードポイント）で数える位置と長さを、文字列を頭から調べずに求める計画である（2026-11-16）。ConMa の言語は変えない（docs/dev/FAST-PLAN-ja.md の F2〜F5 と同じく、VM の動きだけを変える）。

## 1. 目的と、測ったこと

* **ConMa の文字列の位置は文字で数える**（docs/PRIMITIVES.md の `__String_length__`、`__String_substring__`、`__String_find__`、`__String_find_any__`）。Rust 版の VM は、文字列を UTF-8 の `Rc<str>`（`Value::Str`）で持つので、位置をバイトの位置にするには、文字列を頭から調べる。
    * `__String_length__` は、全体が ASCII か（`is_ascii`）を調べ、そうでなければ文字を数える（vm/src/prim/string.rs の `char_count`）。
    * `__String_substring__`、`__String_find__`、`__String_find_any__` は、位置の前のバイトが ASCII か（`char_to_byte`）を調べ、そうでなければ文字をたどる。`__String_find__` は、見つけた所の位置を、そこまでの文字を数えて求める（`chars_in`）。
    * どれも、呼ぶたびに文字列の長さ（か位置）に比例する手間がかかる。長い文字列を 1 文字ずつ読むと、全体で文字列の長さの 2 乗になる。
* **測った例**（2026-11-16、Apple M4、user 秒。sjs/README-ja.md の「文字列の添字」）：SJS の `for (let i = 0; i < s.length; i++) { if (s[i] === "a") n++; }` は、1 回に `s.length`（`__String_length__`）と `s[i]`（`__String_substring__`）を呼ぶ。

| 文字数 | Rust 版の VM | wasm 版の VM | wasm 版の 1 回 |
|---|---|---|---|
| 2 万 | （起動が大半） | 0.45 秒 | 23 µs |
| 10 万 | 2.21 秒 | 2.99 秒 | 30 µs |
| 20 万 | 3.88 秒 | 8.78 秒 | 44 µs |

* ネイティブの VM では `is_ascii` が速いので目立たないが、wasm 版の VM では、1 回の時間が文字列の長さとともに増える。Node.js は 20 万文字で 0.05 秒。
* ConSh は、`$( )` の行を読むときに、読んだ塊を 1024 文字ずつの断片に切って位置で進める（consh/include/README-ja.md の「今の最適化版」）。これは、この手間を避けるための工夫で、文字列の位置が速くなれば要らなくなる。
* Python 版の VM は Python の `str`（PEP 393。文字の幅をそろえて持つ）を使うので、もともと位置で直接取り出せる。

## 2. 方針

* **見えるものは変えない**：結果、エラー、ステップの数、トレースは今と同じ。test/ のログが変わらないことで確かめる。
* **すべて ASCII の文字列だけを速くする**：ASCII なら、文字の位置はバイトの位置と同じなので、位置も長さもすぐ分かる。ConSh と SJS の文字列（コマンド、変数、数、`seq` の出力など）のほとんどは ASCII である。ASCII でない文字列は、文字数だけを覚え（`__String_length__` が速くなる）、位置は今と同じく頭から調べる（2026-11-21 に変えた。7）。
* **印は作るときに受け継ぐ**：ASCII の 2 つをつないだもの（`__String_concat__`）と、ASCII の一部（`__String_substring__`、`__String_strip_suffix__`）は ASCII なので、調べずに印を付ける。外から来た文字列（OS から読んだ行、`__Number_toString__` など）は、初めて位置や長さが要るときに一度だけ調べて覚える。
* **ほかのやり方は採らない**：文字の幅を 1、2、4 バイトにそろえて持つ形（Python の PEP 393）は、どの文字列でも速いが、OS への出入りや比較で UTF-8 との変換が要り、変更が大きい。一定の文字数ごとにバイトの位置の目印を持つ形（Swift の breadcrumbs）は、ASCII でない長い文字列にも効くが、要るのはまだ見えていない。どちらも、この計画の後で必要になったら考える。

## 3. 形

* `Value::Str(Rc<str>)` を `Value::Str(Rc<StrObj>)` にする。`StrObj` は本文（UTF-8）と、覚えた情報（`Cell`）を持つ。

| 情報 | 意味 |
|---|---|
| まだ調べていない | 初めて要るときに調べる |
| ASCII | 文字数はバイトの数。位置はバイトの位置 |
| ASCII でない、文字数 n | 長さはすぐ分かる。位置は今と同じく頭から調べる |

* プログラムに書いた文字列（`Value::StrNode`、AST の節）は、今は読むたびに本文を作り直している（`text` の `Cow::Owned`）。短いものがほとんどなので、この計画では変えない（S1 で測って、効くなら足す）。
* 使う所：`__String_length__`、`__String_substring__`、`__String_find__`、`__String_find_any__` が印を見る。`__String_concat__`、`__String_substring__`、`__String_strip_suffix__` が印を受け継ぐ。`string_value` は「まだ調べていない」で作る。変換した VM の生成コードが呼ぶ関数（vm/src/transpiled.rs の `d_string_concat` など）も同じ関数を使う。
* `StrObj` を 1 つの割り当てにする（本文を同じ領域に置く）か、本文を別に持つ（`Rc` から `Box<str>` を指す）かは、S2 で測って決める。`Rc<str>` は 16 バイトの太いポインタなので、`Rc<StrObj>`（8 バイト）にすると `Value` が小さくなるかもしれない。

## 4. 決めたこと（2026-11-16、ユーザーと）

1. **見えるものは変えない**：結果、エラー、ステップの数、トレースは今と同じにする。test/ のログが変わらないことで確かめる。
2. **ASCII でない文字列の位置は今のまま**：文字数だけを覚え、位置は今と同じく頭から調べる。**2026-11-21 に変えた**（ユーザーの指示）：ASCII でない文字列も、最後に求めた位置を覚え、次の位置をそこからたどる（7）。
3. **印を付ける時期**：つなぐ、一部を取るなど、作るときに受け継げるものは作るときに付け、外から来たものは初めて要るときに一度だけ調べる。

## 7. ASCII でない文字列の位置（2026-11-21）

* **きっかけ**：ConJS のプログラム（conjs/test/step14 の case2、vm/wasm/web/stars.con.js）の `conma build` が約 7 秒かかった。変換したテキストは、先頭のコメント（`;; ConJS を変換したもの`）と日本語の String のリテラルを含み、本体が 93 KB の 1 行になる。ConMa 版のフロントエンドの字句解析は、テキスト全体を位置で少しずつ読む（`__String_substring__`、`__String_find_any__`）ので、4 の 2 のとおり位置を毎回頭からたどると、手間が長さの 2 乗になる。ASCII でない文字を `x` にした同じテキストは 0.47 秒。
* **形**：`StrObj` に、最後に求めた位置（文字の位置とバイトの位置の組、`mark`）を持たせる（vm/src/value.rs）。ASCII でない文字列の位置は、`mark` から前か後ろへたどるか、頭のほうが近ければ頭からたどって求め、求めた位置を `mark` にする（vm/src/prim/string.rs の `char_to_byte_at`）。`__String_substring__` は、始めの位置を求めてから、そこから終わりの位置をたどる（`mark` は終わりに残り、続けて読む位置に近い）。`mark` は、印（`info`）と同じく覚えておくだけのもので、結果、エラー、ステップの数は変わらない。プログラムに書いた文字列（`Value::StrNode`）は今までどおり頭からたどる（短いため）。
* 2 の「ほかのやり方」の、一定の文字数ごとの目印（Swift の breadcrumbs）は採らなかった：位置を少しずつ動かして読むもの（字句解析、1 文字ずつのループ）には、最後の位置だけで足りる。あちこちを飛んで読むときは、今までどおり、たどる手間が飛んだ距離（か頭からの距離）になる。
* **確かめたこと**：test/step46 に case2 を足した（ASCII でない 1 つの文字列の位置を、前へ、少し後ろへ、頭に近い所へ、終わりへ、範囲の外へ動かし、1 文字ずつ前から後ろへ、後ろから前へ読む。ログは Python 版の VM で作り、Rust 版、wasm 版の VM で同じ）。test/（Rust 版と wasm 版の VM、wasm 版は既知の step40 だけ）、conjs/test、sjs/test、consh/test（Rust 版の VM）が通る。
