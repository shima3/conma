# Contributing

This is for the developers of ConMa and of ConSh. A developer of ConMa changes its VMs, its front end or its standard library; one who only runs ConMa programs is a user of ConMa. A developer of ConSh changes ConSh, and is a user of ConMa unless they also change the VM. The documents for the users are in [docs](../index.md) (and docs/consh for ConSh), and those for the developers in docs/dev (and docs/consh/dev); a document for both is in docs. GitHub Pages publishes docs without docs/dev and docs/consh/dev (`exclude` in docs/_config.yml, 2026-11-19): the documents for the developers are read on GitHub, in `alpha`, and are listed in [docs/dev/README.md](README.md) and [docs/consh/dev/README.md](../consh/dev/README.md), where a new one is added; their links to other documents name the `.md` files. The rules only for ConSh (where its files go, and changing both its optimized and reference versions) are in [docs/consh/dev/DEVELOPING-ja.md](../../docs/consh/dev/DEVELOPING-ja.md) (in Japanese). [docs/dev/CHECKLISTS.md](CHECKLISTS.md) lists, task by task (a piece of work, a pull request, a review, a Full Test), the steps of the rules below, each with the part that has the rule.

## Tests

[docs/dev/TESTS-ja.md](TESTS-ja.md) (in Japanese) lists every test suite with what to build first, the known differences and the notes for the tester, and [docs/dev/TESTS-RECORD-ja.md](TESTS-RECORD-ja.md) (in Japanese; in TESTS-ja.md until 2026-11-22) is the record of who ran every suite on which commit. Say in the commit message what you ran to check a change; when you run every suite, also add a line to the record.

A run of every suite there is called a **Full Test** (2026-11-18). It is a name, not that of a command or a file, and is written so everywhere, in English and in Japanese, at the beginning of a sentence and in a heading too: 「1ec4c7b の Full Test」, "the Full Test of 1ec4c7b". Older commit messages say "full run" or "full test run" for the same thing.

A run on I7, the machine on Windows, of every suite of docs/dev/TESTS-ja.md, Windows（I7）で流す, with each VM it lists (the Rust VM and the wasm VM), is called a **Windows Test** (2026-11-23), and is written as Full Test is: 「1ec4c7b の Windows Test」. It shows which commit runs on Windows, which CI does not show in full (it runs no wasm VM there). It does not make a commit tested: only a Full Test does, and only a Full Test removes the notes for the tester (Branches 3), as a Windows Test does not run the suites of Unix. I7 runs it on its own branch `i7/test`, into which it merges `alpha` as the tester does (Branches 3), and adds a line to the record (docs/dev/TESTS-RECORD-ja.md): 「Windows Test」, the commit of `alpha` it ran, and the differences besides the known ones that apply to I7 and to the VM that ran (docs/dev/TESTS-ja.md, 既知の違い: the rows 「Windows（I7）」, and, for the wasm VM, those of the wasm VM, 「wasm 版」). When the user says so (Branches 2), it merges `i7/test` into `alpha` only, never into `main`, which gets only what a Full Test tested; the line reaches `main` with the next Full Test.

GitHub Actions also runs the fast suites, on Linux and macOS, for every pull request and every push of `alpha` (**CI**, [.github/workflows/ci.yml](../../.github/workflows/ci.yml), 2026-11-22): the Rust and wasm VMs with test/, consh/test (Rust and wasm VMs), consh/js/test, sjs/test, conjs/test (Rust and wasm VMs), `cargo test` of vm and test/host-api.sh. A difference that is not a known one (docs/dev/TESTS-ja.md) fails the run, as does a build that fails. It is there to find early what breaks on another system than the machines of the developers, as Linux is not among them; it does not replace the Full Test, which still alone makes a commit tested (Branches 3) and still runs on the machine of the tester. An author of a pull request looks at its checks (`gh pr checks N`) before they hand it to a reviewer, and a reviewer names a check that failed. On Windows it runs, with the Rust VM, the suites that I7 runs (docs/dev/TESTS-ja.md, Windows（I7）で流す; since stage P6c, docs/dev/PLATFORM-PLAN-ja.md, section 4.11), with the known differences of I7.

## Languages of the documents

The documents for the developers are in English (2026-11-23). A new one is written in English. A Japanese one that is still changed as the work goes on (docs/dev/TESTS-ja.md and docs/consh/dev/DEVELOPING-ja.md) is moved to English step by step, as `NAME.md`. The plans, the reviews and the records (`*-PLAN-ja.md`, `*-REVIEW-ja.md`, `REVIEW-ja.md`, docs/dev/TESTS-RECORD-ja.md) record their own time and stay in Japanese; a new line of a record is written in the language of the record.

The documents for the users are in English and in Japanese, which the reader switches between: the English one is named `NAME.md` and the Japanese one `NAME-ja.md`, in the same directory. The English one begins with the line `**English** | [日本語](NAME-ja.md)` and the Japanese one with `[English](NAME.md) | **日本語**`, which GitHub and GitHub Pages both show as a link. The two say the same and have the same headings: a change to one is made to the other in the same commit, and CI checks that each pair has both lines and the same number of headings of each level ([.github/doc-pairs.py](../../.github/doc-pairs.py)). A document for the users that is in one language only, until it is translated, is listed with "(in Japanese)" on the index pages; when one is translated, a README that mixes things for the users and for the developers is first split, and the part for the developers goes to docs/dev in English (as conjs/README.md and docs/dev/CONJS.md, 2026-11-23).

## Commit messages

Write the first line as a summary of about 50 to 70 characters, then a blank line, then the details: what changed and why, and what you ran to check it and what you did not (see Tests). Commits before 2026-11-16 are written as one long sentence; they are left as they are.

Make a move of files a commit of its own (`git mv` only), and change the references in the next commit, so that the history of each file follows the move.

## Files that moved

Files and directories have been moved and renamed. A text that describes the present (a README, the specification, the design, the comments of the code) is changed to the new place. A text that records its own time (the reviews, the plans, the steps of the roadmap) keeps the old path and adds a note after it: "(moved to `NEW` on 2026-11-15)", or "(moved on DATE; now `NEW`)" for a file that moved more than once, and "(removed on DATE)" for one that was removed, with where its content went if it went somewhere; in Japanese, 「（2026-11-15 に NEW へ移動）」, 「（DATE に移動。今は NEW）」 and 「（DATE に削除）」. The date is that of the move. A reference to another document, which the reader follows to read it, is changed to the new place in every text, the reviews too, as the document is the same. Line numbers in such a text are those of its time, and are not changed. The records of docs/dev/TESTS-ja.md name the commit, and get no notes.

## Branches and Git settings

GitHub has two branches: `main`, which gets only states that passed every suite, and `alpha`, where the work of everybody comes together. Nobody commits to either directly: changes come in by merges, so the first-parent history of `main` (`git log --first-parent main`) lists the tested states. A push of `main` also publishes docs/ and the browser version of ConSh on GitHub Pages (.github/workflows/pages.yml, consh/js/README-ja.md). No hook or check stops a direct commit; take care yourself.

1. **A piece of work** (a feature, a fix, a plan and its stages) has a short branch of its own, made from the latest `alpha` in the clone where it is done and named after the machine and the work: `m4/chan`, `m1/string-index` (the Apple M1, M2 and M4 machines are `m1`, `m2` and `m4`, and the Windows machine I7 is `i7` (2026-11-22), so that the tables of times say where they were measured). The name `test` is kept for the tester's branch (3): a piece of work that adds tests is named otherwise, such as `m4/tests-step46`. Only one person or session writes to it. It stays in the clone; push it to GitHub only to keep a long piece of work safe, to go on with it on another machine, or to open a pull request for it (6), and delete it there when it is merged.
2. **When the work is done**, its author runs the tests the change touches and the benchmarks it affects, and says in the commit messages what they ran (see Tests). When the tester has something to run or measure for the branch, they write their notes for the tester in docs/dev/TESTS-ja.md, section 申し送り, under a heading of the branch (what to rebuild and in which order, the new tests, what they ran and did not run, anything to watch for, and a line 「種類：」 for the version: see Versions), and commit them on the branch. Only a branch whose files are all documents in the sense of 5 (files under `docs/` and `.github/`, and files named `*.md`), and that asks for no benchmark, gets no heading, such as a design that goes into `alpha` alone (2026-11-21): what it changed is in its commit messages and its pull request, and a heading would only say that there is nothing to run and wait there for the next test. A branch that changes any other file has a heading, even when the author thinks no suite reads that file (`.gitignore` or a sample page, say): the tester runs every suite on it anyway and needs to know what changed. They measure again themselves the benchmarks the change affects, without waiting for the user's word; a Full Bench, which only the user starts, they ask for there, in a line that begins with 「ベンチマーク：」 (see Benchmarks). Then, when the user says so (as every merge into `alpha` or `main` and every push of them, 2026-11-22: that was already how it went, and CLAUDE.md said so), they merge it into `alpha` and push: `git checkout alpha`, `git pull`, `git merge m4/chan`, `git push`; if the push is refused because somebody pushed in the meantime, `git pull` and `git push` again. The branch is then deleted (`git branch -d m4/chan`). A piece of work that goes on after that gets a new branch from `alpha`.
3. **The tester** keeps a branch of their own in their clone, named after the machine as the branches of work are: `m2/test`, for example. Unlike those, it is kept from one test to the next, and only the tester writes to it, also on a machine where they develop too (their development goes on branches of work). They merge `alpha` into it (`git pull` on `alpha`, then `git merge alpha` on `m2/test`) and run every suite of docs/dev/TESTS-ja.md there. If it passes, they add the line of the record (docs/dev/TESTS-RECORD-ja.md; the commit of `alpha` they tested), remove the notes of the branches that commit contains, raise `VERSION` as their 「種類：」 lines say (Versions), and commit on `m2/test`. Commits that reach `alpha` while the suites run are left for the next run: they are not merged into `m2/test` before the record, the record names only the commit that was run, and their notes stay (when `m2/test` is merged into `alpha` and the notes conflict, keep those of the branches not yet tested). A line that asks for a benchmark (「ベンチマーク：」) stays until the benchmark is measured (see Benchmarks); a heading goes when no line is left under it. Then, when the user says so (2), they merge `m2/test` into `main` (`git checkout main`, `git pull`, `git merge m2/test`, `git push`; with a new version, the tag too: Versions), so that `main` gets exactly what was tested and not what reached `alpha` during the tests, and into `alpha` (`git checkout alpha`, `git pull`, `git merge m2/test`, `git push`), so that the record and the removed notes reach everybody. If something fails, they tell the author, who fixes it on a new branch.
4. **The tester measures a Full Bench**, when the user tells them to (a developer measures the other benchmarks of their own change in the same way; see Benchmarks), on a branch of its own for each commit measured, `m2/bench-1a2b3c4` (the machine and the first 7 digits of the commit), and merges it into `alpha` only (see Benchmarks). Benchmarks that are fine do not make a commit tested: `main` still gets only what passed every suite (3).
5. **A change of documents only** may reach `main` without a run of every suite, so that a fix of a document or of the workflow of GitHub Pages is published at once (2026-11-18). It is a change whose files are all files that no build and no test reads: files under `docs/` and `.github/`, and files named `*.md` anywhere. A comment in a source file (`.se`, `.rs`, `.py`, a script) is not a document: it moves the positions in the modules, the logs and the transpiled code. A change that touches any other file, even for the sake of a document (such as `consh/js/build.sh` for the page of ConSh), goes the usual way (1 to 3).
    * Make its branch from the latest `main`, not from `alpha`, so that it brings nothing untested into `main`: `git checkout main`, `git pull`, `git checkout -b m4/docs-fix`.
    * Check what can be checked without the suites: that the links of the documents you changed lead to files that exist, and, for a workflow, what it runs (the Jekyll of GitHub Pages runs in the build of Pages that every pull request gets, from 2026-11-23; it can also be run with the image the workflow uses). Say in the commit message what you checked.
    * Add the line of the record (docs/dev/TESTS-RECORD-ja.md) in the branch, with 「文書だけ」 and what you checked; its commit column names the branch, as a commit cannot name its own hash.
    * When the user says so (2), merge the branch into `main` (`git checkout main`, `git pull`, `git merge m4/docs-fix`, `git push`) and into `alpha` (`git checkout alpha`, `git pull`, `git merge m4/docs-fix`, `git push`), then delete it.
6. **A pull request** (2026-11-20) is how a piece of work is reviewed and its tests are run by somebody other than its author before it is merged. The user decides which work goes through one; the author may also open one when they want a review. It goes between 2 and its merge, and changes nothing else: the notes of docs/dev/TESTS-ja.md and the record of docs/dev/TESTS-RECORD-ja.md stay as in 2 and 3, a Full Test is still run on `alpha` after the merge, and tests run on a pull request do not make a commit tested. Benchmarks go as before (see Benchmarks); the times a change needs may be quoted in its description.
    * **Opening.** When the work and its tests are done (2), the author pushes the branch and opens the pull request into `alpha` with gh (GitHub CLI). `gh pr create --body-file` does not read the template, so copy it and fill it in: `cp .github/pull_request_template.md body.md`, then `git push -u origin m1/foo` and `gh pr create --base alpha --title "M1: ..." --label wait-m2 --body-file body.md` (the title and the label as in the next two items; or `gh pr create --template .github/pull_request_template.md` to write it interactively). The description says what changes, what the author ran (each suite with the VMs and the commit), what they did not run, the known differences seen, and what they want looked at. The number of the pull request is known only after it is opened: the author then adds it to their notes in docs/dev/TESTS-ja.md (shima3/conma#N) in a commit of its own and pushes it. A change of documents only (5) goes into `main` (`--base main`).
    * **Who wrote it.** Every clone uses the same GitHub account, so a description or a comment begins with the machine of its writer and what it is: 「M2 のレビューです」, 「M1 の答えです」, and the title of a pull request begins with the machine of its author: `M1: Let ConJS read files a line at a time` (2026-11-21). Name the machine, not a role: who tests and who develops can change. For the same reason GitHub refuses an approval or a request for changes (`gh pr review --approve`, `--request-changes`) on the account's own pull requests: reviews are comments.
    * **Whose turn.** An open pull request has a label that names whoever has to act next (2026-11-21), so that the user sees in the list of pull requests whom to tell: `wait-m1`, `wait-m2`, `wait-m4` or `wait-i7` for a machine (to review, to answer or to fix), `wait-user` for the user (to choose who reviews, to decide on the merge or on a question). It names the machine, not a role, because the user may ask another machine than the usual one for a review. The author opens the pull request with the label of the machine that is to review it, or with `wait-user` when none is chosen yet; the user, or the machine they ask, then changes it. Whoever posts a comment changes the label in the same step: `gh pr comment N --body-file review.md`, then `gh pr edit N --remove-label wait-m2 --add-label wait-m1`. A review that leaves something to answer hands the turn to the author; an answer hands it back to the reviewer; a comment that says 「指摘なし。」 (Answers) also hands it back to the author, who hands it to the user (`wait-user`) as Answers says (since 2026-11-21: which cases need the author before a merge was too hard to tell). The user answers in the chat of a machine, not on GitHub, so the machine that acts on the user's words changes the label (from `wait-user` to whoever acts next), when it posts the comment that says what it did, or at once if it posts none. When two machines review, each has a label, and each removes its own when it has commented. A pull request that its author merged leaves the list, so its label is not removed; one that another machine merged keeps the author's label until the author has checked it (Merging). If the label and the last comment disagree, the last comment is right: fix the label. The open pull requests that wait for the user: https://github.com/shima3/conma/pulls?q=is%3Apr+is%3Aopen+label%3Await-user
    * **"Check your PRs".** When the whole of the user's message is 「PR確認」, "check your PRs" or "PRs" (2026-11-21; the word in a longer sentence is not this), a machine lists the open pull requests with its own label (`gh pr list --repo shima3/conma --label wait-m2` on the M2), and the merged ones that still have it (`--state merged`; Merging), and, for each, does what the last comment asks: reviews a new one, answers or fixes a review of its own, checks an answer, does what is left after 「指摘なし。」, checks a merge by another machine. The signal is the same as the user naming each of those pull requests (「m1 が PR した」), so it posts as it always does: the user decided on 2026-11-21 that a machine posts its comments without showing them first, and reports afterwards what it posted. It also says which open pull requests have no `wait-` label, as one may have been forgotten. When none has its label, it says so. It never merges on this signal, even a pull request with `wait-user`: a merge waits for the user's own words (Merging).
    * **Review and tests.** Whoever the user asks (another developer, or the tester) reads it with `gh pr view N --comments` and `gh pr diff N`, fetches the branch, runs the tests the change touches on the head of the branch, and answers in one comment (`gh pr comment N --body-file review.md`): the commit, the suites and VMs run and their results (with the lines that differ), then what they found, most important first, each with a concrete case. They report only what they ran on the commit they name, and say what they did not run. If the branch does not merge cleanly into the latest `alpha`, or `alpha` has changed something the work touches since it was opened (a move of files, say), the reviewer asks the author to take in `alpha` first and runs the tests after that.
    * **Answers.** The author answers with new commits on the same branch and a comment that says what changed and in which commit. They push those commits and never rebase them; to take in `alpha`, they merge it into the branch (`git merge alpha`). The reviewer reads the new commits, runs again what they touch, and comments again. When nothing is left, the reviewer says so in a comment whose first sentence names the writer and the commit and whose second is 「指摘なし。」: 「M2 の確認です（a2cb6e2）。指摘なし。」 (until 2026-11-21 it began 「指摘なし」, which could not go with Who wrote it), and hands the turn back to the author. The author then does what is left before a merge, if anything (a suggestion the reviewer left to them, a paragraph of the review in a design, the notes, taking in `alpha`), says in a comment what they did, or that nothing was left, and hands the turn to the user (`wait-user`); that is the sign for the user to decide on the merge.
    * **Merging.** Only when the user says so, the author, or another machine that the user tells to, merges it into `alpha` as in 2 (a local `git merge` and `git push` also marks the pull request merged), or with `gh pr merge N --merge`, then deletes the branch on GitHub (`git push origin --delete m1/foo`) and, if it is the author, in the clone. A change of documents only is merged into `main` the same way; after `gh pr merge`, which makes the merge commit on GitHub, the one who merges pulls `main` and then merges the branch, or `main`, into `alpha` as in 5. A machine that merges a pull request of another author says so in a comment (who told it to, and where the branch went) and leaves the author's label on it (`wait-m2`), although the merge has closed it. The author, when they find it ("Check your PRs"), checks that the work reached `alpha` (and `main`), deletes the branch in their clone, says in a comment what they checked, and removes the label; that ends the pull request, as a merged one cannot be closed again. The notes keep the number of the pull request and say briefly what was run on it, so that the tester can find what the Full Test still has to cover; the results in detail stay in its comments.

A commit that has been pushed is never rebased, so that the hashes written in documents and messages stay right: `alpha` is pulled with a merge (`branch.alpha.rebase false` below), and a branch takes in `alpha` with `git merge alpha`, not `git rebase`. From 2026-11-15 to 2026-11-16 everybody committed to `alpha` directly, kept linear by rebasing on pull; records that say "alpha の xxxxxxx" name those commits, which stay in `alpha` and `main`.

Run these once in each clone; they go to `.git/config`, which is not committed, so pulling does not set them:

```
git config merge.ff true
git config pull.rebase true
git config pull.ff true
git config pull.autostash true
git config branch.main.mergeoptions --no-ff
git config branch.main.rebase merges
git config branch.alpha.mergeoptions --no-ff
git config branch.alpha.rebase false
```

* `git pull` fast-forwards when it can. Otherwise, on `alpha` it makes a merge commit (`branch.alpha.rebase false`), and on other branches it puts your local commits that are not pushed on top of what was pulled (rebase); changes in the working tree are stashed and put back.
* `git merge` fast-forwards when it can and otherwise makes a merge commit; on `main` and `alpha` it always makes a merge commit (`branch.main.mergeoptions`, `branch.alpha.mergeoptions`), so that the first-parent history of `alpha` (`git log --first-parent alpha`) lists the pieces of work merged into it. `git pull` still fast-forwards on them when it can (`pull.ff true` comes before the merge options), so a pull with nothing of your own makes no empty merge commit. Until 2026-11-16 the clones set `merge.ff only`, which stops such a merge; `merge.ff true` replaces it, and also overrides a global `merge.ff false`, which would make a merge commit even where a fast-forward is possible.
* On `main`, `git merge m2/test` always makes a merge commit (`branch.main.mergeoptions`), and `git pull` keeps merge commits when it rebases (`branch.main.rebase merges`; a plain rebase would flatten them). Pull `main` before merging into it.
* If you commit to `main` or `alpha` by mistake and have not pushed it, move the commit to a branch of the work (`git branch m4/fix` there, then `git reset --keep HEAD~1` on `main` or `alpha`); if you have pushed it, tell the others before you change that branch again.
* `pull.ff true` is there to override a global `pull.ff only` (`git config --global`), which would stop `git pull` before it could rebase or merge; a setting of the clone comes before a global one (`git config --show-origin --get-regexp '^(merge|pull|branch)\.'` shows which applies).

## Versions

The version of ConMa is the line of `VERSION` at the root (0.1.0 from 2026-11-24; semantic versioning, with no promise of compatibility before 1.0), and `bin/version` prints it with the commit (README.md, Version). It goes up when `main` gets new work, by these rules (the user's, 2026-11-24):

* **MAJOR** goes up only when the user says so (1.0 among them).
* **MINOR** goes up when a feature was added; **PATCH** goes up when things were only fixed. A MINOR that goes up sets PATCH to 0.
* **The notes say which.** The notes of each branch (Branches 2) have a line 「種類：」 with 機能 (a feature was added), 直し (only fixes), 両方 (both) or なし (neither: tests, benchmarks or the workflow only). A branch of documents only (5), which has no notes, changes neither the number nor the tag.
* **The tester decides.** In a Full Test (3), the tester reads the 「種類：」 lines of the notes they remove: if one is 機能 or 両方, MINOR goes up; if they are all 直し and なし, PATCH; if all are なし, nothing. They change `VERSION` on `m2/test` in the commit of the line of the record, which names the new version.
* **A tag on `main`.** When `m2/test` is merged into `main` (3) with a new version, the merge commit gets an annotated tag (`git tag -a v0.2.0 -m "ConMa 0.2.0"` on `main`), pushed with `main` (`git push origin v0.2.0`) when the user says so.
* The first Full Test that contains `VERSION` keeps 0.1.0 and tags it `v0.1.0`.

`consh/bin/consh.ps1` prints the same line as `bin/version` in its own code: change both together.

## Benchmarks

The benchmarks are in bench/ (ConMa programs against CPython), consh/bench (ConSh scripts against Bash and the Rust version of ConSh) and sjs/bench (SJS programs against Node.js and CPython, and in sjs/bench/consh the same computations as ConSh scripts whose work is all in `(( ))`, which only the wasm VM runs in about a second; until 2026-11-19 they were consh/bench 19 to 21) and conjs/bench (ConJS programs against Node.js, on the Rust and wasm VMs, from 2026-11-24). The tables of their results are in bench/README.md, consh/bench/README-ja.md, sjs/README-ja.md and conjs/bench/README-ja.md, called the READMEs of the benchmarks below. They are measured as follows.

A measurement of every benchmark in one of the four directories, with the versions that the request names, at the sizes the tables give, on one machine, is called a **Full ConMa Bench** (bench/), a **Full ConSh Bench** (consh/bench), a **Full SJS Bench** (sjs/bench) or a **Full ConJS Bench** (conjs/bench, from 2026-11-24), and the four together a **Full Bench** (2026-11-18; three until 2026-11-24). They are written as Full Test is (see Tests). Unlike a Full Test, which always runs every suite on every version, a Full Bench takes every benchmark but only the versions asked for: to measure every version, the request names them all, and a request that names none means every version that the tables compare (as the Full ConSh Bench of eb1ff60 did; until 2026-11-19 this sentence said every version always). One is done only when the user asks for it; otherwise only what a change needs is measured again (2), by the developer of the change (3).

1. **Sizes.** Measure with a size (the parameter of a program or of a script) at which the fastest version in the table (of those it compares) takes about one second, so that the start and the noise of the machine are a small part of each time.
    * Not when the start itself is measured, or when a time must be compared with one measured before at the same size.
    * A version that takes more than 60 seconds for one run is not measured, or is measured at a smaller size, which the table says. When it must be measured at the same size, it is run once.
    * A size can change, so it is not in the name of a script. A script whose name has its size is renamed; texts that record their own time keep the old name with a note, as for files that moved (see Files that moved). Scripts that would have the same name without their sizes become one. In consh/bench and sjs/bench/consh, a script and its Bash version (`bash/` beside it, with the same name) are renamed together. The size of a script is in its first line, a comment, and in the tables of its results.
2. **What to measure again.** Measure again only the versions that a change made faster or gave something new; for the others, use the times measured before.
    * Measure again those too when there are no times before, or when they were measured at another size or on another machine and do not tell what is to be compared.
    * When the difference is expected to be under 10%, which the state of the machine can hide, measure the version before the change too, alternating the two.
    * A transpiled VM built before may be measured without building it again when `git diff --stat BUILT MEASURED -- vm include bin consh/include bench test/transpiled` prints nothing (BUILT the commit it was built at, MEASURED the commit to measure): nothing that goes into it has changed.
    * For a version that takes long to build (the transpiled VM: about 20 minutes), copy its binary before rebuilding it, and measure the copy as the version before. Check with `CONMA_TRANSPILED_REPORT=1` that the copy uses the transpiled code of the present modules (a module of another text runs without it, more slowly). Do not build the version before in another directory: the modules have the paths of their files in them, and the transpiled code is chosen by the text of a module. consh/bench/run.py takes the copy as `VERSION=PATH` (`-v conma:transpiled=/tmp/before/conma,conma:transpiled`; consh/bench/README-ja.md) and runs the versions in turn. Never measure a transpiled VM built with `CONMA2RUST_COMPACT=1` (its code is laid out otherwise; vm/README.md), and do not take its build time as that of the transpiled VM.
3. **Who measures.** The developer of a change measures again, on their own machine, the benchmarks it affects; only a Full Bench is asked for, and only the user starts it (2026-11-18; before, every measurement was asked for).
    * It has to be measured again when the change touches what the versions share (a VM, the standard library, the front end, the modules of ConSh or their transpiled code), when it is expected to change the times in another way (such as a module that has to be made again), or when a compiler or interpreter has a new version.
    * **A measurement that is not a Full Bench** the developer does without waiting for the user's word, when they see it is needed, and measures as little as tells what is needed. They make a branch from the commit measured (normally the last commit of the branch of work), named after their machine and that commit (`m1/bench-1a2b3c4`), build what is to be measured (a build that has not changed may be used again, 2), measure, write the results in the README of each benchmark, and commit. Then they merge the branch into the latest `alpha` only, push it, and delete the branch, as the tester does below. They do not run other heavy work on the machine while measuring, they check the versions of the compilers and interpreters there, and the tables say the machine.
    * **A Full ConMa Bench, Full ConSh Bench, Full SJS Bench or Full ConJS Bench** is asked for by the developer in the notes of their branch (docs/dev/TESTS-ja.md, 申し送り), in a line that begins with 「ベンチマーク：」. The line says which of the four; the commit to measure (its first 7 digits), and the commit before when the times are to be compared with it; and the versions (such as the optimized ConSh on the transpiled VM), which are the only ones measured (every version the tables compare if it names none). It does not name who measures. When the user asks only for "a Full Bench", the developer picks by what the change touches: all four for `vm/` or `include/`, a Full ConSh Bench for `consh/include` (and a Full SJS Bench too when the change touches `(( ))` or the SJS files there, `sjs_*.se` and consh_jsstmt.se), a Full SJS Bench and a Full ConJS Bench for `sjs` (ConJS shares its translator and runtime), a Full ConJS Bench for `conjs`; they ask the user about the choice before pushing the notes.
    * The user decides who measures a Full Bench (normally the tester, on their machine) and when. A request in the notes is not by itself a sign to start: whoever measures starts when the user tells them to, so that two people do not measure the same request and the measuring does not overlap other heavy work.
    * Whoever measures a Full Bench measures the commit the request names, or, if none is named, the latest commit of `alpha`. They make a branch from it, named after their machine and that commit (`m2/bench-1a2b3c4`), build what is to be measured, measure, write the results in the README of each benchmark, remove the lines of the requests they did (a heading goes when no line is left under it), and commit. Then they merge the branch into the latest `alpha`, mending conflicts in the READMEs if there are any, and say in the merge commit whether there was a problem. They push `alpha`, then delete the branch.
    * The tester and their machine can change, so the tables say the machine of each time. Someone other than the tester who measures (a developer, or a session of Claude on another machine) does so on their own machine, in the same way: a branch named after that machine (`m4/bench-1a2b3c4`), merged into `alpha` only, with the machine in the tables. They do not run other heavy work on the machine while measuring, and they check the versions of the compilers and interpreters there, which may differ from the tester's. Within one table, keep the columns to be compared to one machine where possible.
4. **Tables.** When a table puts times measured now beside times measured before, each column says when it was measured, the commit, the machine, the versions of the compilers and interpreters (rustc, Node.js, CPython, Bash) and how it was measured (user + sys or real time, the least of how many runs).
    * A column measured on another machine, at another time or at another size has a note; so does a version whose output differed.
    * The default is user + sys, the least of 3 runs, the start included; a column measured so may leave out how it was measured.
    * When it helps, or when asked for, whoever measures also counts the steps (`CONMA_PROFILE`, vm/tools/vm_profile.py). The steps do not depend on the machine, so they tell a change of a ConMa program (such as ConSh) apart from the noise of the machine. Count them in runs of their own: counting makes the Rust VM 2.5 to 3 times slower, so the times of those runs are not written in the tables. Count them on the Rust VM only; the transpiled and wasm VMs would count the same. They are not quite exact when a script reads the output of an external command through a pipe, whose pieces depend on the OS: tens of steps in 30 million (consh/bench `02`).
