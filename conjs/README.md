# ConJS: a subset of JavaScript with lightweight threads and blocking calls

To begin: the [quick start](QUICKSTART.md) (install, build, and run a server written in ConJS) and the [tutorial](TUTORIAL.md) (the language by examples).

ConJS is a subset of JavaScript with lightweight threads that switch cooperatively (called "tasks" below) and blocking calls that stop only the task that makes them. A call that waits (a function of the host, a frame of an animation) is written as an ordinary call, with no `await`. While it waits, only that task stops, and the others run. It is made now with the translator and the runtime of SJS ([../sjs/README-ja.md](../sjs/README-ja.md), a safe subset of JavaScript), but it is a language of its own, and the JavaScript it takes will grow. The plan and the design are in sections 4.1 and 4.2 of [docs/dev/PLATFORM-PLAN-ja.md](../docs/dev/PLATFORM-PLAN-ja.md), and what was made in section 8.4 (stage P3b, 2026-11-19). How it is made and its tests are in [docs/dev/CONJS.md](../docs/dev/CONJS.md), for the developers.

```js
const t = spawn(() => host.wait("test.later", 2, "slow"));   // a new task; the caller goes on running
console.log(host.wait("test.later", 1, "fast"));             // only this task waits
console.log(join(t));                                        // waits for t to end and takes its return value
```

## Usage

```
conjs/conjs file.con.js           # translate it and run it on the wasm VM (Node.js; run vm/wasm/build.sh first); CONMA_HOST gives functions of the host
conjs/conjs --emit file.con.js    # print the ConMa source it is translated to
conjs/test/run_all.sh             # the tests (on the wasm VM)
conjs/test/compare.sh             # compare the cases of step10 with Node.js
conjs/bench/run.sh NAME           # a benchmark against Node.js (from 2026-11-24; the table in conjs/bench/README-ja.md)
conjs/conjs --prepare             # make the modules of the translator and the runtime in advance (the first run is then fast; from 2026-11-23)
conjs/conjs --version             # print the version of ConMa (from 2026-11-24; see Version of the README of ConMa)
```

ConJS runs on the wasm VM only, from 2026-11-25 (stage P10; section 4.13 of docs/dev/PLATFORM-PLAN-ja.md): `conjs/lang.conf` names it, and without it `conjs/conjs` says how to build it. Before, it ran on the Rust VM by default and on the VM that `CONMA_VM` chose (the wasm VM and the Python VM); `CONMA_VM=rust` still works, for the developers, but it is no longer tested. Code that uses `async` and `await` goes into a function of the host (docs/HOST-ja.md, 3.2). The translation runs on the Rust VM when it is built, which makes it faster, and the translated program runs on the wasm VM. Without the Rust VM, the translation runs on the wasm VM too (made by vm/wasm/build.sh; Node.js), from 2026-11-23 (`build` and `link` of vm-node.js); the modules are the same to the byte either way. `CONMA_TRANSLATE_VM=wasm` translates on the wasm VM even when the Rust VM is there. The translator is that of SJS (sjs/include), with the mark of the language (`"sjs_lang"` of the PDict set to `"conjs"`). Its module is made once, as conjsc.module.se, in the place of bin/cache-dir (as for sjs/sjs). The module of the runtime (conjs_rt.se and the others that the translated source includes) is also made once there, as conjs-rt-HASH.module.se; the translated source is made into a module without its include lines and joined to it with `conma link` (bin/lang; section 4.4 of docs/dev/PLATFORM-PLAN-ja.md, stage P5). A program of only `console.log("hi")` runs in about 0.18 seconds on the wasm VM and 0.08 seconds on the Rust VM (on an Apple M1, 2026-11-25; earlier, about 0.1 seconds on the Rust VM, and before that, the runtime went through the front end every time, in about 1.45 seconds).

On the wasm VM, functions that do not touch the variables outside them run on the JavaScript of the host, which gives the same results faster (from 2026-11-24; docs/dev/CONJS-HOST-PLAN.md). Of the calls that wait, such a function may call `sleep`, `join` and `nextEvent`, and other such functions: it waits in its task as in ConMa. If such a function, after calling a function of ConMa back or after waiting, comes to something the host cannot do, the program stops with `conjs: the host function NAME could not go on after calling back: ...` or `... after waiting: ...` (status 2). Run it again with `CONMA_NO_HOSTJS=1`, which runs every function in ConMa, and please report the program. `CONJS_HOST_REPORT=1` tells which functions fall back to ConMa, and why.

## Language

What SJS takes (「書けるもの」 of sjs/README-ja.md), without the things below, and with the things below added.

* **Left out** (an error when it is translated, such as `conjs: not in ConJS: async`, exit status 2): `async`, `await` (`for await` too) and the name `Promise`. What SJS does not take (`with` and so on) is also reported as "not in ConJS". `then` can be used as an ordinary name. The three names can also be used as keys of objects (`{ async: 1 }`) and as names of members (`o.await`) (the shorthand `{ async }` is a variable, so it is an error).
* **`import` and `export`** (stage P9, 2026-11-23; section 4.12 of docs/dev/PLATFORM-PLAN-ja.md; conjs/include/conjs_modules.se): a program can be split into files, as with the ES Modules of JavaScript. SJS leaves them out.
    * **What is taken**: `import { a, b as c } from "./lib.con.js"`, `export const`, `export let`, `export var`, `export function`, `export class` and `export { a, b as c }`, at the top level of a file only. The path begins with `./` or `../`, is relative to the importing file (to the real file when it is a symbolic link), and has the extension, as Node.js wants it.
    * **Meaning** (as in JavaScript): each imported file runs once, before the files that import it, in the depth-first order of ES Modules; the names of each file are its own; imported names are live bindings (a `let` that the exporting file changes later shows the new value) and cannot be assigned. Two paths that name the same file (`./a/../lib.con.js`, a symbolic link) are the same file. The top level of an imported file can wait (`sleep`, `join`), as the top-level `await` of JavaScript does.
    * **Errors when it is translated** (exit status 2): a file not found, a name not exported, a name exported twice, a cycle of imports (`import cycle: a.con.js -> b.con.js -> a.con.js`), an assignment to an imported name, and `import` or `export` not at the top level.
    * **Not taken yet** ("not in ConJS"): `export default` and `import x from`, `import * as m`, `export ... from` and `export *`, `import "x"` without names, `import()` and `import.meta`. A name without a path (`"fs"`) is an error: the libraries of ConJS stay global names.
    * The programs of conjs/test/step19 run the same in Node.js 22 and later, which reads `import` in a `.js` file without a `package.json`.
* **Classes** (stage P5b; section 4.5 of docs/dev/PLATFORM-PLAN-ja.md; conjs/include/conjs_class.se): SJS leaves them out, but ConJS takes them.
    * **`class`** (declarations and expressions): `constructor`, methods, `static` methods (inherited from the parent; `this` is the class the method was read from), fields of instances (`x = 1;`; set in the order written, before the constructor runs; the initializer can use `this`), `extends` (a class, or a constructor of the built-in errors), `super(...)`, `super.m(...)` and generator methods. A class with `extends` and no constructor passes its arguments to the parent as they are.
    * **`new C(...)`**: C is a class or `Error`, `TypeError`, `RangeError`, `SyntaxError` or `ReferenceError`. `new` of an ordinary function, and a call of a class without `new`, are a TypeError. The constructors of the errors can be called without `new` too (as in JavaScript). When a constructor returns an object, that object is the value of `new` (as in JavaScript).
    * **`this`**: only in the constructors, the methods and the field initializers of classes, and in arrow functions in them. In an ordinary `function` and at the top level of the program it is an error when it is translated (`conjs: this outside a class`). In the constructor of a class with `extends`, `this` before `super(...)` is a ReferenceError.
    * **`instanceof`**: the right side is a class or a constructor of the errors (others are a TypeError). The errors that the runtime throws (the TypeError of `null.x` and so on) are also instances of `Error` and of the constructor of the same name.
    * **Errors**: an error object has `name`, `message` and `toString()`. `name` and `toString` are found the way methods are, as those of the prototype are in JavaScript, so `this.name = "MyErr"` shows in `Object.keys` and in JSON (as in JavaScript). `message` does not show in `Object.keys` nor in JSON.
    * **Not added** (an error when it is translated): getters and setters, private fields beginning with `#`, `static` fields and blocks, methods with computed names, and `new.target`. The prototype (`prototype`, `constructor`, `__proto__`) cannot be read in any form, as before.
    * `console.log` prints an instance as `Point { x: 1, y: 2 }` and a class as `[class Point]` (`[class B extends A]`), as Node.js does. `Object.keys`, `JSON.stringify` and the spread see only the object's own properties (as in JavaScript).
* **`spawn(f)`**: puts f, a function with no arguments, at the end of the queue as a new task, and returns the task. The caller goes on running until it next waits. A task prints as `[Task]` in `console.log`, and its `typeof` is `"object"`.
* **`join(t)`**: waits until the task t ends, and returns the return value of its f. When t ended with an exception, it throws that exception again, with the position where it was thrown in t. A task can be joined any number of times, from any number of tasks. Joining the task itself is a TypeError.
* **`host.call(name, ...args)`**: a function of the host that returns at once (`__Host_call__`). **`host.wait(name, ...args)`**: a function of the host that waits (`__Host_start__`). **`host.available(feature)`**: `__Feature_available__`. Numbers, strings, Booleans, objects (their own properties only) and arrays of them can be passed; an LList the host returns becomes an array, a Dict an object, and null `undefined` (an empty array becomes `undefined` too). A function the host does not have, and a function that fails, throw an `Error` with the message of the host. How to add functions of the host (in a browser, in Node.js and in the Rust VM) and the values that can be passed are in [docs/HOST-ja.md](../docs/HOST-ja.md) (stage P7). The functions for the tests (`test.add`, `test.echo`, `test.fail`, `test.later`) are in every VM.
* **The library of calls that wait** (stage P5; conjs/include/conjs_lib.se): the names follow JavaScript, but no Promise is returned: only the calling task waits until the result comes. They are things of the host, which SJS leaves out, so they are in ConJS only, not in SJS.
    * **`sleep(ms)`**: only the calling task waits for ms milliseconds (a name JavaScript does not have). An ms that is `undefined`, negative, NaN or infinite is 0; one that is not a number is a TypeError. It returns `undefined`.
    * **`setTimeout(f, ms, ...args)`**: the same as `spawn(() => { sleep(ms); return f(...args); })`. Unlike JavaScript, it returns a task, not a number, so `join` gives the return value of f (there is no `clearTimeout`). Unlike JavaScript, an exception that f throws does not stop the program there: it is reported at the end of the program, as that of a task that was not joined.
    * **`Date.now()`**: the milliseconds since 1 January 1970 (an integer). `Date` is an object with only this, and `new Date()` cannot be written (`new` is only for classes and the constructors of the errors).
    * **`fs.readFile(path)`, `fs.writeFile(path, text)`**: read and write a whole file as a string (the names of Node.js; `fs` is global). A relative path is from the directory the program was run in. An ordinary file is read and written at once, so no other task runs meanwhile. A file that cannot be read or written gives an Error whose message begins with `fs.readFile: `. In a browser page (the wasm VM with no files of the host) they read and write files in the memory of the VM (they are lost when the page is closed; not checked yet).
    * **Reading a file line by line** (stage P8; conjs/include/conjs_file.se):
        * **`fs.open(path, mode)`**: opens a file and returns a file object. mode is `"r"` (the default), `"w"` or `"a"`. A file that cannot be opened gives an Error. It is made like the FileHandle that `fs.promises.open` of Node.js returns (`fs.open` of Node.js is another thing, which passes a file descriptor to a callback).
        * A file object (`File { path: 'a.txt' }` in `console.log`): `readLine()` (the next line, without its `\n` or `\r\n`; `undefined` at the end), `readLines()` (a generator of the rest of the lines: `for (const line of f.readLines())`; it closes the file when it ends and when the loop is left by `break`, an exception or `return`), `read()` (all the rest), `write(text)`, `close()` (any number of times) and `closed` (whether it is closed). Reading or writing after it is closed is an Error.
        * **`fs.readLines(path)`**: the same as `fs.open(path).readLines()` (a short way that Node.js does not have).
        * **`fs.stdin`**, **`fs.stdout`**: file objects of the standard input (for reading only) and of the standard output (`write` only; it adds no newline). The standard input cannot be read both as keys (`nextEvent`) and as lines: the one used first decides, and the other gives an Error.
        * An ordinary file is read without waiting. From a pipe or the standard input, when the data has not come yet, only the calling task waits. The time to read grows with the number of lines (about 22 microseconds a line on the Rust VM).
    * **`argv`** (stage P8): the array of the arguments given to the program (`["a", "b"]` for `conjs/conjs file.con.js a b`; `process.argv.slice(2)` of Node.js).
    * **`fetch(url, options)`**: an HTTP request. options has `method` (a string), `headers` (an object) and `body` (a string). It returns an object like a Response, whose body has been read in full, with `status`, `ok` (the status is from 200 to 299), `text()` and `json()` (none of them waits). A 404 and the like are not exceptions but make `ok` false; when it cannot connect, it throws a TypeError (`fetch failed`) (as in JavaScript). The wasm VM uses the `fetch` of the host (Node.js 18 or later, and browsers); the Rust and Python VMs run `curl` in a VProc that waits for it (without curl, a TypeError). `json()` uses the same reader as `JSON.parse`. With curl, HEAD is sent with `--head`, not `-X HEAD` (curl with `-X HEAD` waits for a body that never comes and fails).
    * **`http.listen(port, host)`** (stage P6b; Node.js only): starts an HTTP server and returns a server object. port is a number (0 when not given: the OS chooses), host is a string (`"127.0.0.1"` when not given: other machines cannot reach it). It can be used only when the wasm VM runs on Node.js (the feature `"server"`; vm/wasm/host/server.js); on the other VMs it is an Error (`http.listen: this platform has no server (Node.js only)`). A port that cannot be used is an Error (`server.listen: EADDRINUSE: address already in use`).
        * A server object: `port` (the real number), `accept()` (the next request; only the calling task waits until one comes; requests that come while no task takes them wait in a queue; after it is closed, `undefined`) and `close()` (it takes no new requests; the requests already taken can still be answered, the requests in the queue that were not taken are closed with 503, and a waiting `accept()` gets `undefined`).
        * A request object: `method`, `url` (the path and what follows `?`), `headers` (`req.headers` of Node.js as it is: lowercase names, headers of the same name joined, and only `set-cookie` an array) and `body` (a string, read in full). `respond(status, headers, body)` answers it (headers is an object, and can be left out: `respond(status, body)`; with no body, it is empty; a second answer is an Error; a header value that is not a string, a number or an array of them, or that Node.js does not take, such as one with a newline, is an Error, and the request stays to be answered again), and `json()` is `JSON.parse(body)`. A request whose body is over 1 MB is not taken but answered with 413.
        * **How it ends**: a server goes on waiting for requests until it is closed with `close()` or ended with Ctrl-C. When only tasks waiting in `accept()` are left, that is the ordinary state of a running server, and it is not taken as a deadlock (as with `http.createServer().listen()` of Node.js).
        * **How it differs from JavaScript**: `http.createServer` of Node.js calls a callback for each request, and the points where it waits need `async` and `await`. In ConJS it is written as a loop that takes the requests in turn, `for (;;) { const req = server.accept(); spawn(() => handle(req)); }`, and the work for one request is written from top to bottom (the same form as `net/http` of Go and servers with threads). As the form differs, the name differs too from `http.createServer`.
* **Waiting for input** (stages P5c and P6a): keys and clicks are waited for as calls that wait. Input that comes while nothing waits is not thrown away but kept in a queue, in the order it came.
    * In a browser page (stage P5c): the functions of the host `input.next` and `input.poll` (the feature `"input"`; vm/wasm/host/input.js). `host.available("input")` tells whether the feature is there.
    * In a terminal (stage P6a): without the feature `"input"`, keys are read from the standard input (conjs/include/conjs_term.se; the VM was not changed). When the standard input is a terminal, the first read sets it with `stty -icanon -echo` to read one character at a time without showing it, and the end of the program sets it back (when the program ends normally, with an exception that nothing catches, and with Ctrl-C; Ctrl-C gives exit status 130). It also reads from files and pipes. The names of the keys follow the browser: ordinary characters, `"Enter"`, `"Tab"`, `"Backspace"`, the arrows such as `"ArrowUp"`, and `"Escape"`; other ESC sequences and control characters are `"Unidentified"`. No clicks come. When the standard input ends, `nextEvent` throws an Error (`nextEvent: the input has ended`). macOS and Linux only (not Windows yet).
    * When the terminal is not set back (in rare cases, such as when the VM stops on an error of ConMa), stop the VM from another terminal and type `stty sane` (or `reset`).
    * **`nextEvent(ms)`**: returns the first input of the queue. When the queue is empty, only the calling task waits for the next input. An input is `{ type: "key", key: "ArrowUp" }` (`key` is `KeyboardEvent.key`; the repeats of a key held down come one by one) or `{ type: "click", x: 10, y: 20 }` (in the coordinates of the canvas). When no input comes in ms, `undefined`. An ms that is `undefined` (not given) or `Infinity` sets no limit; a negative one and NaN are 0; one that is not a number is a TypeError (unlike `sleep`, not giving it sets no limit). When two tasks wait at once, the one that began first gets the first input.
    * **`pollEvent()`**: the first input of the queue, or `undefined` when it is empty. It does not wait. Throwing the rest away with `while (pollEvent()) {}` when the screen changes keeps the keys pressed on one screen from going to the next.
* **How it differs from JavaScript** (files): `readLines()` for reading lines in Node.js is looped with `for await`, but in ConJS with `for` (only the calling task waits until the result comes). Lines end only at `\n` and `\r\n`: unlike readline of Node.js, a lone `\r` does not end a line (`"a\rb\nc"` is three lines in Node.js, and two in ConJS, `"a\rb"` and `"c"`; so for a file with a lone `\r`, merge.con.js and merge.node.js print different things). The standard input, the standard output and the arguments are `process.stdin`, `process.stdout` and `process.argv` in Node.js, but ConJS has no `process`, and puts them in `fs.stdin`, `fs.stdout` and `argv`.
* **How it differs from JavaScript** (classes): a method is made as a function bound to `this` each time the member is read. So a method taken out and called later still has the original object as `this` (in JavaScript, `undefined`), and `o.m === o.m` is false (in JavaScript, true). As there is no prototype, a method is looked for in the class and its parents only when the member read is not an own property. A constructor of a class with `extends` that ends without calling `super(...)` is not an error (in JavaScript, a ReferenceError; the fields of the parent and of this class are not set). When the constructor of the parent returns an object, it does not become `this` of the child (in JavaScript it does; only what the constructor of the class written with `new` returns becomes the value of `new`).
* **No colors of functions**: a task can wait in any function (a function passed to `map` of an array, the body of a generator, inside try and finally).
* **No interruptions**: tasks run in one VProc and switch only at calls that wait (`host.wait` and `join`). The code between two calls that wait runs without interruption. A long loop that does not wait stops the other tasks while it runs (as in JavaScript).
* **The order tasks run in**: the queue of tasks that can run is FIFO. A task whose call that waits got its result also goes to the end of the queue. The results are taken one at a time when no task can run, so a program that keeps spawning and never empties the queue gets no results from the host (as when microtasks keep being queued in Node.js).
* **The end**: when main (the statements of the file) ends with an exception that nothing catches, the program ends at once, without waiting for the other tasks (exit status 2). When main ends, the tasks left go on running. When all have ended, the tasks that ended with an exception and were not joined are printed in the order they ended, as `FILE:LINE:COLUMN: Uncaught (in task) MESSAGE`, with exit status 2. When only tasks waiting in join are left, it prints `conjs: Deadlock: tasks waiting in join: N`, with exit status 2.

The syntax of ConJS is a subset of that of JavaScript, but a program of ConJS is not a program of JavaScript (`spawn`, `join` and `host` are not in JavaScript, and in JavaScript a call that waits returns a Promise). So in most cases its output is not compared with that of Node.js, as it is in sjs/test. A program that uses neither those nor the library of calls that wait is a program of JavaScript too, so conjs/test/compare.sh compares its standard output with that of Node.js (the cases listed in node.txt of each step; until 2026-11-20, step10 only). A program that both ConJS and SJS take and that uses no call that waits gives the same result in both (they run on the same translator and runtime). ConJS grows first, and what of it is safe moves to SJS to be shared (section 4.1 of docs/dev/PLATFORM-PLAN-ja.md).

## Examples

* **Files** (stage P8; conjs/examples): merge.con.js reads two sorted files line by line and prints the lines in only one of them and the lines in both (the same as `comm` of Unix; `-` is the standard input). It is written just by moving the two `readLine` on in turn by what the comparison gives. The same written in Node.js, merge.node.js, makes two Interfaces of `readline`, and as `for await` cannot be used, it calls `next()` of the two asynchronous iterators with `await`, makes the function `async` and closes them with `try`/`finally`. conjs/test/compare.sh checks that the two print the same (conjs/test/node-pairs.txt). wordcount.con.js counts words with `fs.readLines`, the shortest example of its use.
* **A server** (stage P6b; conjs/examples): counter_server.con.js is a small server that spawns a task for each request (`/count`, `/slow`, `/file?name=...`, `/stop`). While `/slow` waits in `sleep(200)`, it answers other requests. The count is kept in a shared variable, but there is no point that waits between reading it and writing it, so no other task comes in between. With the argument `demo`, it listens on a port the OS chooses, sends requests to itself, prints the answers and ends with `/stop`. The same written in Node.js, counter_server.node.js, makes the callback of `http.createServer` `async` and uses the Promise of `setTimeout`, `fs.promises` and `for await` of `readline`. case2.node-check.js of conjs/test/step18 checks that the two print the same with `demo` (conjs/test/compare.sh runs it).
* **Functions of the host** (stage P7; conjs/examples): host_demo.con.js calls the functions of the host `demo.*`. The same functions are written in Rust, vm/examples/host_demo.rs, and in JavaScript, host_demo.host.js (`CONMA_HOST` of the wasm VM), and test/host-api.sh checks that the two give the same log (the Rust one with `CONMA_VM=rust`, as the API of Rust is there for programs of ConMa, from stage P10) ([docs/HOST-ja.md](../docs/HOST-ja.md)).
* **Pages** (conjs/web; vm/wasm/web until 2026-11-23): canvas_demo.con.js (a bouncing ball on a canvas; seen in canvas.html) and stars.con.js (Stars, 「星ひろい」, a game that waits for input; played in stars.html, stage P5c; conjs/examples/stars-term.con.js is the same game in a terminal, `conjs/conjs conjs/examples/stars-term.con.js`, stage P6a: it imports the rules of the game (the functions that are the same in both: the levels, the ghosts, the moves by keys) from stars.con.js, and each file has its own order of the screens and its own drawing, so stars.con.js has nothing of the terminal and stars-term.con.js nothing of the canvas; from 2026-11-23 to 2026-11-24 it imported the order of the screens too (`play`) and passed its drawing to it, and before that stars.con.js ran in both). conjs/web/build.sh translates them for the pages. The same game is written in plain JavaScript for the browser in two ways, stars-events.js (event-driven: a variable for the screen, branches in the handler of the keys, setInterval for the ghosts) and stars-async.js (async/await: the shape of the ConJS version, with await at every wait and Promises made by hand for the keys), played in stars-events.html and stars-async.html; compare.html shows two of the three versions side by side, with the lines that wait marked (from 2026-11-23).
