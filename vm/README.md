# ConMa VM in Rust

A second implementation of the ConMa VM. It reads the same modules (the output of `bin/resolver`) and takes the same arguments as `test/vproc_run.py`. The goal is to give the same output, traces and error messages as `test/vproc_step.py`, step by step, and to be much faster. It is the product, the Python VM the reference; with the ConMa frontend it embeds, it runs ConMa source files without Python.

## Build and run

```
cd vm && cargo build --release
vm/target/release/conma [--trace] <module_file> <func_name>
vm/target/release/conma [--trace] --main <module_file> [<arg> ...]
```

`conma build [--warn-arity] [--include <dir>]... <source>` writes the module of a source file, as `bin/includer` and `bin/resolver` do, and `conma run [--include <dir>]... <source> [<arg> ...]` makes it and runs it with `__start__` and the arguments, as `--main` does. Both use the ConMa frontend (`include/frontend.se`), whose module `vm/frontend.module.se` is in the repository and embedded in the executable (`include_str!`), so they need no Python; the standard library is `include/` of the repository (or `CONMA_INCLUDE`), searched after the `--include` directories. `__VProc_spawn__` uses it too (in another process of the executable). After changing a file of the frontend in `include/`, run `bin/update-frontend` and build again; `test/frontend` fails until then (docs/SELFHOST.md, "The frontend in the repository"). The ConMa frontend makes the module of ConSh in 3.7 s, `bin/includer` and `bin/resolver` in 1.2 s.

It needs Rust 1.75 or later (`rust-version` in `Cargo.toml`), and no crates. ConSh run directly in Rust (`consh/rust`, `CONSH_IMPL=rust`) needs Rust 1.87 or later, for `std::io::pipe`. Both `Cargo.lock` files are in version 3, which Cargo before 1.78 can read.

`test/vm.sh` starts either VM with the arguments of `vproc_run.py`: the Python one by default, the Rust one when `CONMA_VM=rust`. Every `test.sh`, `consh/bin/consh` and the ConSh tests start the VM through it, so

```
CONMA_VM=rust test/step3/test.sh
```

runs a test with the Rust VM. `test/vm_compare.sh <module_file> <func_name>` runs both VMs with `--trace` and shows the differences in the output, the exit code and the trace. With `CONMA_SEED=<n>`, both VMs choose the VProc to run next with the same pseudo-random numbers (see "Scheduling and Termination" in docs/DESIGN.md), so `vm_compare.sh` also compares them under a seed.

## Stages

The VM is written in the order of the steps of [docs/ROADMAP.md](../docs/ROADMAP.md); a stage is done when the tests of its steps pass with `CONMA_VM=rust`.

| Stage | Steps | Status |
|---|---|---|
| 1. Core: S-expressions, module loading, `step`, traces | 1–3 | done |
| 2. Data primitives: CChain/CFrame, `__Cont_get__`, Number, String, Dict, MSeq, Ref, PDict, `__Sexp_read__` | 4–8, 12, 18, 19, 28, 30, 34 | done |
| 3. VProcs and the scheduler, LazyList, `__Ref_wait_change__` | 10, 17, 20 | done |
| 4. OS: Streams, files, pipes, processes, signals | 9, 11, 13–16, 21–27, 29, 31–33 | done: every step passes |
| 5. ConSh: every test, and collecting cycles so that ConSh can run for long | `consh/test` | done |
| 6. Front end and start-up | `selfhost1`–`7`, `module1`, `module2` | done: every test passes without changes to the VM (see Start-up) |
| 7. Speed (once the steps match) | every test, and the same traces | first round done (see Speed) |

## Start-up

Measured on an Apple M4, with the ConSh module already built:

* The ConMa version of ConSh starts in about 0.018 s (`consh/bench/00_start.sh`, 2026-11-09), most of it loading the ConSh module (2.2 MB, about 86 MB of memory); the Rust version of ConSh in 0.002 s.
* Building the ConSh module, when its sources have changed, takes 2.78 s with `conma build` (the ConMa frontend, which `bin/consh` uses when the Rust VM is built; 3.58 s before its files in `include/` were made faster, `reference/README-ja.md`) and 1.32 s with `bin/includer` and `bin/resolver` (Python).

## Speed

Measured with the profiler of macOS (`sample`) on the ConMa front end building the ConSh module, and then on ConSh. Two changes took most of the time away:

* The allocator. A step makes and drops small Rc blocks (LVNodes, Closures, CFrames, LList cells), and the allocator of macOS took about half of the time (it also clears each block it frees). `alloc.rs` keeps blocks of up to 256 bytes in a free list for each multiple of 16 bytes, carved from chunks of 256 KB, so a block is reused by the next one of the same size. Larger blocks go to the system allocator. Small blocks are never given back to the system, so the memory of a process stays at its peak.
* Strings. A String made at run time was kept in source form, so every String primitive unescaped its arguments and escaped its result: the lexer, which takes a line apart one character at a time, spent about 40% of its time there. Such a String now keeps its text.

Smaller ones: `load_body` reuses the Vec of the OList, and the collector checks plain counters at each step.

| Run | Before | After |
|---|---|---|
| ConMa front end, the ConSh module | 9.9 s | 3.7 s |
| ConSh, `x=$(f $i)` 3000 times | 3.1 s | 1.7 s |
| ConSh, `x=$(f $i)` 20000 times | 21.0 s | 11.1 s |
| ConSh, `echo $i \| cat` 3000 times (a process each time) | 9.9 s | 8.9 s |

Every test passes with `CONMA_VM=rust`, and the traces of steps 1–8, 10, 12, 17–20, 28, 30 and 34 (129 runs) are the same as those of the Python VM. The time is now spread over the interpreter itself (`step`, the scheduler, cloning and dropping values).

Later measurements, on ConSh loops: a local variable is looked up at a mean depth of about 2 in its LVEnv (at most 16 to 40), so an LVEnv kept as arrays of frames would not make lookups faster; and keeping the values of global variables in the compiled expressions saved nothing, because the time goes to cloning the value (the reference count of the Closure), not to finding it. What helped is that the scheduler runs the steps of a VProc one after another while no other VProc is ready and none waits (no trapped SIGINT, no collection due, no kill pending), instead of putting it back in the ready queue after each step: this is what a pass of the scheduler would do anyway, and it saves about 10% of the time of a ConSh loop that runs in one VProc. A loop with `$( )` or pipes has VProcs waiting for channels, so it is not helped.

`__Dict_lookup_or__` and `__Dict_put__` called with a String written in place as the key have a cache for each such place (`DictSite` of `module.rs`, the `Ic` of transpiled code: the last shape and the position of the key), which `load_body_interp` hands to the VProc, and both read their operands where they are instead of moving them to new Vecs. In ConSh loops, 83% of the Dict operations go through such a place and 86% of those hit the cache, but the cache alone saves only 1–2% (finding a key costs little); with the operands read in place, 4–5%.

A Closure applied to exactly as many operands as its remaining parameters takes two steps: one binds them (a partially applied Closure with no parameters left), the next loads its Body (docs/VPROC_STEP.md, Case 2). Unless something shows each step (`--trace`, `CONMA_PROFILE`), the VM does both in one step and counts two (`Machine::fuse_apply`, docs/FAST-PLAN-ja.md 4.1), so the steps are numbered as before and a VProc gets as many steps from the budget. What changes is that another VProc cannot run between the two steps, so VProcs may be switched at other times (FAST-PLAN 3.3); in the tests, only the step number of an error in a VProc other than the first one changed (test/step10, which now leaves it out). The scripts of consh/bench take 5–11% less time (`02_for_seq_100000` 1.24 s → 1.10 s, `10_pipe_for_stdin` 2.77 s → 2.45 s), and the programs of bench/ 8–11%.

While a VProc is ready and others wait for the OS, the scheduler checks the OS every 64 steps (`POLL_INTERVAL`, as in the Python VM), and a check (`poll()` and `waitpid()`) took about 7 µs: in `for i in $(seq 1 20000); do n=$i; done`, where a VProc waits for `seq` to end, the 155,250 checks took 1.1 s of the 1.85 s, mostly in the kernel or descheduled. A process that waits can only have ended if a SIGCHLD came, so while only processes wait, a check now does nothing unless the SIGCHLD handler has counted a signal since the last check, or a process was added to the waiting list since then (it may have ended before the handler was installed). The VProcs wake at the same checks as before, so the steps are the same. That loop now takes 0.61 s, `echo $i` 20000 times 1.29 s instead of 3.27 s, and a function called 20000 times 1.87 s instead of 4.95 s.

To see where a ConMa program spends its steps, run it with `CONMA_PROFILE=<file>`: each step is counted under the Body that the VProc is running, and the calls of each Body and the steps that apply each primitive are counted too. `python3 test/vm_profile.py <file>` sums them by file, by top-level `define` (steps, calls and steps per call) and by primitive; `--callers NAME` shows the lines that call a function, and `--thunks` the lines that pass `__if__`, `__unless__` or `__if_then_else__` a condition written as a function instead of a Boolean. The counts do not depend on the speed of the VM, so they also tell how a change to a ConMa program (such as ConSh) would speed up the Python VM.

## Transpiled code (experimental)

`vm/conma2rust/conma2rust.py`, the ConMa-to-Rust transpiler, makes Rust code for ConMa modules (files made by `bin/resolver`), and `vm/conma2rust/build.sh <module>...` builds the VM with it in `vm/target-transpiled`; `CONMA_VM=transpiled` in `test/vm.sh` runs that VM. The transpiled code of a module is used only for a module file with the same text (FNV-1a hash). The transpiled code also keeps the files of its module (the `(F ...)` at its start): when a module file has the same files but another hash, which happens when a source file was changed after the transpiled VM was built (`consh/bin/consh` makes its module again then), the VM says on standard error that the transpiled code is not used and that the transpiled VM should be built again (`conma: warning: the transpiled code of this program was made from another version of its module, ...`), instead of running more slowly without a word. `CONMA_TRANSPILED_REPORT=1` says whether it is used, and `CONMA_TRANSPILED_OFF=1` turns it off.

For each Function whose Body can run without the VM (a primitive that only works on its operands, `__NULL__` passing values on, `__if_then_else__`, `__if__` and `__unless__` with clauses written in place), the transpiled code runs that Body and the ones after it. Where a Body needs the VM, it is loaded, and `run` (`src/transpiled.rs`) goes on with the steps after it as the VM would, as long as they are calls (a Closure with as many operands as parameters), returns (null as the Operator), escape continuations or safe primitives, entering transpiled code where it can; anything else (a primitive that may block or switch VProcs, a partial application) is left to the VM, and so is the VProc after 1,000 such steps, so that the other VProcs run. All this is one step of the VM. The results are those of the VM; the number of steps, and so the order in which VProcs run, differ, so traces and the step numbers in error messages differ, and tests that depend on that order may give another of the possible results (`test/step20` case11 and case21). With `--trace` or `CONMA_PROFILE` the transpiled code is not used.

The most used primitives (`__is_null__`, `__String_equal__`, `__LList_uncons__`, `__Dict_lookup_or__`, the Number arithmetic and so on; `DIRECT` in `conma2rust.py`) are called directly, with their operands in Rust variables and their results bound without the OList, through functions shared with the primitives (`is_null_core`, `equal_core` and so on), and `__Cont_get__ ,(return)` makes the continuation in place.

**Fused chains.** For each top-level Function, each function expression, and each LCont or clause where the code above hands the VProc back (see below), the transpiler also writes one Rust function for the Body and the Bodies after it (`Fuser` in `conma2rust.py`). The variables these Bodies bind are Rust variables, not LVEnv nodes; Numbers that go only between Number primitives (`__Number_add__`, `__Number_subtract__`, `__Number_multiply__`, `__Number_divide__`, `__Number_sqrt__`, `__Number_floor__` and the predicates) are `f64` and computed with Rust arithmetic, an operand that is not a Number giving the error of the primitive; the operands of the direct primitives are passed by reference; `__Dict_lookup_or__` and `__Dict_put__` with a String key written in place (without escapes) look it up by its text, which the transpiler writes into the code (`d_dict_lookup_str`, `d_dict_put_str`), with its hash in the index of a Dict as a constant that the Rust compiler computes (`str_hash` is a `const fn`; the index keeps each String key with its `str_hash`), so that such a lookup does not hash the key: richards 20 takes 0.88 s instead of 1.00 s, and nbody 0.30 s instead of 0.36 s. The index finds a String key by its hash alone (a u64 key in the hash map, with the text or texts of that hash beside it), and compares a short text byte by byte instead of calling `memcmp`: nbody takes 0.25 s instead of 0.29 s. `__NULL__`, and `__if_then_else__`, `__if__` and `__unless__` without an LCont whose clauses are written in place (both inlined as a Rust `match`), are run in place too, and a chain ends with a return or a call without an LCont (left to `apply`, which counts it for the budget). A call with an LCont is a Rust call (below), after which the chain goes on with its variables. `__Cont_get__ ,(return)` makes the continuation in place, in a Rust variable, and `return v` is a call without an LCont. `__if_then_else__`, `__if__` and `__unless__` with an LCont have their clauses inlined in a labeled Rust block: what a clause returns is the value of the block, and the LCont goes on after it (so it is written once). The VM would have the CFrames of the LConts of the clauses the code is in on the CChain; wherever the code hands the VProc back inside a clause (a bail, an `onError`, a call left to the VM), it puts them there first, and a Rust call from a clause puts them there if it is left (`fused_call` and `frame_run` take a function that builds the CFrames, `cframe_on`); a call without an LCont in a clause is a call whose LCont is the clause's, except a continuation (`return`), which drops the LCont. A `__Cont_get__` in a clause is left to the VM (its continuation would lack those CFrames). With these, 560 of the 645 top-level functions of ConSh are fused from their first Body (319 start with `__Cont_get__`), and its 15,000 function calls take 0.91 s instead of 0.98 s. The parameters of the Function are Rust variables too: each fused Function has a direct entry (`DirectFn`, in `Table::dfns`) that takes its arguments as Values, and a Rust call (`fused_call`) or a call that `apply` makes passes them there instead of putting them into LVEnv nodes that the chain would read back; its entry for the VM reads them from the LVEnv, and passes that LVEnv on so that a bail reuses it (`full`; after a direct call, a bail makes it). fib(32) takes 0.48 s instead of 0.70 s (CPython 3.9.6 0.37 s), richards 20 1.79 s instead of 1.98 s, and ConSh is not faster. The transpiler knows which variables the code after each Body reads (`Fuser.uses`, from the Functions it contains): the last use of a variable that is not read later moves its value instead of cloning it, and an LVEnv made for the VM has null in place of such a variable (the code that runs with it does not read it). `__is_null__` and the Number predicates give a Rust `bool`, which `__if_then_else__`, `__if__` and `__unless__` use as it is and which becomes a Boolean only where it is used as a Value (`bool_value`). With these, richards 20 takes 1.03 s instead of 1.21 s, fib(32) 0.39 s instead of 0.48 s, and the 15,000 function calls of ConSh 0.81 s instead of 0.90 s. A chain returns its values in an array, not a `Vec`, and when they are for the Rust call that is running (its CChain is the one the call started with) it goes back to that call at once (`fused_return`, `finish_return`) instead of through `apply`: richards 20 takes 1.00 s instead of 1.03 s, fib(32) 0.36 s instead of 0.39 s. A Rust call whose callee returns its values at once does not go through `drive`, and when no continuation was made in it, `frame_run` ends it without looking for CFrames to give: richards 20 takes 0.83 s instead of 0.87 s, fib(32) 0.31 s instead of 0.36 s. A value that `__Dict_lookup_or__` reads with a String key written in place and that the chain uses only as conditions (`Fuser.use_kinds`) is a Rust `bool` too, tested in the Dict without cloning it (`d_dict_lookup_bool_str`); a missing key or a value that is not a Boolean is left to the code of that Body: richards 20 takes 0.78 s instead of 0.83 s. A Function that calls itself without an LCont (outside such clauses) is written as a Rust loop: its parameters are Rust variables, and where the Closure it is running is called again (the same Function and LVEnv, checked when called, `self_call`), the chain sets them to the new arguments and starts again instead of making an LVEnv for them; such a call counts for the budget, as `apply` would count it, so that the loop lets the other VProcs run. A loop of 10,000,000 iterations takes 0.12 s instead of 0.65 s (CPython 3.9.6 0.32 s), and nbody 0.43 s instead of 0.50 s; ConSh, whose loops mostly go through its own functions, is not faster. At any other Body, or when a result is not what the chain expects (an `onError`, a Boolean that is not one), it makes the LVEnv the VM would have from the LVEnv it started with and its variables, and enters the transpiled code of that Body above ("bail"); so the results are those of the VM. `vp.lvenv`, which is only shown in traces, is the LVEnv of the Closure the chain runs (without its parameters). The `onMissing` of `__Dict_lookup_or__` with a String key written in place, and the `onError` of `__Number_divide__` and `__Number_sqrt__` computed on `f64`, are evaluated only when they are applied: in a program where such an operand is an undefined variable, the VM stops with an error at that Body, and the transpiled code only when the operand is needed.

**Inlining.** A call with an LCont of a global variable whose value is a small top-level Function (at most 8 Bodies, without `__Cont_get__`, not one it is written in, two levels at most; `INLINE_SIZE`, `INLINE_DEPTH` and `Fuser.inline` in `conma2rust.py`) is written as the code of that Function, in a labeled block as a clause with an LCont is: what the Function returns is the value of the block, and the LCont goes on after it. The code runs in the LVEnv of the Closure, after checking that the global variable holds a Closure of that Function (`inline_env`; otherwise the call is made as above), with its parameters in Rust variables numbered after those of the caller, and a String written in place passed to it stays a constant, so that `Sh_get sh "global"` of ConSh (`__Dict_lookup_or__ sh key ...`) is a lookup with a String key written in place, with its cache of the shape. Where it hands the VProc back, the CFrame of the caller's LCont is put on the CChain, as for a clause; a Function whose code would hand it back on its usual path (not for a condition that is not a Boolean) is not inlined. This takes the calls of the small functions of ConSh (a simple command calls about 170 functions, two thirds of them of 12 steps or fewer; `Sh_get` 32 times) out of the call machinery, where most of its time went (the calls and returns, and dropping and allocating their LVEnv nodes and frames, about half of its samples): the 15,000 function calls of ConSh take 0.59 s instead of 0.67 s, and richards 20 0.60 s instead of 0.69 s; the transpiled code of ConSh is 12.9 MB instead of 9.0 MB, and the transpiled VM takes about 4 min 50 s to build instead of 3 min 20 s.

**Other primitives and onMissing functions.** In a fused chain, a primitive of CHAIN (`conma2rust.py`) that is not called directly is called with its operands in the OList (`d_prim`, as `prim_call` calls it), and the chain binds the results from there; when it applies onError, the VM goes on (`after_prim`). A `__Dict_lookup_or__` whose onMissing is a function written in place goes on with the value when the key is there (by its text and cache when the key is a String written in place, `d_dict_get` otherwise) and leaves a missing key to the VM, which runs that Body (a lookup only reads), makes the Closure and applies it; such a retry loads the Body for the VM (`deopt`), since the code of the Body above would be the same chain again when it is the first Body of a fused Function (before, a retry at such a Body would never end). With these, the fused chains of ConSh hand the VProc back 16 times for each of its function calls instead of 48, more of its functions are inlined (2,354 calls instead of 1,752), and its 15,000 function calls take 0.57 s instead of 0.59 s, richards 20 0.54 s instead of 0.60 s; the transpiled code of ConSh is 16.8 MB instead of 13.2 MB, and the transpiled VM takes about 7 min 30 s to build instead of 5 min. `test/transpiled` runs a program that uses inlined calls, these primitives, onMissing functions and clauses that are continuations or Closures in variables (also a constant key put into a Dict through an inlined call, which the inlining above passed wrongly to the code for a new key or a value that is not a Dict); `bench/build.sh` builds its transpiled code in, so that it tests that code with `CONMA_VM=transpiled`.

**Clauses that are continuations.** A clause of `__if_then_else__`, `__if__` or `__unless__` that is not written in place, a variable or a global, is the usual way to return early (`__if__ condition return ,()`, `return` a continuation of `__Cont_get__`). When the chosen clause is a continuation, a fused chain applies it to no values (`fused_tail_call`), as the VM does (the VM drops the LCont, and the CChain is that of the continuation), and so does `if_call`, which loaded the Body for the VM instead; another value (`__nop__`, a Closure) is left to the VM, which runs the Body. Such a case, and a condition that is not a Boolean, now loads the Body for the VM (`deopt`) as a retry does, so that a Function whose first Body is such an `__if__` is fused (before, any bail at the first Body left the whole Function to the code of its Bodies). For ConSh, the bail sites of its transpiled code go from 1,942 to 848, 33 more Functions are fused from their first Body, its transpiled code is 17.3 MB instead of 16.8 MB, the Bodies loaded for the VM for each of its function calls go from 13 to 8, and its 15,000 function calls take 0.53 s instead of 0.57 s (richards and the other benchmarks are not faster).

**Size of the generated code.** Where a fused chain hands the VProc back (a bail, a CFrame), it makes the LVEnv the VM would have from its variables; this was written as one call of `lv_push` for each variable, which made 46% of the generated code of ConSh (137,000 calls). It is now one call of `lv_build` with the names as a table and the values in an array, so that the transpiled code of ConSh is 15.1 MB instead of 20.0 MB, and the transpiled VM (built with the benchmarks, test/transpiled and the fast version of ConSh) takes 3 min 35 s to build instead of 8 min 27 s, with the same speed. `bench/build.sh` builds in the transpiled code of the reference version of ConSh only when `CONMA_BENCH_REFERENCE` is set (it about doubles the build, 17 min with both before `lv_build`).

**Counts.** `CONMA_TRANSPILED_COUNTS=<file>` makes the transpiled VM count, by Body, where the transpiled code hands the VProc back, and write the counts to the file when it ends (`vm/src/transpiled.rs`, "Counts"; the program does the same, and without the variable the VM is not slower): `bail` where a fused chain enters the code of a Body above (`bail` in the generated code), `enter` each time the code of a Body is entered (after a bail, the code of a Body going on with the next one, a Closure applied without a direct entry), `deopt` each time a Body is loaded for the VM, `run` each time the VM enters transpiled code, and `leave` each time a step is left to the VM, by what it applies. `python3 test/transpiled_counts.py [--top N] <file>` sums them by function and by Body, with the text of its line. For the 3,000 function calls of ConSh (`for i in $(seq 1 3000); do add $i x > (r); done`), the fused chains bailed about 48 times for each call, mostly at primitives they did not call and at `__Dict_lookup_or__` whose onMissing is a function written in place (13 times since then, above: mostly at calls passing a function written in place and conditions written as functions), and the steps left to the VM are mostly `__LazyList_claim__` and `__LazyList_publish__` (the lines of `$(seq ...)`, 7 for each call).

**Positions in Strings.** Positions in Strings count code points, so `__String_find__`, `__String_substring__` and `__String_find_any__` copied their String operands (`string_args`) and counted the code points of the whole String at each call, and walked it code point by code point to the position: taking the lines of a long String one by one by position took time quadratic in its length. They now read the text of a String made at run time without copying it (`text`), take a position whose bytes before it are ASCII as that byte offset (`char_to_byte`; otherwise they walk the code points as before), and count the code points of the whole String only for the message of an index out of range; `__String_length__` and `__String_strip_suffix__` no longer copy either. The results and errors are the same. Taking the 8,000 lines of a String of 104,000 characters by position takes 0.036 s instead of 0.72 s; the scripts of ConSh that read many lines are 3% to 15% faster (`for` over `$(seq 1 100000)` 1.34 s instead of 1.43 s with the fast version, 4.02 s instead of 4.17 s with the reference version, which reads lines with util.se).

**MSeqs.** The rest that `__MSeq_uncons__` returns shares the items of the MSeq it is taken from, one further on (`MSeqObj::rest`: the items are behind an `Rc`, with a start), instead of copying them, and an MSeq copies its items (from its start) before it changes them when another MSeq shares them (`items_mut`), so that each still behaves as an MSeq of its own. Taking all the items of an MSeq one by one with `__MSeq_uncons__` took time quadratic in their number, since each rest was a copy: ConSh collects the output written to a variable list (`seq 1 40000 > (first . rest)`) in an MSeq and takes it apart that way, which took 4.8 s for 40,000 lines and did not end in 10 minutes for 100,000; it now takes 0.43 s and 1.07 s (the Python VM still copies the rest). The cycle collector sees shared items as a value of their own (`Node::Items` in `gc.rs`), reached from each MSeq that shares them, as it counts the references to the values in them once.

**Copies of Dicts.** `__Dict_copy__` makes a Dict that shares the entries and the index of the one it copies (both are behind an `Rc`), and either of them copies them when it is changed (`DictObj::entries_mut`, `index_mut`, with `Rc::make_mut`), so that a copy that is only read, or changed in a few keys after many reads, does not clone and drop all the values. The cycle collector sees the shared entries as a value of their own (`Node::Entries` in `gc.rs`), reached from each Dict that shares them, so that it counts the references to the values in them once, and a garbage Dict lets go of its entries, which go with the last Dict that shares them. ConSh copies Dicts four times for each of its function calls: the copies took about 2.4% of its time on the transpiled VM (0.7% on the Rust VM) and now take none, but its 15,000 function calls are only about 1% faster, within what runs vary (0.50 to 0.53 s on the transpiled VM; 1.50 s instead of 1.51 s on the Rust VM, the old and new VMs run in turn), probably because ConSh changes most of its copies, which then clone the entries all the same; the benchmarks, which do not copy Dicts, are as fast as before.

**Dicts.** The index of a Dict keeps String keys by their text in a map that is looked up with a borrowed `&str` (`DictIndex`, `index_key`), so that a lookup does not make a String, and both of its maps use an Fx hash instead of SipHash (Dicts do not need protection against keys made to collide).

**Shapes and inline caches (records in transpiled code).** ConMa has no records: a program keeps the fields of an object in a Dict (richards, the contexts of ConSh). Instead of adding records to the language, the VM gives Dicts shapes, and transpiled code caches them (`value.rs`, "Shapes"). A Dict whose keys are all Strings, put in one after another and never removed, has the shape of that sequence of keys (`shape_after`, a tree of shapes kept by the VM): Dicts with the same shape have each key at the same position. A new Dict has the empty shape, `__Dict_copy__` keeps the shape, and a Dict has no shape (`SHAPE_NONE`) once a key is removed or a key that is not a String is put in, and when it would have more than 64 keys or the VM more than 65,536 shapes (Dicts used as tables). Each place in transpiled code that reads or writes a Dict with a String key written in place (`d_dict_lookup_str`, `d_dict_lookup_bool_str`, `d_dict_put_str`) has a cache (`Ic`, a `static` of the generated code) with the last shape and the position of the key it found there; when the Dict has that shape, the key is at that position, without the index (`find_str_cached`). Shapes do not change what a program does: the VM itself does not use them, and the tests of test/ give the same traces. richards 20 takes 0.69 s instead of 0.78 s (its Dict lookups took about 22% of its time, half of it in the index); nbody, fib and the loop, which use few Dicts, and ConSh, whose Dict lookups take about 1% of its time (most of it goes to cloning and dropping values, LVEnv nodes and calls), are not faster.

A call written as `f a ... ,(x ...) ...` (f a variable), and a clause of `__if__` and the others followed by an LCont, is run as a Rust call when f is a Closure of the module with transpiled code and as many operands as parameters: the LCont is not made into a Closure and pushed to the CChain, but stays in the Rust code (`rust_call`), which binds the values the call returns to it; a call without an LCont (a tail call) goes on in place. A Rust call returns when the VProc passes values to the CChain it was called with (null as the Operator, or a continuation whose CChain is that one). Where the VProc must leave transpiled code (a step of the VM, the end of the budget, a continuation made out of the Rust calls), each Rust call puts the CFrame the VM would have pushed into the CChain on the way out, so that the VM goes on with the same CChain; a continuation made in a Rust call around the current one is applied by that one, leaving the ones in between. A continuation made in a Rust call has a CChain without the CFrames of the Rust calls around it; each Rust call records the continuations made in it, and those still in use when it ends get its CFrame then (`ContObj::cchain` can change for that). Rust calls deeper than 256 are made as the VM makes them, and each call counts as a step for the budget. The Boolean Closures are applied in place too. Alone, this gained little (making the LCont Closure and the CFrame was not where the time went), but it lets fused chains (above) call a function and go on with their Rust variables: a call with an LCont in a fused chain is a Rust call (`fused_call`, sharing `frame_run` with `rust_call`), and the chain binds the values it returns; the LVEnv of the LCont is made only if the call is left or a continuation made in it outlives it. A Rust call that is left costs more than a call made as the VM makes it, so the transpiled code counts, for each Function, how often its Rust calls returned values and how often they were left (to the VM, or by an escape); a Function left more than 8 times, and more than a third as often as it returned values, is called as the VM calls it from then on (`Table::rust_ok`). ConSh reaches a step of the VM (reading a LazyList, setting a Ref) through many calls for every command, and its Rust calls made it about 10% slower than without them (15,000 function calls: 1.08 s against 0.98 s); with this rule it takes 1.00 s, while nbody, whose Functions are never left, keeps them (0.52 s, 0.55 s without Rust calls). A Rust call from a fused chain gets its operands in an array instead of a Vec, and the chain binds the values from the OList, which keeps its buffer; with this, ConSh takes 0.98 s, as before Rust calls, and nbody 0.49 s.

Measurements (Apple M4): a loop of 10,000,000 iterations takes 1.99 s instead of 3.76 s; ConSh (with `/tmp/consh.module.se`) is 1.5 to 1.6 times as fast, and its tests pass. The time now goes mostly to the values themselves (cloning and dropping them, LVEnv nodes, Closures, the cycle collector), not to the steps; much of the cycle collector's work for ConSh came from cycles that ConSh made by mistake for every command, which it no longer makes (consh/PLAN-ja.md), so that ConSh with transpiled code now runs a loop of 15,000 function calls in 1.90 s instead of 3.29 s.

## Design

* `sexp.rs` — reading and writing S-expressions. `to_string` writes a list on one line when it fits in 80 characters, as `sexp_to_str` does, so that traces match.
* `module.rs` — loading a module. Every Function and Body is compiled once, when the module is loaded. A global variable that is `Undefined` becomes the primitive of the same name, if there is one.
* `value.rs` — values. They follow the Python classes, including the two forms of a String: a literal of the program keeps its AST node (`StrNode`) and a String made at run time keeps its text (`Str`), which is escaped and quoted only when a trace writes it.
* `step.rs` — one step, as `step` in `vproc_step.py`.
* `vproc.rs` — the state of a VProc. A VProc is held as a `VProcCell`, whose serial number and state are outside the `RefCell` of the rest, so that a primitive can act on its own VProc (suspend it, wait, kill it) while that VProc runs the step.
* `sched.rs` — the scheduler: the ready queue and the VProcs that wait for the OS (a process to exit, a Stream to be readable or writable), for another VProc, for a LazyList or for a Ref to change. `__Ref_wait_change__` waits while the value is the same object, as `is` in Python. Numbers therefore have an identity too: every new Number gets its own id, and ConSh depends on it (it sets a Ref to an equal but new Number to wake the VProcs that wait for it).
* `sys.rs` — the C functions that the standard library does not provide (pipe, dup, poll, signal, kill, sysconf), with the constants of macOS and Linux. The crate has no dependencies.
* `gc.rs` — collecting cycles (see Memory).
* `alloc.rs` — the global allocator: free lists for blocks of up to 256 bytes (see Speed).
* `profile.rs` — step counts for `CONMA_PROFILE` (see Speed).
* `trace.rs` — values and VProcs as S-expressions.
* `prim/` — the primitives: `basic.rs` (`__is_null__`, `__type_name__`), `os.rs`, `number.rs`, `llist.rs`, `cchain.rs` (CChain, CFrame, `__Cont_get__`), `refs.rs` (Ref, PDict), `collections.rs` (MSeq, Dict), `string.rs` (String, `__Sexp_read__`), `vprocs.rs` (VProc, and loading a program with `bin/includer` and `bin/resolver` for `__VProc_spawn__`), `lazy.rs` (LazyList, `__Ref_wait_change__`), `stream.rs` (Streams, files and directories, the environment), `process.rs` (processes and SIGINT). Traces write a primitive by the name of its Python function (`(PrimFunc "prim_OS_print")`).

Memory: values are reference counted (`Rc`). Values without mutable parts cannot form cycles, so cycles can only come through Refs, MSeqs, Dicts, the PDict, VProcs and GVEnvs (a VProc can hold itself, for example in its LVEnv), and ConSh makes such cycles all the time: without collecting them, a loop of `$( )` kept about 40 KB per iteration. `gc.rs` collects them as the cycle collector of Python does, without knowing the roots: every Ref, MSeq, Dict, VProc and GVEnv is registered when it is made, and a collection finds every value they reach, counts the references to each one from inside that graph, and takes a value with more references (`Rc::strong_count`) as reachable from outside (the scheduler, a primitive, any Rust code). The containers that nothing reachable from outside reaches are emptied, which frees the cycles. A reference that the collector does not see only keeps values alive. Collections run between two steps, after as many containers have been made as survived the last one, and at least a quarter as many as the values the last one went through (at least 10000): a collection takes time in proportion to all the values it goes through, and when few containers reach many other values (ConSh taking apart the 100,000 lines written to a variable list, `seq 1 100000 > (first . rest)`, with a CChain of 100,000 CFrames), collecting after every 10,000 containers made the time quadratic (that script took 1.09 s on the transpiled VM, 95% of it collecting, and 400,000 lines 10.7 s with 1.6 GB; now 0.47 s and 1.83 s with 650 MB); `CONMA_GC_THRESHOLD=n` collects after every n containers instead, to test the collector, and `CONMA_GC_STATS=1` prints what each collection freed and kept (the entries that copies of Dicts share are counted as `Entries`). The list of VProcs that a deadlock is reported from keeps only the VProcs that have not finished. Long LLists and LVEnvs are dropped without recursion, and the VM runs in a thread with a large stack, because modules are deeply nested.

OS: as in the Python VM, fds made by the VM are not inherited by child processes, a child gets the Streams given to `__OS_spawn__` as its standard streams, and SIGCHLD (and a SIGINT after `__OS_trap_interrupt__`) writes to a pipe, so that the scheduler sleeps in `poll` until a process exits or a Stream is ready. When VProcs wait for the OS while others run, the OS is checked every 64 steps, as in the Python VM; such traces depend on timing, so they may differ from run to run in either VM.
