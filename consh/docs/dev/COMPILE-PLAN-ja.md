# ConSh のスクリプトを前もって変換して速くする計画

ConMa 版の ConSh（最適化版）が文を実行する手間を、スクリプトを前もって変換して減らす計画である（2026-11-16）。2 段に分け、段階 1 は今のクロージャへの変換を広げ、段階 2（ConMa のコードを作る本当の変換）は段階 1 を測ってから決める。参照版（consh/reference）は変えない（仕様の参照として、最適化版と出力を比べる）。

## 1. 目的と、測ったこと

### 1.1 今の速さ（2026-11-16、Apple M4、consh/bench/README-ja.md）

| スクリプト | Bash | Rust 版の ConSh | 最適化版＋変換した VM | 最適化版＋wasm 版の VM |
|---|---|---|---|---|
| `02` for と代入 10 万回 | 0.097 秒 | 0.068 秒 | 0.43 秒 | 0.96 秒 |
| `13` 関数の呼び出し 10 万回 | 32.9 秒（fork） | 0.26 秒 | 3.2 秒 | 7.5 秒 |

関数の呼び出し 1 回（`13`）に、Rust 版の VM で約 2,000 ステップかかる。

### 1.2 今もしている変換

最適化版は、文を初めて実行するときに、文脈 `sh` を受け取って実行するクロージャ（文のコード）に変換し、節ごとに覚えて使い回す（consh/include/consh_eval.se の `Stmt_compile`、`Lines_compile`、`Assign_compile`、`Cmd_compile`）。文の種類の振り分け、代入の右辺、単純文の先頭の語がリテラルのときのコマンドの名前と組み込みコマンドの決定は、変換のときに 1 回だけする。

まだ変換していないもの：`if`、`for`、パイプ、`return`、`shift`、`(( ))` などは、文のコードが実行のたびに `Eval_if` などを呼んで、節を読む。語の展開（`Eval_args`、`Var_fields`、`Expand_*`）も、実行のたびに語の節を読む。関数は後から定義できるので、名前で関数を探すこと（`Func_lookup`）は実行のたびにする。外部コマンドの引数の長さの上限（`Arg_limit_new`、`Arg_max`）は、関数や組み込みコマンドを呼ぶときにも作る。

### 1.3 ステップの内訳（Rust 版の VM の `CONMA_PROFILE`、関数を分類）

| スクリプト | 節を読む | 実行のたびに決めている | 語の展開と値 | 関数の呼び出しと文脈 | LazyList とループ | コマンドの実行 | ほか |
|---|---|---|---|---|---|---|---|
| `02` for と代入 | 0% | 25% | 7% | 5% | 53% | 4% | 6% |
| `13` 関数の呼び出し | 2% | 22% | 9% | 31% | 9% | 12% | 16% |
| `06` 関数と echo | 5% | 14% | 23% | 15% | 11% | 15% | 18% |
| `14` 入れ子の for と if | 15% | 11% | 12% | 24% | 2% | 12% | 25% |

* 節を読む：`Node_split`、`Part_split`、`List_first`、`Parts_count_from`、`If_parts` など。
* 実行のたびに決めている：`Func_lookup`、`Arg_max`、`Arg_limit_new`、`Target_split`、`Subst_settle*`。このうち `Subst_settle*`（文の終わりに `$( )` を待つ）は、外側の文の `$( )`（`for` の `$(seq ...)` など）も待つので、前もっては消せない。前もって決められるのは、関数を探すこと（関数の定義が変わらないかぎり）と、関数と組み込みコマンドの引数の長さの上限。
* 関数の呼び出しと文脈：`Func_call`、`Func_bind`、`Capture_*`（`> (n)`）、`Eval_redirs*`、文脈の Dict の写し。LazyList とループ：`$( )` の値の LazyList、`For_*`。これらは ConSh の意味（変数を Dict で持つ、値が遅延の列、出力を受け取る仕組み）から来ていて、表し方を変えないかぎり、変換しても減らない。

### 1.4 見込み

* **段階 1**（今の変換を広げる）：節を読む手間（0〜15%）と、前もって決められる分（数〜10%）が減る。1.2〜1.4 倍の見込み。どの VM でも効き、ConSh の関数は変換した VM の Rust のコードのまま動く。
* **段階 2**（ConMa のコードを作る）：変数を Dict でなく決まった場所に置く、値の遅延をやめられる所ではやめる、など表し方まで変えれば、関数の呼び出しと文脈、LazyList の分も減らせる。ただし：ConSh の意味（動的な関数の定義、`$( )` の並行、変数リスト、継続）を保つ解析が要る。実行時に作ったモジュールは、変換した VM では Rust のコードにならず、解釈して動くので、変換した VM ではかえって遅くなるおそれがある（ConSh の `(( ))` の SJS と同じ）。前もってモジュールにする形（`consh compile`）なら、bench/build.sh で変換した VM に入れられる。

## 2. 方針

* **段階 1 から作る**：今の文のコードの作り方（文脈を受け取るクロージャ）を、`if`、`for`、パイプ、語の展開に広げる。見える動きは変えない（consh/test が、最適化版と参照版の両方で通ること）。
* **関数を探した結果を覚える**：関数の定義の表に版の番号を持たせ、定義や削除のたびに進める。文のコードは、覚えた版と同じなら、前に探した関数を使う。
* **関数と組み込みコマンドの呼び出しでは、外部コマンドの引数の長さの上限を作らない**。
* **段階 2 は、段階 1 を測ってから決める**。

## 3. 決めたこと（2026-11-16、ユーザーと）

1. **段階 1 から作り、段階 2 は段階 1 の後で決める**。
2. **対象は最適化版だけ**。参照版は今のまま（変換しない、読みやすい形）にし、最適化版と出力を比べる相手にする。
3. **関数を探した結果は、定義の表の版の番号で覚える**。定義や削除のたびに版を進め、文のコードは、覚えた版と同じなら前に探した関数を使う。関数の見え方（字句のスコープ）を変えないことは、consh/test で確かめる。

## 4. 作り方（段階 1）

| 段階 | 内容 | 確かめ方 |
|---|---|---|
| P0 | 測る台：consh/bench の `02`、`06`、`13`、`14`、`18` のステップと時間を、Rust 版、変換した、wasm 版の VM で記録する（1.1、1.3 の表を正式にする） | 表にする |
| P1 | 関数と組み込みコマンドの呼び出しで、引数の長さの上限を作らない（`Eval_cmd_parts`） | consh/test を最適化版と参照版で。ARG_MAX のテスト（外部コマンド）が通ること |
| P2 | 関数を探した結果を、定義の表の版の番号で覚える | consh/test。関数を後から定義する、定義し直す、関数の中で定義するスクリプトを足す |
| P3 | `if` と `for` の文のコード（条件、本体、語を前もって変換する） | consh/test |
| P4 | 語の展開のコード（語の種類の振り分けを前もってする） | consh/test。consh/test の expand1 |
| P5 | パイプ、`return`、`shift` など残りの文 | consh/test |
| P6 | 測って書く。段階 2 を決める | 表にする |

各段階で、consh/test を最適化版と参照版の両方で、Rust 版の VM で流す。変換した VM と wasm 版の VM は、P6 の前に流す。

## 5. 今の状態

計画を書き、3 を決めた（2026-11-16）。

* **P0（測った、2026-11-16、97740fa、Apple M4）**：最適化版。ステップは Rust 版の VM の `CONMA_PROFILE`、時間は consh/bench/run.py（user + sys、3 回の最小）。

| スクリプト | ステップ | Rust 版の VM | 変換した VM | wasm 版の VM |
|---|---|---|---|---|
| `02_for_seq_100000` | 33,171,438 | 0.759 秒 | 0.411 秒 | 0.941 秒 |
| `06_func_echo` | 4,760,307 | 0.135 秒 | 0.105 秒 | 0.346 秒 |
| `13_func_assign_100000` | 200,338,767 | 6.014 秒 | 3.068 秒 | 7.352 秒 |
| `14_nested_for_if` | 271,851,469 | 7.158 秒 | 3.291 秒 | 10.243 秒 |
| `18_pipe_funcs` | 103,036,180 | 3.103 秒 | 1.976 秒 | 4.168 秒 |

表の名前は測ったときのもの：`02_for_seq_100000`（2026-11-17 に 02_for_seq へ名前を変更）、`13_func_assign_100000`（2026-11-17 に 13_func_assign へ名前を変更）。

* **P1（作った、2026-11-16）**：先頭の語が決まっている単純文では、引数のバイト数の上限（`Arg_limit_new` の Dict と 2 つのクロージャ）を、コマンドを決めた後、外部コマンドのときだけ作る（`Arg_limit_from` に分けた）。ARG_MAX の値の確かめ（`Arg_max`）は、今までどおりどのコマンドでもする（無効な ARG_MAX は、関数でも組み込みコマンドでもエラー。Rust 版と参照版も同じ）。減ったのは小さい：`13` が 2 億 34 万から 1 億 9,954 万ステップ（−0.4%）、`06` が 476 万から 474 万。残る `Arg_max`（1 回 21 ステップ）は、環境変数を引いて値を確かめる。consh/test は最適化版と参照版の Rust 版の VM で違いなく通る。
* **P2（見送った、2026-11-16）**：`Func_lookup` はステップの 3〜4.5% で、覚えても 2% 前後しか減らない。版の番号だけで覚えると、同じ文のコードが別のスコープの並びで実行されるとき（関数の中で関数を定義し、そこで作った関数値を後で呼ぶなど）、別のスコープの関数を返す例が作れる。正しくするには、スコープごとの番号を比べることになり、手間と危うさに見合わない。
* **段階 1 の見直し（2026-11-16）**：P3 の前に `14` を数え直すと、`if` を前もって変換して減るのは 3〜4%（`If_parts` の 2.4% と、節を読む一部）。`for` の繰り返しごとの手間は、ループ変数と continue の継続を作る意味の側。語の展開（P4）も数 %。段階 1 全体で 1 割前後の見込みで、1.4 の 1.2〜1.4 倍には届かない。一方、変換と関係なく 1 回の手間が大きい関数がある（`13`：`Capture_new` 102 ステップで 5.1%、`Func_call` 81 ステップで 4.0%、`Eval_redirs_from` 41 ステップで 4.1%、`Subst_settle*` 合わせて約 10%）。続けるかどうか、これらの関数を軽くすることに移るかを、ユーザーと決める。
* **重い関数を軽くする（2026-11-16、ユーザーと決めた。ブランチ m4/consh-heavy）**：段階 1 の P3 以降は止め、変換と関係なく 1 回の手間が大きい関数を、最適化版だけで、動きを変えずに軽くする。
  * `Subst_settle`：文の終わりのたびに、外側の `$(seq ...)` のように値の先頭がそろった（`"full"`）OS のパイプの `$( )` の記録をたどり直していた（`13` で 1 文 約 80 ステップ）。残ったものがどれも `"full"` なら global の `"substsParked"` に覚え、次からは状態が `"done"` になったものがないかだけを見る（新しい `$( )` を起動したら覚えを消す）。`"full"` の記録は、`"done"` にならないかぎり `"blocked"` として残るので、結果は同じ。
  * `Func_call`：変数リストの名前と rest の名前、本体の文を、呼ぶたびに節から取り出していた。`Func_make` で 1 回だけ取り出して関数の Dict に置き（`"names"`、`"restName"`、`"lines"`）、引数の数は、渡しながら調べ、合わないと分かった所で `Arity_check` のエラーにする（`Func_bind_args`。渡した先は、エラーなら使われない局所変数の写し）。
  * ステップ（Rust 版の VM の `CONMA_PROFILE`、P1 の後から）：`02` 33,171,524 → 29,717,888（−10.4%）、`06` 4,736,320 → 4,514,370（−4.7%）、`13` 199,538,776 → 181,778,556（−8.9%）、`14` 270,771,486 → 262,671,667（−3.0%）、`18` 102,636,170 → 102,825,739（+0.2%。`$(stdin)` のチャネルの記録で、`"full"` かを見る分）。
  * 時間（Apple M4、consh/bench/run.py、3 回の最小）：Rust 版の VM で `02` 0.686 秒、`06` 0.133 秒、`13` 5.703 秒、`14` 7.027 秒、`18` 3.153 秒、wasm 版の VM で 0.958、0.341、7.167、10.032、4.315 秒。P0 の表と比べると、Rust 版の VM の `02` が −10%、`13` が −5%、ほかは揺れの中。変換した VM は、P1 からモジュールが変わって古いので、測っていない（`bench/build.sh` で作り直す）。
  * 残りの内訳（`13`、1 回の繰り返し約 1,800 ステップ）：`Eval_cmd_parts` 8.7%（1 回 80）、`Capture_new` 5.6%（102）、`Eval_redirs_from` 4.5%、`Subst_settle` と `Substs_none_done` 合わせて 7.9%、`Func_lookup` 3.9%、`Cmd_run_resolved` 3.8%。1 つで 1 割を超えるものはなく、1〜3% ずつの手当てが続く。
