# SJS の配列を使う数の関数を WebAssembly にする計画

consh/SJS-WASM-PLAN-ja.md（以下「前の計画」）の続きで、その 9 節（数の配列）を作る計画である。前の計画の段階 1〜5 で、数だけを扱う関数は WebAssembly（以下 wasm）で動くようになったが、配列を使う関数は、今も ConMa 版で動く。nbody（consh/sjs/bench/nbody.sjs）は、そのために速くならない。2026-11-14 に書いた。

**状態**：案。まだ何も作っていない。2026-11-14 に、8 の決めることをすべて決めた（方式は案 A、プリミティブは高速版 ConMa だけに新しく足す、メモリの命令は手で書いた WAT にも開く、写す大きさの上限は設けない、値を返さない関数と定数の式は先に入れる）。段階 A0〜A5 を作った（2026-11-14。10〜15）。計画した段階はすべて済んだ。

## 1. 目的と、今の様子

* nbody 2000 は、Rust 版の VM の SJS で 1.08 秒、wasm 版の VM で 1.66 秒、手で書いた ConMa（Rust 版の VM）で 0.092 秒、CPython で 0.026 秒（Apple M1。前の計画の 16）。
* nbody の時間のほとんどは `advance` で、`advance` は、体の配列（`bodies`、7 つの数の配列が 5 つ）と、組の配列（`pairs`、体の配列 2 つの配列が 10 個）を受け取り、数を読み書きするだけである。`energy` も同じ形で、`offsetMomentum` は値を返さない。
* 配列を使う数の関数を wasm にできれば、loop や fib と同じく、時間のほとんどが VM の起動になる見込みである。

## 2. SJS の配列の今の表し方

* 配列は Dict で、`"t"` が `"array"`、`"id"` が番号、`"items"` が添字の文字列（`"0"`、`"1"`、…）から値への Dict、`"length"` が長さの Ref である（consh/include/sjs_rt.se の「配列」）。穴（`[1, , 2]`）があれば `"holes"`、タグ付きテンプレートの配列は `"frozen"` を持つ。
* 要素は SJS の値なら何でもよく、型は混ざってよい。添字の読み書き（`Sjs_get_index`、`Sjs_set_index`）、長さ、配列のメソッド（`Sjs_array_method`）、`for...of`、分割代入など、sjs_rt.se の 19 か所以上が、この形を直接読む。
* ConMa には配列の値がない（前の計画を作る前から）。

## 3. 方式

### 3.1. 案 A：呼ぶときに写す（2026-11-14 に、これにすると決めた）

wasm 版を呼ぶとき、引数の配列を wasm のモジュールのメモリに写し、wasm 版が終わったら、書き換えた数を元の配列に書き戻す。

* **メモリの形**：モジュールが自分のメモリ（`(memory ...)`）を持ち、export する。メモリを f64 の列として使い、配列 1 つを「長さ、要素 0、要素 1、…」の連続した語に置く。配列の要素が配列なら、その配列の先頭の語の番号を f64 で入れる（整数なので、2^53 までちょうど表せる）。引数の配列も、先頭の語の番号として渡す。
* **形の確かめ**：wasm 版は、引数の形を変換のときに決める（9 の例では、`bodies` は「数の配列の配列」、`pairs` は「数の配列の配列の配列」）。写すとき、配列がその形で、穴がなく、葉がすべて数であることを確かめ、違えば ConMa 版で動かす（前の計画の 5.2 と同じ考え方）。
* **別名を保つ**：同じ配列（同じ `"id"`）は 1 回だけ写し、同じ番号で参照する。nbody の `pairs` の要素は `bodies` の要素そのものなので、wasm の中でも同じ場所を読み書きする。
* **書き戻す**：結果が `"ok"` なら、数の配列の要素を、元の配列の `"items"` に書き戻す。`"fuel"` と `"trap"` では書き戻さず、写しを捨てる。だから、配列を書き換える関数でも、前の計画の「やり直せる」（2）が成り立つ。やり直すたびに写し直すので、やり直しの合間にほかの VProc が配列を書き換えても、最後の 1 回を、その時点で一度に動かしたのと同じ結果になる。
* **wasm 版の中でできないこと**：配列を作る、長さを変える（`push`、長さより後への代入）、配列の要素に配列を入れる。範囲の外の読み書きと、整数でない添字は、trap にして ConMa 版で動かす（JavaScript では、読むと `undefined`、書くと配列が延びるので、ConMa 版に任せる）。
* **費用**：呼ぶたびに、引数の配列の大きさに比例して写す。nbody の `advance` は 1 回だけ（中で 2000 回回る）呼ばれ、配列は語 50 個ほどなので、無視できる。大きな配列を受け取る小さな関数を何度も呼ぶプログラムでは、写す費用が勝って、ConMa 版より遅くなることがある。
* **ConMa の言語**：ConMa の値は変えない。VM には、メモリに写して呼び、メモリを返すプリミティブが要る（4）。

### 3.2. 案 B：数の配列という値を足す

VM に、f64 の列を持つ新しい値（数の配列）を足し、SJS の配列のうち要素がすべて数のものを、その値で表す。wasm のモジュールとは、数の配列だけを置く `WebAssembly.Memory` を共有し、写さずに読み書きする。

* 写す費用がない。ConMa 版も、Dict でなく f64 の列を読むので速くなる。
* ただし、SJS の配列の 19 か所以上と配列のメソッドを、2 つの表し方の両方に対応させ、数でない値を入れたときに Dict に戻す（V8 の elements kind の移り変わりと同じ）仕組みが要る。nbody の `pairs` のような「配列の配列」は数の配列でないので、別に参照の配列も要る。
* VM には、新しい値、そのプリミティブ（作る、読む、書く、長さ、延ばす）、GC、共有するメモリの割り当て（VM の Rust のヒープの外）、ネイティブ、変換版、Python の VM での動きが要る。高速版 ConMa の新しい機能になる。
* 共有するメモリを、配列を受け取らない wasm のモジュールからも読めないようにする（安全性）必要がある。

案 A のほうがずっと小さく、nbody は案 A で足りる見込みなので、案 A から作ることを勧める。案 B は、案 A で写す費用が問題になるプログラムが出てきたら考える。

### 3.3. 案 C：配列を写さず、wasm 版の中で作る配列だけを扱う

数の関数の中で作り、外に出さない配列だけを、wasm のメモリに置く。引数の配列は扱わないので、nbody は速くならない。案 A の後で、案 A に足すことはできる。

## 4. 案 A の仕組み

### 4.1. アセンブラとプリミティブ（高速版 ConMa、機能 `"wasm"` を広げる）

* アセンブラ（vm/src/prim/wasm_asm.rs）が受け付ける部分集合に（手で書いた WAT も使える。8 の 3）、モジュール自身のメモリ（`(memory $m? 初めのページ数)`。import はしない）と、`f64.load`、`f64.store`、`memory.size`、`memory.grow`（i32 の添字と `offset=`、`align=`）を足す。メモリは `__memory` の名前で export する（`__fuel` と同じく予約する）。import、テーブル、大域の変数は、今までどおり受け付けない。
* メモリを持つモジュールの関数は、引数だけでなくメモリにもよるが、`__Wasm_call__` で呼ぶとき、呼ぶ前にメモリを 0 で埋めることにすれば、今までどおり「同じ引数なら同じ結果」になる（ホストが埋める）。
* **新しいプリミティブ**（高速版 ConMa だけ。簡潔版 ConMa には足さない。8 の 2）`__Wasm_call_memory__ onError module name args memory fuel ,(status value memory)`：`memory`（Number の LList。f64 の語）をメモリの先頭に書いてから呼び、`"ok"` なら、終わった後のメモリの同じ長さの語を LList で返す。メモリが足りなければ、ホストが `memory.grow` で広げる。ネイティブの VM は、`__Wasm_call__` と同じく onError に進む。Python の VM は、bin/concise が入れる include/ref/wasm.se の代わりの定義（`__Wasm_call_memory__` も足す）で onError に進む。
* docs/PRIMITIVES.md の 16 節を直す。

### 4.2. 実行時の支え（sjs_rt.se）

* **写す**：`Sjs_wasm_pack shapes args ,(ok words params)`：引数を、変換器が決めた形（数、数の配列、配列の配列、…）と照らしながら、配列を `"id"` ごとに 1 回ずつ、語の列に置く。形が違う、穴がある、葉が数でない、凍った配列なら、偽。
* **書き戻す**：`Sjs_wasm_unpack words`：写した数の配列ごとに、要素の語を `"items"` に入れる（変わったものだけでもよい）。
* `Sjs_wasm_fn` は、配列の引数があるときだけ、`__Wasm_call__` の代わりに `__Wasm_call_memory__` を使う。燃料のやり直しは、やり直すたびに写し直す。

### 4.3. 変換器（sjs_wasm.se）

* **型**：局所の変数と引数の型を、数（f64）に加えて、配列（深さ k の、葉が数の配列。wasm では、配列の先頭の語の番号を f64 で持つ）にする。引数の型は、関数の中での使い方から決める（`b[X]` を算術に使えば数の配列、`pairs` の要素を `[b1, b2]` で分ければ配列の配列、など）。決まらないか、使い方が食い違えば、数の関数にしない。
* **式と文**：`a[i]`（i は数。範囲と整数を確かめ、違えば trap）、`a.length`、`a[i] = 数` と複合の代入（数の配列だけ）、`const b = a[i]`（配列の配列から配列を取り出す）、`for (const x of a)` と `for (const [x, y] of a)`（添字のループにする。分ける要素が足りなければ trap）。
* **値を返さない関数**：最後まで来るか、値のない `return` で終わる関数も、数の関数にする（nbody の `offsetMomentum`）。wasm 版は 0 を返し、`Sjs_wasm_fn` が `undefined` にする。ConMa 版が値を返すかどうかは、変換のときに決まる。
* **定数の式**：一番外の `const` は、数のリテラルに加えて、それまでの数の定数と数のリテラルの算術（`const SOLAR_MASS = 4 * PI * PI`）も、数の定数にする。WAT では、同じ順の算術を、使う所に書く（ConMa 版と同じ丸めになる）。

## 5. 安全性

* モジュールのメモリは、そのモジュールだけのもので、VM のメモリやほかのモジュールとは共有しない。import は今までどおり 1 つもない。
* 範囲の外の `f64.load` と `f64.store` は、wasm の中で trap になる（メモリの外には出られない）。添字の確かめは、配列の長さに対するもので、メモリの範囲とは別に、変換器が入れる。
* 手で書いた WAT も、メモリと読み書きの命令を使えるようになるが、触れられるのは、自分のメモリと、ホストが写した語だけである。

## 8. 決めること

1. **方式**：案 A（呼ぶときに写す）にする（2026-11-14 に決めた）。案 B は、案 A で写す費用が問題になるプログラムが出てきたら考える。
2. **プリミティブ**：`__Wasm_call_memory__` を新しく足す。高速版 ConMa（機能 `"wasm"`）には足すが、簡潔版 ConMa には足さない（2026-11-14 に決めた）。簡潔版の VM（Python）では、`__Wasm_call__` と同じく、include/ref/wasm.se の代わりの定義が onError に進む。`__Wasm_call__` は変えない。
3. **メモリを手で書いた WAT にも開く**（2026-11-14 に決めた）：`(memory ...)` と読み書きの命令は、アセンブラの部分集合に入れるので、ConMa のプログラムが手で書く WAT でも使える。触れられるのは、そのモジュール自身のメモリと、ホストが写した語だけである（5）。
4. **写す大きさの上限は設けない**（2026-11-14 に決めた）。段階 A5 で、写す費用を測ってから考え直す。
5. **値を返さない関数と定数の式は、配列より先に入れる**（2026-11-14 に決めた）：段階 A0 として作る（7）。配列がなくても、数の関数が増える。

## 9. 例：nbody の `advance` の形

```
function advance(bodies, pairs, dt, n) {      // bodies：数の配列の配列、pairs：数の配列の配列の配列、dt、n：数
  for (let k = 0; k < n; k++) {
    for (const [b1, b2] of pairs) {           // pairs の要素を 2 つの数の配列に分ける
      const dx = b1[X] - b2[X]                // X は一番外の数の定数
      ...
      b1[VX] -= dx * m2mag                    // 数の配列の要素への複合の代入
    }
    for (const b of bodies) {
      b[X] += dt * b[VX]
    }
  }
}                                             // 値を返さない
```

写すと、体の配列 5 つ（語 8 個ずつ）、組の配列 10 個（語 3 個ずつ）、`bodies`（語 6 個）、`pairs`（語 11 個）の、語 87 個になる。`pairs` の組の要素は体の配列の先頭の語の番号なので、`b1[VX] -= ...` は `bodies` の中の同じ体を書き換える。

## 10. 段階 A0 の結果（2026-11-14）

* **定数の式**：一番外の `const` のうち、最初の呼び出しのある文より前のもので、数のリテラル、それまでの数の定数、括弧、単項の `-` と `+`、`+ - * / %` からできた式を、数の定数にする（sjs_wasm.se の `Wx_const_expr`）。WAT では、使う所に同じ順の算術を書く（`%` は `$__mod`）。`const SOLAR_MASS = 4 * PI * PI` も数の定数になる。
* **値を返さない関数**：本体に値のある `return` がなく、値のない `return` か最後まで来て終わる関数も、数の関数にする（`Wx_returns` で数える）。wasm 版は 0 を返し、`Sjs_wasm_fn` と `Sjs_wasm_fn_checked` の新しい引数 `void` が真なら、`undefined` を返す。値のある `return` とない `return` が混ざる関数は、数の関数にしない（JavaScript では、道によって `undefined` を返すため）。値を返さない数の関数の呼び出しは型 `"V"` で、式の文としてだけ数の関数の中に書ける（値を使えば、数の関数にしない）。
* **確かめたこと**：consh/sjs/test/step9 の case3（定数の式 5 つ、値を返さない関数、それを文として呼ぶ関数、数の関数にならない 3 つ）を、Node.js の結果と、Rust 版の VM と wasm 版の VM で比べた。step9 の case1、case2 と、consh/test/step21 も、両方の VM で通る。
* nbody の `offsetMomentum` は、まだ配列を使うので数の関数にならない（段階 A3 から）。

## 11. 段階 A1 の結果（2026-11-14。ブランチ alpha）

* **アセンブラ**（vm/src/prim/wasm_asm.rs）：`(memory $m? 最小 最大?)`（ページの数。import と export は書けない）を 1 つまで受け付け、`__memory` の名前で export する（予約した名前）。命令に `f64.load` と `f64.store`（`offset=` と、1、2、4、8 バイトの `align=`。既定は 8）、`memory.size`、`memory.grow` を足した。手で書いた WAT でも使える（8 の 3）。
* **プリミティブ**：`__Wasm_call_memory__ onError module name args memory fuel ,(status value memory)`（vm/src/prim/wasm.rs。`__Wasm_call__` と、引数を確かめて呼ぶ所を共有する）。高速版 ConMa だけで、include/ref/wasm.se の代わりの定義は onError に進む（8 の 2）。フロントエンドが `(Uses "wasm")` を書く名前にも足した。
* **ホスト**（consh/js/conma.js の `host_wasm_call`）：メモリのあるモジュールなら、呼ぶたびに 0 で埋めてから語を書き（入らなければ広げる）、`"ok"` なら同じ数の語を VM に写し戻す。`__Wasm_call__` でも 0 で埋める。import の形を、`host_wasm_call(id, 名前, 引数, 語, 語の数, 燃料, 結果)` に変えた。
* **計画と違うこと**：メモリの大きさは、呼び出しが広げると、次の呼び出しにも残る（0 で埋めるのは中身だけ）。`memory.size` を使う関数は、それより前の呼び出しによって結果が変わりうる。SJS の変換器は `memory.size` を出さないので、数の関数には関わらない。docs/PRIMITIVES.md の 16 節に書いた。
* **確かめたこと**：test/fast7 の case8（読む、書く、0 で埋めること、`-0`、`offset=`、語のない呼び出し、1 ページより多い 1 万語、`memory.size` と `memory.grow`、メモリの外の trap、誤った引数、メモリのないモジュール、受け付けない形 7 つ）が、wasm 版の VM、ネイティブの VM、Python の VM で通る。case5 のログは、`(module (memory 1))` を受け付け、メモリのない `f64.load` をホストが拒むように変わった。

## 12. 段階 A2 の結果（2026-11-14。ブランチ alpha）

* **引数の形**：`Sjs_wasm_fn` と `Sjs_wasm_fn_checked` は、引数の数の代わりに、引数ごとの深さ（0 は数、1 は数の配列、2 は数の配列の配列、…）を空白で区切った文字列を受け取る（`Sjs_wasm_depths`）。変換器（sjs_wasm.se）は、fn の節の `"wasmShapes"` に入れる。段階 A3 までは、どれも 0。
* **写す**（`Sjs_wasm_pack`）：深さに従い、子の配列を先に、配列 1 つを「長さ、要素…」の語に置く。要素が配列なら、その先頭の語の番号を入れる。同じ配列（`"id"`）は 1 回だけ置くので、別名が保たれる。配列でない、凍っている、要素がない（穴）、数の配列の要素が数でない、形が深すぎるか浅すぎる、引数が足りない場合は写さず、ConMa 版で動かす。
* **呼ぶ**（`Sjs_wasm_run_memory`）：配列の引数があれば `__Wasm_call_memory__` で呼ぶ。燃料が切れれば、燃料を 2 倍にして写し直してやり直す（その間にほかの VProc が配列を変えても、最後の 1 回をその時点で一度に動かしたのと同じになる）。
* **書き戻す**（`Sjs_wasm_unpack`）：`"ok"` なら、数の配列ごとに、その要素の語を `"items"` に入れる（長さは変わらない）。`"fuel"` と `"trap"` では書き戻さない。
* **確かめたこと**：consh/sjs/test/step11 の case1（ConMa で書いたプログラムが、手で書いた WAT のモジュールと、"[ConMa]" を出す ConMa 版を Sjs_wasm_fn で包んで呼ぶ）で、読む、書く（値を返さない関数）、同じ配列を 2 回入れた配列（別名）、10 万要素の配列（燃料のやり直しで写し直す）、メモリの外の trap（書き戻さない）、写さない 6 つの場合、`-0` の要素を、Rust 版の VM（ConMa 版）と wasm 版の VM（wasm 版）で比べ、配列の結果が同じになった（違うのは "[ConMa]" の印だけ）。

## 13. 段階 A3 の結果（2026-11-14。ブランチ alpha）

* **深さの推論**（sjs_wasm.se の `Wy_infer_all`）：数の関数の候補すべての本体から、引数と局所の変数の深さの等式（`深さ(a) = 深さ(b) + k`）を集めて解く。算術と比較の被演算子、添字、戻り値は深さ 0、`a[i]` は a より 1 浅く、`for (const x of a)` の x は a より 1 浅く、`for (const [x, y] of a)` と `const [x, y] = a` の x と y は 2 浅く、`a.length` の a は 1 以上、数の関数の呼び出しの引数は呼ばれる関数の引数と同じ深さ。決まらないものは、等式の右辺を 0 以上で最も浅くする。食い違えば、その関数を数の関数にしない（`"conflict"`）。引数の深さは、包む関数に渡す形（`"wasmShapes"`）にもなる。
* **WAT**：局所の変数の型を、数（`"N"`）か深さ d の配列（`"A" と d`）にした（配列は先頭の語の番号を f64 で持つ）。`a[i]` は `$__get`、数の配列の要素への代入と複合の代入と `++`、`--` は `$__set`、`a.length` は `$__len`。`$__get` と `$__set` は、添字が整数で 0 以上、長さより小さいことを確かめ、違えば trap にする（ConMa 版が、JavaScript と同じく `undefined` を読むか、配列を延ばす）。`for...of` は添字のループにし、分割代入は要素の 0、1、… 番目を `$__get` で読む。数の関数の呼び出しの引数は、呼ばれる関数の引数と同じ型でなければならない。配列を使う関数があるときだけ、モジュールにメモリ（1 ページ）と配列の補助の関数を入れる。配列の真偽、配列の比較、配列を返すこと、配列を作ること、長さを変えることは、数の関数にしない。
* **SJS_WASM_STRICT**：環境変数 `SJS_WASM_STRICT` があれば、`Sjs_wasm_module` が、モジュールを作れなかった理由（WebAssembly がない場合を除く）を標準エラーに出す。作れないと ConMa 版で動いて出力が変わらないので、変換器の作った WAT の誤り（作っている間に、`for...of` の閉じ括弧が足りないことがあった）を、テストで見つけるため。consh/sjs/test の step9 と step10 は、wasm 版の VM でこれを付けて流す。
* **確かめたこと**：
    * consh/sjs/test/step9 の case4（配列を読む、書く、長さ、`for...of` と分割代入、配列の配列、別名、配列を渡す数の関数どうしの呼び出し、長さより後への代入、数でない要素、深さの違う配列、`-0` の要素。15 の関数が数の関数になる）と case5（nbody の N を 100 にしたもの。`offsetMomentum`、`energy`、`advance` が数の関数になる）を、Node.js の結果と、Rust 版の VM と wasm 版の VM で比べた。
    * nbody 2000 は、wasm 版の VM で 0.20 秒になった（ConMa 版だけなら 1.62 秒、Rust 版の VM の SJS は 1.08 秒。1 回ずつ。Apple M1）。測り直しは段階 A5。

## 16. 写す費用の改善（2026-11-14。ブランチ alpha）

15 の写す費用を減らした。

* **書き戻しを省く**：変換器が、数の関数が配列に書くか（自分か、たどって呼ぶ数の関数が `$__set` を使うか。sjs_wasm.se の `Wx_mark_writes`）を fn の節の `"wasmWrites"` に付け、`Sjs_wasm_fn` と `Sjs_wasm_fn_checked` の新しい引数 `writes` に渡す。書かない関数は、`"ok"` の後に `Sjs_wasm_unpack` を呼ばない。
* **数の配列を 1 回で写す**：`Sjs_wasm_pack_array` は、数の配列の長さと要素を、語の列（逆順）に直接積む（`Sjs_wasm_numbers_onto`）。前は、要素を逆順の LList に集め、逆にして、語の列に積んでいた。
* **測った結果**（15 と同じプログラム。読む関数は配列を合計し、書く関数は要素に 1 を掛ける。時間は 3 回の最良）：

| n、k | 読む：wasm 版（15 のとき） | 読む：ConMa 版だけ | 書く：wasm 版 | 書く：ConMa 版だけ |
|---|---|---|---|---|
| 3、100000 | 3.051 秒（4.359 秒） | 4.174 秒 | 4.128 秒 | 7.215 秒 |
| 1000、1000 | 2.362 秒（4.563 秒） | 4.691 秒 | 3.672 秒 | 15.8 秒 |
| 100000、10 | 12.084 秒（16.949 秒） | 8.197 秒 | 15.544 秒 | 19.109 秒 |

* 小さい配列と中くらいの配列では、wasm 版が ConMa 版より速くなった。書く関数は、どの大きさでも ConMa 版より速い。大きな配列を読むだけの関数を何度も呼ぶと、まだ ConMa 版の 1.5 倍かかる。残りは、要素ごとにキーの文字列を作り、`"items"` を引き、数か確かめて積むのを ConMa で行う費用と、語の LList を逆にし、VM とホストの間で写す費用である。これをさらに減らすには、写す処理（Dict の `"0"`、`"1"`、… の値を語の列に積む）を VM のプリミティブにすることになる（新しいプリミティブを足すかは、決めること）。
