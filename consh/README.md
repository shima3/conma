# ConSh

ConSh は ConMa 言語で動作するシェルである。仕様と設計は [PLAN-ja.md](PLAN-ja.md) にある。

## 構成

```
consh/
├── PLAN-ja.md           仕様と設計
├── AST.md               consh_parse が出力する構文木の形式（英語）
├── bin/
│   ├── consh            ConSh を起動する（consh_parse --pos か consh_parser.se で構文木を作り、ConMa 版に渡す）
│   └── consh_parse      Python の参照実装：構文解析と語の展開の結果をテキストで出す
├── include/
│   ├── consh_main.se    main：ConSh の入口
│   ├── consh_ast.se     consh_parse の構文木の読み込み（__Sexp_read__ と、ConMa で読む Sexp_read）と書き戻し
│   ├── consh_parser.se  構文解析（consh --conma-parser で使う。consh_parse と同じ構文木を作る）
│   ├── consh_glob.se    glob
│   ├── consh_repl.se    対話モード
│   ├── consh_util.se    LList、LazyList、Dict の補助関数
│   ├── consh_expand.se  語の展開
│   └── consh_eval.se    文の実行
└── test/
    ├── run_all.sh       すべての test.sh を実行する
    ├── common.sh        各 test.sh が共通に使うパスと関数
    ├── parse1/          文法のテスト：caseN.sh を consh_parse に渡し、caseN.log と比べる
    ├── parse2/          構文木の位置のテスト：consh_parse --pos に渡す
    ├── parse3/          ConMa 版の構文解析のテスト：parse1 と parse2 の各スクリプトで、consh_parse --pos と同じ構文木とエラーになるか
    ├── expand1/         語の展開のテスト：consh_parse --expand に渡す。caseN.args の各行が引数になる
    └── stepN/           ConMa 版のテスト：test.sh, caseN.log。step1 は構文木の読み込み、step2 は単純な文、step3 は関数など、step4 はコマンド置換、step5 はパイプ、step6 は変数リストへのリダイレクトと stdin、step7 は & と wait、kill、step8 は外部コマンドの出力を直接つなぐ、step9 は ARG_MAX、step10 は関数の中の外部コマンドの出力、step11 は glob、step12 は対話モードと exit、step13 は中断や kill で止めたときの後始末（開いたファイルを閉じ、起動した VProc を止める）
```

* ConSh のために ConMa に足すプリミティブやライブラリは、`consh/` ではなく、リポジトリのルートの `docs/`、`include/`、`test/` に置く。
* `include/` のファイルには、ルートの `include/` のファイルと名前がぶつからないよう、`consh_` を付ける。
* 大きくなったら、`consh_lexer.se`、`consh_expand.se`、`consh_builtin.se` などに分ける。

## 実行

```
bin/consh [--conma-parser] [--dump] スクリプト [引数 ...]
bin/consh
```

引数なしで起動すると対話モードになり、標準入力から1行ずつ読んで実行する（段階 13）。プロンプトは変数 `PS1` と `PS2`（なければ `$ ` と `> `）。エラーでは終わらず、次のプロンプトに戻る。Ctrl-C は実行中のコマンドだけを止め（`$?` は 130）、`&` で起動したジョブは止めない。入力が終われば（Ctrl-D）終わる。
標準入力が端末で、[rlwrap](https://github.com/hanslub42/rlwrap) があれば（`brew install rlwrap` など）、rlwrap を通して起動し、行の編集と履歴（`~/.consh_history`）が使える。環境変数 `CONSH_NO_RLWRAP` を空でない値にすると、rlwrap を使わない。

ConMa 版は、既定では構文解析をせず、Python の `consh_parse --pos` が作った構文木のファイルを、ConMa の `__Sexp_read__`（Step 30）で読む（形式は [AST.md](AST.md)）。
`--conma-parser` を付けると、ConMa 版の構文解析（`consh_parser.se`、段階 12）でスクリプトを読み、Python を使わずに動く。
構文木は `consh_parse --pos` と同じで、構文エラーのメッセージは `consh_parse:` の代わりに `consh:` で始まる。
`--dump` を付けると、実行せず、ConMa 版が読んだ構文木を S 式に書き戻して出す。
ConMa のモジュールは `/tmp/consh.module.se` に作り、`.se` のソースが変わったときだけ作り直す。

### できること（段階 3〜13）

* 変数定義、`export`、前置の変数定義、語の展開
    * `$x`、`${x}`、`"$x"` の区別、入れ子の LazyList の葉、OFS による文字列化、既定値 `${x-値}`、値 `(語 ...)`、ANSI-C クォート `$'...'`
    * 未定義の変数と、足りない位置パラメータの参照はエラーになる
* 外部コマンドの起動と `$?`。スクリプトは最後の文の `$?` で終わる
* ファイルへのリダイレクト（`<`、`>`、`>>`、`2>`、`2>&1`、`1>&2`）
* 関数の定義と呼び出し、変数リスト `(a b . rest)`、`return`、レキシカルスコープ、前置の変数定義の層
    * 関数と組み込みコマンドには、`${list}` を LazyList のまま渡す。外部コマンドには葉ごとの語にして渡す
    * 前置の変数定義は、同じ文の語の展開にも反映する（`OFS=, echo "$list"`）
    * 先頭の語が `${list}` なら、要素を順に引数にする（先頭の要素だけは再帰的に展開してコマンド名を取る）。先頭の語の LazyList が空ならエラー
* 組み込みコマンド `echo`、`cd`、`defined`、`builtin`、`command`、`stdin`、`wait`、`kill`、`exit`
* if 文（`elif`、`else`、`fi` の後のリダイレクト）
* リストfor文、`break [変数名]`、`continue [変数名]`（`done` の後のリダイレクト）
    * 語は関数の引数と同じ規則で展開し、LazyList の値は1階層だけ開いて要素ごとに回す
* コマンド置換 `$( )`（段階 4）。標準出力の要素の LazyList が値になる。外部コマンドの出力は行ごとの要素になる
    * 別の VProc で動かし、終わるのを待たずに値にする。値は読み進めるのと並行に作られるので、`for x in $(yes)` も終わる
    * 文の終わりに、`$( )` が終わるか、出力が 16 要素たまって書き手が待つまで待つ。出力の少ない `$( )` の副作用（`x=$(mkdir d)`）は次の文より前に終わる
    * 中の変数定義、関数定義、`export`、`cd`、`$?` は外に影響しない。中から `return` や外のループへの `break`、`continue` はできない
* パイプライン `f | g`（段階 5）。各要素を別の VProc で動かし、前の要素の出力の要素を次の要素の標準入力にする
    * `$?` は最後の要素の終了ステータス。中の変数定義、`export`、`cd` は外に影響しない
    * 読み手が先に終わると、書き手は次に書いたときに止まる（`yes | head -1` が終わる）
    * パイプに書き手や読み手がいなくなるリダイレクト（`f > file | g`、`f | g < file`）はエラー
    * 両側が外部コマンド（先頭の語がクォートか裸文字だけ）なら、OS のパイプで直接つなぐ（段階 8）。それ以外は要素を1つずつ受け渡すので遅い（PLAN-ja.md の 2.3）

* 変数リストへのリダイレクト（段階 6）
    * `> (a b . rest)`、`2> (a b . rest)`：出力の1つ目、2つ目の値を `a`、`b` に、残りの LazyList を `rest` に入れる。変数の数だけ受け取った後に書くとコマンドを止める（`$?` は 0）
    * `< (a b . rest)`：`a`、`b` の値と `rest` の要素を標準入力にする
* 組み込みコマンド `stdin`（段階 6）。標準入力の要素を標準出力に出す。関数と呼び出し側で読み出し位置を共有する
    * `stdin > (a . rest)` は `a` の分だけ位置を進め、`rest` は参照した時点で読む

* `&`、`$!`、`$$`、組み込みコマンド `wait`、`kill`（段階 7）
    * `&` のパイプラインは別の VProc で動き、`$!` はその VProc の番号（パイプラインなら最後の要素）。`$$` はインタプリタのプロセスID
    * `wait ID` の `$?` はジョブの終了ステータス（`kill` で止めたら 143、ないジョブは 127）。`wait` だけなら、すべてのジョブを待つ
    * `f > (a b . rest) &` の `a`、`b` は値ができるまで待つ遅延の値、`rest` は伸びる LazyList になる
    * スクリプトの終わりに、まだ終わっていないジョブを待つ
* 外部コマンドの出力を直接つなぐ（段階 8）
    * 外部コマンドの標準出力がトップレベルの標準出力のままなら、シェルの標準出力の Stream をそのまま渡す（端末なら端末のまま。`ls` が複数列になり、`less` や `vi` も動く）
    * 外部コマンドどうしのパイプは、OS のパイプでつなぐ
* 外部コマンドの引数のバイト数の上限（段階 9）
    * コマンド名を含む各引数の UTF-8 のバイト数 + 1 の合計が、環境変数 `ARG_MAX`（なければ OS の値）を超えたらエラーにする。無限の LazyList を引数に展開しても止まる
* 関数、if 文、for 文の中の外部コマンドも、出力先が端末やファイルのままなら直接書く（段階 10）
* glob（段階 11）
    * `*`、`?`、`[...]` を、外部コマンド、関数、組み込みコマンドの引数、for 文の語、値 `(語 ...)`、リダイレクト先に適用する。一致しなければ語を残す
    * `${-語}` は、一致した名前の LazyList（一致しなければ空）。関数には1つの LazyList として渡せる


標準出力は、要素（行）の並びとして扱う。

* トップレベルの標準出力は、要素を1行ずつ書く。
* 外部コマンドの標準出力が `$( )`、変数リスト、関数や組み込みコマンドとのパイプに行くときは、パイプで受け取って行ごとの要素にする。そのため、最後の行に改行がなければ改行が付き、`\r\n` は改行になる（PLAN-ja.md の 1.3）。
* 外部コマンドの標準出力が端末やファイルのままなら、バイト列をそのまま書く。トップレベルでも（段階 8）、出力を端末やファイルに向けた関数、if 文、for 文の中でも（`f > ファイル`、`for …; done > ファイル`、段階 10）同じである。外部コマンドどうしのパイプも、バイト列をそのまま渡す。
* 要素が LazyList のとき（`echo ${list}`）、ストリームに書くときに OFS で文字列化して1行にする。端末に書くときはトップレベルの OFS、`> ファイル` のときはリダイレクトを書いた文の OFS を使う。
* 標準エラー出力は、要素にせず、そのまま書く。ただし `2>&1` で標準出力と同じ行き先にしたときは、標準出力と同じ要素の並びに入る。

仕様にない部分は、次のようにした。

* 変数定義、`export`、関数定義の文の後、`$?` は 0 になる（Bash と同じ）。本体が空の関数の戻り値も 0。
* 環境変数は、起動時の環境変数から始める。局所変数には取り込まないが、局所変数がなければ参照できる。
* 仕様で「エラーとする」もの（未定義の局所変数の `export`、リダイレクト元の重複、リダイレクト先が1語にならない、関数の中の `$1`、`$@`、`$#`、0 から 255 でない `return`、パイプラインの中の `return`、まだないもの）は、メッセージを出して終了ステータス 1 で終わる。
* コマンドを起動できない場合は `$?` を 127、ファイルを開けない場合や `cd` できない場合は 1 にして続ける。
* 語がすべて消えた単純文は、リダイレクトだけを行い、`$?` を 0 にする。
* 環境変数 `HOME` がないときの引数なしの `cd` は、メッセージを出し、`$?` を 1 にして続ける（ディレクトリが見つからないときと同じ）。
* `defined` に変数名がないか、2つ以上ある場合はエラーとする。
* `echo` はオプションを取らず、引数を空白で区切って連結した1つの要素を出す。
* if 文の中の関数定義も、変数定義と同じく if 文の外のスコープに入る。
* if 文の条件、本体、`else` のスクリプトを実行する前の `$?` は、そのときの値のまま。たとえば `else` の中の `$?` は最後の条件の値になる（Bash と同じ）。
* キーワードの直後に `)` は置けない（PLAN-ja.md の文法どおり）。そのため `$(if a; then b; fi)` は構文エラーになる。
* `cd` は、それを実行した VProc のカレントディレクトリを変える（ConMa の Step 23）。パイプラインの要素と `$( )` の中の `cd` は、シェルのカレントディレクトリを変えない。
* パイプラインと `$( )` は、ConMa の `__VProc_start__`（Step 24）と `__OS_wait_writable__`（Step 25）を使う。`&`、`kill`、`$!`、`$$` は Step 26 の `__VProc_kill__`、`__OS_kill__`、`__VProc_id__`、`__OS_getpid__` を使う。`ARG_MAX` がないときは Step 27 の `__OS_sysconf__` で OS の値を得る。glob は Step 29 の `__OS_listdir__` を使う。対話モードの Ctrl-C は Step 31 の `__OS_trap_interrupt__` を、`&` のジョブの外部コマンドの起動は Step 32 の `__OS_spawn_detached__` を使う。

構文木と展開の結果を見るには、Python の参照実装を使う。構文木の形式は [AST.md](AST.md)、展開の結果の形式は `bin/consh_parse` の先頭に書いてある。`--pos` を付けると、構文木に行と桁が入る。

```
bin/consh_parse [--pos] スクリプト
bin/consh_parse --expand スクリプト [引数 ...]
```
