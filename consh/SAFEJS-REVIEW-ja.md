## 2. 24ada60：js を既定で使えなくする

使えるかどうかを起動したときに 1 度だけ決め、`$?` で 3 つの状態（使える、使えない、JavaScript がない）を区別する作りは妥当である。ブラウザで URL の引数ではなくサーバーの config.json で決めるのも、リンクで外から有効にされないので正しい。

1. **子のプロセスにも引き継がれる**
    * `CONSH_ENABLE_JS=1` は環境変数なので、ConSh から起動した ConSh にも引き継がれる（`env` の出力で確かめた）。
    * そのため、信頼したスクリプトの中から他人のスクリプトを `consh other.sh` で動かすと、そちらでも js が使える。
    * 意図した動きなら README に一言書く。そうでないなら、起動のときに環境変数から消す。
2. **Node.js では、使えなくする意味が薄い**
    * Node.js 版の ConSh は、もともと外部コマンドを実行できるので、js を止めても、できることはほとんど減らない。
    * 守れるのはブラウザ版だけ、と README に書いておくと、誤解されない。

## 3. SJS の計画

全体の方針はよい。`(( ))` の中にだけ書くこと、段階 A のホストで動かす形から段階 B の ConMa への変換に進むこと、変換を ConMa を検証する材料にすることである。2.1 の「今の `((` と `$((` は構文エラーなので、意味の変わる書き方はない」も確かめた。文の始めの `(( 1 + 2 ))`、語の中の `$(( 1 + 2 ))`、リストの入れ子（`x=((a b) c)`、`x=(a (b c))`、`> ((a b) c)`）は、どれも構文エラーである。

### 3.1 設計上のリスク

1. **段階 A で、await の後に大域変数の参照先が入れ替わる**（4.1）
    * 4.1 では、評価のたびに「今の SJS変数」の Proxy を差し替える。
    * すると、`async` 関数が await の後に大域変数を読み書きしたとき、そのとき差し替わっている別の評価の SJS変数を見てしまう。別の VProc の、別のシェルの変数である。
    * 案：関数を呼ぶたびに、その呼び出しの SJS変数を閉じ込める。または、段階 A では、`async` 関数の中で大域変数を使えなくする。
2. **段階 A と段階 B で、オブジェクトの写しの意味が変わりうる**（2.2 の 4.4）
    * 「関数、`$( )` などで写しになる」とあるが、段階 A で写されるのはホストの表の番号だけである。そのため、シェル関数の中の `(( o.a = 1 ))` は、呼び出し側の `o` も変える。
    * 段階 B で Dict を書き込み時に写す（COW）なら、呼び出し側は変わらない。
    * 段階 A と段階 B で同じ結果になる、という目標に関わるので、浅い写しか深い写しかを決めて書くべきである。
3. **段階 A の SJS は、CONSH_ENABLE_JS がなくても動くのか**（2.3）
    * 段階 A の SJS は、ホストの `Function` で動き、5 にあるとおり安全の境界ではない。
    * それなのに、`CONSH_ENABLE_JS` がなくても `(( ))` が動くなら、3.22 で js を止めた効果が、確認の抜け道 1 つで失われる。
    * 段階 A の間は `(( ))` も `CONSH_ENABLE_JS` を条件にする、などと明記するべきである。
4. **4.3 の継続の最適化は、reset と shift と両立しない**
    * 条件 1〜3 を満たしても、CChain のプリミティブで LCont が取り出され、別の CChain の上で呼ばれれば、`return` の時の CChain は `__Cont_get__` の時と同じにならない。ConSh の `shift` と `$k` がそうである。
    * 今の `return` は、取り出した時の CChain に戻る。最適化した形は、今の CChain の一番上に戻るので、意味が変わる。
    * その関数の実行中に CChain が取り出されうるかどうかは、構文だけでは決められない。最適化を、継続を取り出さないことがわかっているコードに限る必要がある。
    * この節は SJS の計画からは独立しているので、docs/ROADMAP.md など ConMa の文書に移すと見つけやすい。

### 3.2 使い勝手

5. **`$(( n + 1 ))` で、シェル変数が読めない**（2.2 の 4）
    * Bash の利用者は、`n=3; echo $(( n + 1 ))` と書けると思うはずである。しかし `n` は SJS変数なので、未定義のエラーになる。
    * SJS変数が未定義で、同じ名前のシェル変数があるときは、メッセージで `$(( (x) => … )) ${n}` の形を案内するとよい。2.4 で FOR-BASH-USERS.md に書くと決めている件にも加えるべきである。
    * 対応（2026-11-11）：SAFEJS-PLAN-ja.md の 2.2 の 7 に、`$名前` でシェル変数を読む規則を足した（`$(( $n + 1 ))`）。演算子の被演算子の `$n` は数にし（数にならなければエラー）、`+` は数どうしだけを足して、文字列の連結はテンプレート文字列で書くことにした（2.2 の 7、3.1 の演算の型）。代入を許すかは、2.4 で決める。未定義の SJS変数のメッセージでは、`$n` と書くよう案内すればよい。
6. **戻り値を標準エラーに出すことの影響**（2.2 の 3）
    * 戻り値を受け取らずに呼ぶと、値が端末にエラーのように出る。
    * `2>/dev/null` で値を捨てると、エラーのメッセージも消える。
    * 計画は割り切っているが、この 2 つも書いておくとよい。
7. **大域変数を、呼び出した時の変数として読む**（2.2 の 4.5）
    * これは動的なスコープなので、作った場所の変数を覚えるクロージャを期待する人は驚く。
    * 例を 1 つ載せるとよい。たとえば、シェル関数の中で作った関数が、外で呼ばれたときにどの `n` を見るかである。

### 3.3 細かい点

8. **安全の確認は拒否リストに近い**
    * 3.2 は、拒否するプロパティ名と、許可する大域の名前を組み合わせている。
    * 段階 A を少しでも堅くするなら、メソッドの名前も許可するものだけにすると、抜け道が減る（`.call`、`.bind` なども含めて）。
9. **将来、リストの入れ子を足すときの衝突**
    * 将来 ConSh にリストの入れ子（`x=((a b) c)`）を足すと、値の位置の `((` とぶつかる。
    * 今は `$((` と文の始めだけなので問題ないが、文法のメモに残しておくと安全である。
